## §1 背景

### 1.1 为什么要统一路径管理？

项目经历了多次路径问题的反复，核心痛点如下：

1. **`process.cwd()` 不可靠**：用户可能从任意目录启动程序，而 `process.cwd()` 返回的是"用户当前工作目录"，不是"项目根目录"。编译为独立 exe 后，`cwd` 更是不可预测。

2. **`__dirname` 编译失效**：使用 `esbuild` 等工具编译为单文件或 exe 后，`__dirname` 指向临时目录，而非源码位置。

3. **路径分裂（双轨制）**：多个模块各自实现了路径解析逻辑，导致同一个路径含义在不同模块中不一致。例如 `memory/services/paths.ts` 和 `config/paths.ts` 对"记忆目录"的解析结果可能不同。

4. **数据混乱**：用户数据（配置、个人记忆）和系统数据（数据库、日志）混放，导致备份、迁移、清理困难。

### 1.2 治理历程

- 早期：各模块自行管理路径，使用 `process.cwd()` + 字符串拼接
- 中期：引入 `pyapp.ts` 引导层，提供 `resolveProjectRoot()` 等基础函数
- 当前：建立 `config/paths.ts` 统一管理中心，提供 36+ 个 `resolve*` 导出函数，覆盖 L1/L2/L3 全层级
- 本次：将路径规范固化为 rule 文件，约束后续所有编码行为，并对存量代码进行四阶段治理

## §2 三层架构（L1 / L2 / L3）

### 2.1 层级定义

| 层级 | 目录 | Git 跟踪 | 用途 | 根函数 | 典型数据 |
|------|------|----------|------|--------|---------|
| **L1：代码文档** | `app/`（除 `app/data/`） | ✅ 跟踪 | 源代码、文档、内置资源 | `resolveProjectRoot()` | — |
| **L2：项目数据** | `app/data/` | ❌ 忽略 | 项目级运行时数据 | `resolveDataDir()` | 数据库、会话、日志、缓存、项目记忆、治理审计 |
| **L3：用户数据** | `~/.pyapp/` | ❌ 忽略 | 用户级跨项目数据 | `resolvePyappHome()` | 用户配置、个人记忆、OAuth 令牌、权限规则、附件 |

### 2.2 分层判断方法

判断一条数据属于哪个层级，回答两个问题：

```
Q1：这条数据换个项目还有用吗？
  ├─ 有用 → L3（用户数据）：用户配置、个人记忆、OAuth 令牌
  └─ 没用 → L2（项目数据）：数据库、会话、项目记忆

Q2：这条数据用户需要自己管理吗？
  ├─ 需要 → L3：配置、设置、个人文件
  └─ 不需要 → L2：缓存、日志、临时文件
```

### 2.3 数据流向图

```
用户操作
    │
    ├─ L1：读取代码、文档、内置资源
    │      └─ resolveProjectRoot()
    │
    ├─ L2：项目运行时数据
    │      ├─ 数据库读写      → resolveDbPath()
    │      ├─ 会话管理        → resolveSessionsDir()
    │      ├─ 日志写入        → resolveLogsDir()
    │      ├─ 缓存读写        → resolveCacheDir()
    │      ├─ 项目记忆        → resolveMemoryDir()
    │      ├─ 团队记忆        → resolveTeamMemoryDir()
    │      ├─ 治理审计        → resolveGovernanceDir()
    │      ├─ 安全数据        → resolveSecurityDir()
    │      └─ 定时任务        → resolveChronosDir()
    │
    ├─ L3：用户级跨项目数据
    │      ├─ 用户配置        → resolveUserConfigPath()
    │      ├─ 用户设置        → resolveUserSettingsPath()
    │      ├─ 个人记忆        → resolveUserMemoryDir()
    │      ├─ OAuth 令牌      → resolveOAuthDir()
    │      ├─ 权限规则        → resolvePermissionsDir()
    │      └─ 附件            → resolveAttachmentsDir()
    │
    └─ 用户工作目录（工具操作）
           └─ process.cwd()
```

## §3 核心规则：用户数据保存 vs 系统数据保存

### 3.1 为什么这是最重要的规则？

用户数据（L3）和系统数据（L2）的混放会导致：

1. **备份困难**：用户想备份自己的数据，却不知道哪些文件是自己的
2. **迁移问题**：用户换项目时，个人配置被遗留在旧项目的 `app/data/` 中
3. **清理风险**：清理"项目数据"时误删用户数据，或反过来
4. **权限混淆**：用户数据可能涉及个人隐私，不应暴露在项目目录中

### 3.2 L2 / L3 归属速查表

| L2（项目数据 → `resolveDataDir()` / `resolve*()`） | L3（用户数据 → `resolvePyappHome()` / `resolveUser*()`） |
|-----------------------------------------------------|---------------------------------------------------------|
| 数据库（`app.db`） | 用户配置（`config.json`） |
| 会话文件（`sessions/`） | 用户设置（`settings.json`） |
| 日志文件（`logs/`） | 用户个人记忆（`memory/`） |
| 缓存（`cache/`） | OAuth 令牌（`oauth/`） |
| 项目记忆（Auto Memory） | 权限规则（`permissions/`） |
| 团队记忆（Team Memory） | 用户附件（`attachments/`） |
| 治理数据（`governance/`） | 用户技能（`skills/`） |
| 安全审计数据（`security/`） | SOUL.md / USER.md |
| 定时任务数据（`chronos/`） | |

### 3.3 违例示例

```typescript
// ❌ P0：系统数据（数据库）写到用户目录
const dbPath = join(resolvePyappHome(), 'app.db');
// → 后果：用户清理个人数据时误删数据库

// ❌ P0：用户数据（配置）写到项目目录
const ucfg = join(resolveProjectRoot(), 'app', 'data', 'user-config.json');
// → 后果：用户切换项目后配置丢失

// ❌ P0：不区分层级，全部写到 cwd
const data = join(process.cwd(), 'data');
// → 后果：cwd 不可信，数据可能写错位置

// ❌ P1：用户数据路径使用 process.cwd() 兜底
const configHome = process.env.HOME || process.cwd();
// → 后果：用户数据可能落在项目目录
```

### 3.4 正确示例

```typescript
// ✅ L2：系统数据
const dbPath = resolveDbPath();
const sessionPath = resolveSessionsDir();
const logsDir = resolveLogsDir();
const cacheDir = resolveCacheDir();
const memoryDir = resolveMemoryDir();

// ✅ L3：用户数据
const userConfig = resolveUserConfigPath();
const userSettings = resolveUserSettingsPath();
const userMemory = resolveUserMemoryDir();
const oauthDir = resolveOAuthDir();
const permissionsDir = resolvePermissionsDir();
```

## §4 路径使用红线

### 🔴 R1：禁止使用 `__dirname`

- **原因**：编译为独立 exe 后，`__dirname` 指向临时解压目录，而非源码位置
- **例外**：无（任何场景都不应使用）
- **替代方案**：使用 `resolveProjectRoot()` 拼接

### 🔴 R2：禁止使用 `process.cwd()` 做持久化

- **原因**：用户可能从任意目录启动程序，`cwd` 不等于项目根目录
- **唯一允许场景**：获取"用户当前工作目录"用于工具操作的目标（如 Bash/CD、Glob/Grep 的工作目录）
- **替代方案**：持久化操作使用 `config/paths.ts` 的 `resolve*` 函数

### 🔴 R3：禁止在 `config/paths.ts` 外定义路径解析逻辑

- **原因**：防止双轨制，确保路径含义一致
- **例外**：`pyapp.ts` 引导层的根目录解析逻辑
- **替代方案**：需要新路径时，在 `config/paths.ts` 中新增导出函数

### 🔴 R4：禁止在 `pyapp.ts` 外实现根目录解析

- **原因**：根目录解析涉及 `--project-dir` 参数、环境变量、exe 路径推断、`cwd` 降级等多层回退，只在 `pyapp.ts` 中统一实现
- **替代方案**：各模块通过 `bootstrap/state.ts` 获取 `getProjectRoot()`

### 🔴 R5：禁止硬编码路径字符串

- **原因**：硬编码路径与环境无关，不可移植；`./` 相对路径依赖 cwd
- **禁止形式**：绝对路径（`C:/...`）、相对路径（`./data/`、`../config/`）、Unix 路径假定
- **替代方案**：所有路径通过 `config/paths.ts` 函数生成

### 🔴 R6：禁止新模块自己实现路径函数

- **原因**：路径函数应收敛到 `config/paths.ts`，新模块不应重复造轮子
- **例外**：无
- **替代方案**：在 `config/paths.ts` 中新增导出函数

### 🔴 R7：严格区分 L2（项目数据）与 L3（用户数据）

- **原因**：数据混放导致备份困难、迁移问题、清理风险、权限混淆
- **判断方法**：见 §3.2 归属速查表，或使用 §2.2 分层判断方法
- **替代方案**：不确定时，优先使用 `resolveDataDir()`（L2），用户明确需要跨项目共享的数据才用 L3

## §5 路径使用决策矩阵

### 5.1 场景 → 函数映射

| 场景 | 层级 | 该用的函数 |
|------|------|-----------|
| 获取项目根目录 | L1 | `resolveProjectRoot()` |
| 数据库操作 | L2 | `resolveDbPath()` |
| 会话数据读写 | L2 | `resolveSessionsDir()` / `resolveSessionFilePath(id)` |
| 日志写入 | L2 | `resolveLogsDir()` |
| 缓存读写 | L2 | `resolveCacheDir()` |
| 记忆读写 | L2 | `resolveMemoryDir()` / `resolveTeamMemoryDir()` |
| 附件读写 | L2 | `resolveAttachmentsDir()` / `resolveAttachmentsDateDir()` |
| 文档加载 | L1 | `resolveDocsDir()` |
| 内置资源加载 | L1 | `join(resolveProjectRoot(), 'app', ...)` |
| 用户配置读写 | L3 | `resolveUserConfigPath()` / `resolveUserSettingsPath()` |
| 用户级记忆读写 | L3 | `resolveUserMemoryDir()` |
| 治理审计数据 | L2 | `resolveGovernanceDir()` |
| 安全数据读写 | L2 | `resolveSecurityDir()` |
| OAuth 令牌 | L3 | `resolveOAuthDir()` |
| 权限规则 | L3 | `resolvePermissionsDir()` |
| 确保目录存在 | — | `ensureDir(dirPath)` |
| 新增数据子目录 | L2 | `resolveDataSubDir(name)` |

### 5.2 决策树

```
需要文件路径？
│
├─ 数据属于「这个项目」还是「这个用户」？
│   ├─ 这个项目 → L2 ──→ resolveDataDir() 或专用函数
│   └─ 这个用户 → L3 ──→ resolvePyappHome() 或 resolveUser*()
│
├─ 是代码/文档/内置资源？
│   └─ L1 ──→ resolveProjectRoot() 拼接
│
├─ 是用户工作目录？
│   └─ 工具操作目标 ──→ process.cwd()（仅用于此场景）
│
└─ 不确定？
    └─ 找 config/paths.ts 看是否有导出，没有则新增
```

## §6 典型错误模式

### 6.1 错误模式分类

| 模式 | 错误写法 | 正确写法 | 风险等级 |
|------|---------|---------|---------|
| `cwd` 持久化 | `join(process.cwd(), 'app', 'data', 'app.db')` | `resolveDbPath()` | 🔴 P0 |
| `cwd` 配置 | `process.cwd()` 作为配置目录 | `resolvePyappHome()` 或 `resolveDataDir()` | 🔴 P0 |
| `cwd` 默认参数 | `cwd: process.cwd()` 作为路径函数默认值 | 使用 `resolve*()` 或要求调用方传入 | 🟠 P1 |
| `cwd` 资源读取 | `join(process.cwd(), 'agents.md')` | `join(resolveProjectRoot(), 'agents.md')` | 🟠 P1 |
| `__dirname` 资源 | `join(__dirname, 'worker.js')` | `join(resolveProjectRoot(), 'app', 'src', ..., 'worker.js')` | 🟡 P2 |
| `__dirname` 数据 | `join(__dirname, '..', 'data')` | `resolveDataDir()` | 🟡 P2 |
| 双轨制 | 模块内自实现路径函数 | 使用 `config/paths.ts` 或在其中新增 | 🟡 P2 |
| L2/L3 混淆 | 用户数据写项目目录或反之 | 按归属速查表选择正确层级 | 🔴 P0 |

### 6.2 修复优先级

| 风险等级 | 定义 | 处理时限 |
|---------|------|---------|
| 🔴 P0 | 数据持久化到错误位置，可能导致数据丢失或混乱 | 立即 |
| 🟠 P1 | 路径解析依赖 cwd，cwd 变化时可能读不到资源 | 近期 |
| 🟡 P2 | 使用 `__dirname` 或存在双轨制，编译 exe 后可能失效 | 中期 |
| 🟢 安全 | 工具操作的目标目录，使用 `process.cwd()` 合理 | 无需修复 |

## §7 新增路径流程

当需要新增一个数据存储路径时，按以下流程操作：

```text
Step 1：确定层级
        ├─ 数据属于「这个项目」？→ L2
        ├─ 数据属于「这个用户」？→ L3
        └─ 是内置资源？→ L1

Step 2：检查 config/paths.ts 是否已有对应函数
        ├─ 有 → 直接使用
        └─ 无 → 进入 Step 3

Step 3：在 config/paths.ts 中新增导出函数
        ├─ 命名规范：resolve<语义>Dir / resolve<语义>Path
        ├─ 目录用 Dir，文件用 Path
        └─ 示例：resolveMyFeatureDir()

Step 4：若是目录，加入 ensureDataDirectories() 的创建列表

Step 5：在新模块中 import 使用

Step 6：运行 bun run typecheck 验证
```

## §8 编译 exe 特殊规则

### 8.1 exe 环境下的路径变化

| 场景 | 开发环境 | exe 环境 |
|------|---------|---------|
| `process.cwd()` | 终端当前目录 | 用户双击 exe 时的目录 |
| `__dirname` | 源码目录 | 临时解压目录 |
| `__filename` | 当前文件路径 | 临时解压路径 |
| `process.execPath` | node.exe | 用户 exe 路径 |
| `argv[0]` | 脚本路径 | exe 路径 |

### 8.2 exe 路径保障机制

`pyapp.ts` 中的六道防线：

1. `chdir` 到项目根目录
2. `Object.defineProperty(process, 'cwd')` 拦截
3. `fs.mkdirSync` / `fs.mkdir` 拦截
4. 创建预定义目录
5. 设置 `LIRI_PROJECT_DIR` 环境变量（⚠️ 2026-09-11 O11 修正：原写作 `PYAPP_PROJECT_DIR`，代码从不读取该名）
6. 全局异常捕获

### 8.3 未覆盖的风险

即便有六道防线，以下场景仍需注意：

- **Worker 脚本加载**：`__dirname` 用于定位 Worker 脚本（如 `dreamWorker.js`）时，需改用 `resolveProjectRoot()` 拼接
- **策略 JSON 加载**：治理策略文件通过 `__dirname` 定位，需改为相对 `resolveProjectRoot()` 的路径
- **语言包加载**：`process.cwd()` 用于定位语言包目录，需改为 `resolveProjectRoot()` 拼接

## §11 治理计划

按四阶段推进，详见 [路径整改实施方案.md](file:///e:/PY/CODES/Liri/app/docs/dev_docs/20260529/路径整改实施方案.md)：

| 阶段 | 范围 | 优先级 | 目标 |
|------|------|--------|------|
| **Phase 0** | P0 数据安全修复 | 🔴 立即 | 所有持久化操作路径走 `config/paths.ts` |
