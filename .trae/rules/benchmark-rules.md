# 对标分析工作规范 / Benchmark Analysis Rules

> 通用对标分析方法论，适用于多产品功能对比、技术选型评估、差距分析等任务。
>
> Generic benchmark analysis methodology for multi-product comparison, technology evaluation, and gap analysis.

**核心原则：先盘点、再读码、后对比；没有读过的代码不下结论。**
**Core principle: Inventory first, read code second, compare third. No conclusion without reading the source.**

---

## 一、四阶段递进法 / Four-Phase Progressive Method

所有对标分析必须按以下四个阶段顺序执行，**不得跳跃**。

```
Phase 0: 清单编制 (Inventory)      → 摸清各产品模块家底，验证目录存在性
Phase 1: 深度阅读 (Deep Reading)    → 逐模块阅读核心代码，到函数/类级别
Phase 2: 维度提取 (Dimension Extraction)  → 提炼统一对比维度
Phase 3: 逐维对比 (Dimension Comparison)  → 按维度填写对比矩阵，含源码证据
Phase 4: 报告合成 (Report Synthesis)      → 基于矩阵撰写报告，含不足分析专项
```

### 阶段间质量门禁

每个阶段完成后，必须回答以下问题才能进入下一阶段：

| 关口 | 检查项 |
|------|--------|
| Phase 0 → 1 | 模块清单是否完整？是否遗漏了一级子目录？**清单是否经过 `LS` 或 `Glob` 已验证目录真实存在？是否有声称存在但实际不存在的模块？** |
| Phase 1 → 2 | **每个模块是否读取了 index.ts + 核心实现？分析是否深入到函数签名、参数、返回值和职责级别？是否有模块标记为"未读"还进入了下一阶段？** |
| Phase 2 → 3 | 维度是否覆盖所有模块？维度定义是否可操作（不模糊）？完整度等级是否有判定标准？ |
| Phase 3 → 4 | 矩阵每个结论都有证据链接？❌ 结论是否经过关键词搜索确认？是否还有 🔍 待确认的条目？**每个评级的结论是否都有对应的源码行号引用？** |

## 二、Phase 0：清单编制 / Inventory

### 目标

编制各产品的模块清单，作为后续分析的底表。**清单不准，后续分析全是空中楼阁。**

### 操作步骤

| # | 操作 | 方法 |
|---|------|------|
| 0.1 | 扫描目标项目源目录 | 遍历目录树，记录一级和二级子目录 |
| 0.2 | 读取入口文件获取导出清单 | 读取 `index.ts` / `__init__.py` |
| 0.3 | 若无入口文件，遍历目录下所有文件 | 读取各文件获取类/函数导出 |
| 0.4 | 记录代码规模 | 源文件数、测试文件数、估算总行数 |
| 0.5 | 记录测试文件清单 | 搜索 `*.test.*` / `test_*.py` |
| 0.6 | **验证目录存在性** | **对清单中每个声称存在的模块，使用 `LS` 或 `Glob` 工具验证目录是否真实存在。防止 inventory 误差。** |

### 清单准确性验证（Inventory Verification）

> **经验教训**: 本分析过程中发现原始 inventory 声称 Liri 有 68 个模块，但实际 `LS` 验证发现其中 `prompts/`、`bridge/`、`account/`、`batch/`、`exchange/`、`migration/`、`persistent-state/` 共 **7 个目录实际上不存在**。

**强制验证规则**:

1. **双重验证**：清单中的每个模块目录，必须通过 `LS` 或 `Glob` 确认存在后才能进入 Phase 1
2. **"声称作证"机制**：当 inventory 或文档声称某产品有某功能时，必须在源码中找到对应文件才能采信
3. **误差记录**：发现声称存在但实际不存在的模块，必须：
   - 在清单中标记为 `❌ 不存在`（并注明来源记录错误）
   - 在报告中记录为 inventory 误差
   - 追溯误差来源（人工录入错误？旧版本已移除？）
4. **防止"凭记忆写结论"**：禁止仅仅因为"记得之前读过"就写结论。每个结论都需重新验证

### 产物格式

每个产品一份独立清单，包含：目录结构树、导出接口表（含源文件+行号）、测试文件清单、代码规模统计、**验证状态列**（已验证/待验证/不存在）。

## 三、Phase 1：深度阅读 / Deep Reading

### 阅读优先级（洋葱模型）

```
第一层: 入口文件          (index.ts / __init__.py → 获取完整导出清单)
  ↓
第二层: 核心接口/抽象类   (interface, abstract class, type definitions)
  ↓
第三层: 核心实现          (Manager, Service, Engine, Provider)
  ↓
第四层: 辅助工具          (utils, helpers, types, constants)
```

> **重要实践**: `index.ts`（或 Python 的 `__init__.py`）是分析模块的首个入口。读取 index.ts 可以快速获得该模块**所有公开接口的完整清单**，这是了解模块职责和边界的最有效方式。

### 分析深度要求

**禁止停留在目录级分析**。每个模块的分析必须深入到：

| 级别 | 必须记录的内容 | 示例 |
|------|--------------|------|
| 模块级 | 模块职责、上下游依赖、架构角色 | session/ → 会话管理，依赖 database/ |
| 文件级 | 关键源文件路径+行号范围 | `index.ts#L10-L120` |
| 类/接口级 | 类名、类型(class/interface)、文件行号、完整职责 | `ChatSession` class at `chat.ts#L50-L200` |
| 函数级 | **函数签名、参数、返回值、职责** | `createChatService(config)` → `ChatService` |
| 导出级 | 所有 `export` 的公开 API | 完整记录 index.ts 的导出清单 |

### 记录内容

每个模块分析记录包含：
- **架构定位**（角色、上下游依赖、模块归属）
- **核心类/接口清单**（名称、类型、文件、行号、职责）
- **关键函数清单**（签名、文件、行号、入参、返回值、职责）
- **所有公开导出**（从 index.ts 获取的完整导出列表）
- **架构特点**（分层、模式、依赖注入、事件驱动等）
- **与竞品差异点**（初步标记 ✅/⚠️/❌/🔵/🟡）
- **不足项**（明确标记为不足并记录原因）
- **未理解的疑问**（等待后续交叉验证）

### 模块状态标注体系

每个模块分析完成后，必须使用以下统一标注标记其完成状态：

| 标记 | 名称 | 定义 | 使用场景 |
|:----:|------|------|---------|
| ✅ | **完整** | 功能实现完整，有测试覆盖 | 模块功能齐全，无重大缺陷 |
| ⚠️ | **基本** | 有核心实现但不够完善，或缺少关键特性 | 框架级实现，未生产化 |
| ❌ | **缺失** | 参考产品有此功能但目标产品完全没有 | 完全空白 |
| 🔵 | **独有** | 目标产品独有，其他参照产品均无 | 差异化优势能力 |
| 🟡 | **有但弱** | 功能存在但明显弱于所有参照实现 | 存在严重不足需要改进 |
| 🔴 | **风险** | 实现存在重大缺陷或安全风险 | 必须优先修复 |
| ★ | **领先** | 功能完整且有独特创新，竞品明显不及 | 核心竞争力 |

> **标注规则**: 一个模块可以有多个标注。例如 `✅★` 表示完整且领先，`⚠️🔵` 表示基础但独有。

## 四、Phase 2：维度提取 / Dimension Extraction

### 维度要求

1. **每个维度在各产品中都有对应物**（或明确标记为"无此模块"）
2. **粒度适中**——不大到无法比较，不小到碎片化
3. **维度之间有正交性**——尽量减少重叠

### 完整度等级定义

为避免主观判断偏差，统一使用以下标度：

| 等级 | 标记 | 定义 |
|------|:----:|------|
| 不存在 | ❌ | 源码中没有任何此功能的实现 |
| 基础 | ⚠️ | 有接口/抽象但实现不完整，或实现但缺少关键特性 |
| 完整 | ✅ | 功能实现完整，有测试覆盖 |
| 领先 | ★ | 功能完整且有独特创新，竞品明显不及 |

## 五、Phase 3：逐维对比 / Dimension Comparison

### 填写规则

**规则1：每个结论必须有证据链接**

格式：`[源文件名:行号](file:///absolute/path/to/file#L行号)`

必须标注到具体行号范围，例如 `index.ts#L10-L120` 而非仅文件名。

**规则2：没读过的代码标记为 "🔍 待确认"**

发现某产品可能有某个功能但尚未读取时，标记为 `🔍`，不得猜测为 ❌。

**规则3：发现遗漏时，回退到 Phase 1**

如果填写矩阵时发现某产品有之前未发现的模块，**暂停矩阵填写**，回到 Phase 1 补读该模块。

**规则4：每个评级都需要证据，不能只对 ❌ 标注证据**

| 评级 | 证据要求 |
|:----:|---------|
| ✅ | 至少引用 1 个核心实现文件 |
| ⚠️ | 说明缺少哪些关键特性，引用已有实现 |
| ❌ | **必须用 grep/SearchCodebase 验证过**才能写 ❌ |
| 🔵 | 说明独有设计特点，引用独有实现 |
| ★ | 说明领先于竞品的具体方面 |

### 评级体系（不足严重度分级）

当需要量化不足的严重程度时，使用以下 P0-P3 分级体系：

| 级别 | 名称 | 分值 | 定义 | 响应策略 |
|:----:|------|:----:|------|---------|
| **P0** | 致命缺失 | 1.0 | 对标参照均有，目标产品完全缺失，影响核心功能 | 必须立即修复 |
| **P1** | 严重不足 | 0.7 | 对标参照完善，目标产品有但明显弱于参照 | 高优先级迭代 |
| **P2** | 中等不足 | 0.4 | 功能存在但不够完善，或不满足生产需求 | 正常迭代 |
| **P3** | 轻微不足 | 0.2 | 功能基本完善但缺少某些非关键特性 | 低优先级优化 |

> **使用时机**: P0-P3 评级仅用于**不足分析专项报告**中，不替代模块状态标注（✅/⚠️/❌）。P0-P3 侧重改进紧迫性，模块标注侧重完成状态。

### 产物格式

```
## 维度N: [维度名]

### 子属性对比

| 子属性 | 产品A | 证据 | 产品B | 证据 | 产品C | 证据 |
|--------|-------|:----:|-------|:----:|-------|:----:|
| ...    | ✅    | 文件:行 | ⚠️   | 文件:行 | ❌   | 文件:行 |

### 综合分析
[该维度的整体对比结论，包含跨维度趋势分析]
```

## 六、Phase 4：报告合成 / Report Synthesis

### 合成规则

1. **矩阵优先**：报告中的任何结论，必须在矩阵中有对应条目
2. **优势/不足源自矩阵**：优势 = 评级 ≥ 竞品的条目；不足 = 评级 < 竞品的条目
3. **发展建议源自不足**：每条发展建议必须对应一条具体不足
4. **不添加矩阵之外的结论**

### 产出物规范

对标分析完成后，必须产出以下**三组核心文件**（按需可分多文件）：

| 文件 | 内容 | 目的 |
|------|------|------|
| **逐模块分析文件** | 每个模块的深度分析，含函数级导出清单、状态标注、对标对比、不足项 | 记录分析过程，可复验 |
| **不足分析专项报告** | 所有不足项汇总，按P0-P3分级，含改进建议、趋势分析、路线图 | 明确改进优先级，指导迭代 |
| **细化对比矩阵** | 按维度逐项对比，每个结论含源码证据链接、加权总分排名 | 量化对比，可验证 |

### 不足分析专项报告规范

不足分析报告必须包含：

1. **评级体系说明**：明确 P0-P3 定义和判定标准
2. **P0 — 致命缺失清单**：必须修复项，含对标参照情况、影响范围、改进建议
3. **P1 — 严重不足清单**：高优先级项，要求同上
4. **P2 — 中等不足清单**：正常迭代项，分模块列出
5. **P3 — 轻微不足清单**：低优先级项
6. **趋势分析**：
   - 不足严重度分布图（P0/P1/P2/P3 占比）
   - 不足按领域分布图
   - 按对标参照统计不足来源
   - 按工作量统计（小型/中型/大型）
7. **改进路线图建议**：分阶段（止血 → 追赶 → 深化 → 领先），每个阶段包含具体任务
8. **改进实施优先级矩阵**：以"高影响 × 高紧迫"为右上象限选出优先项

### 多文件输出策略

当对标范围过大导致单个文件膨胀时，允许按以下规则分拆：

1. **按模块拆分**：将独立模块拆分为单独文件，但保持命名一致
2. **按维度拆分**：Part1 = 架构/AI/工具, Part2 = 网关/插件/基础设施
3. **引入索引文件**：文件群必须有一个顶层索引/目录文件，清晰说明各文件内容和关系
4. **交叉引用**：分拆文件间需互相引用，避免信息孤岛

### 完成标准

对标分析完成后，必须满足以下条件才能视为"已完成"：

1. ✅ 无模块标注为"未读"或 "🔍"
2. ✅ 每个 ❌ 结论都经过 grep/SearchCodebase 双重验证
3. ✅ 每个结论都有源代码路径+行号证据
4. ✅ 存在不足的位置已如实记录，无美化/回避
5. ✅ 改进建议每条都对应具体不足
6. ✅ 按规范产出三组核心文件**

### README 更新原则

1. 仅提取报告中最关键的信息（模块成熟度矩阵 + 优势/不足列表 + 发展路线）
2. 每个结论保持与报告一致
3. 若报告更新，README 必须同步更新
4. **不美化、不回避**——公开发布的内容也需真实反映缺陷

## 七、常见错误禁止清单 / Common Mistakes

| # | 错误类型 | 示例 | 后果 |
|---|----------|------|------|
| 1 | 未找到就等于不存在 | 没有 grep 就写 ❌ | 严重遗漏 |
| 2 | 凭记忆写结论 | 记得之前读过但没再验证 | 内容过时/错误 |
| 3 | 跳跃式合成 | 跳过矩阵直接写报告 | 报告缺乏证据 |
| 4 | 模糊的完整度判断 | 说"比较完善"但不标等级 | 无法量化比较 |
| 5 | 隐藏缺陷 | 发现不足但不写入报告 | 评估失真 |
| 6 | 美化评估 | 把 ⚠️ 写成 ✅ | 误导决策 |
| 7 | **inventory 没验证就采信** | inventory 说有 68 模块，实际 7 个不存在 | 基表不准，全链崩塌 |
| 8 | **对比结论过于 general** | 只说"Liri 的工具系统比较完善"无证据 | 结论不可信，无法复验 |
| 9 | **只对 ❌ 标证据，✅ 和 ⚠️ 靠猜测** | ✅ 结论无源码引用 | 正反结论证据不对称 |
| 10 | **停留在目录级不下沉** | 只记录模块名不深入类/函数级别 | 分析表浅，遗漏细节 |
| 11 | **单文件超载** | 一个文件分析 40+ 模块，可读性差 | 读者无法消化 |
| 12 | **不区分"独有"和"领先"** | 把 🔵 当 ★ 用 | 误导战略判断 |

## 八、目录结构约定 / Directory Convention

### 标准目录结构

```
dev_docs/YYYYMMDD/
├── benchmark-steps.md                    ← 本次对标执行步骤文档
├── inventory/                            ← Phase 0: 模块清单
│   ├── product-a-inventory.md
│   ├── product-b-inventory.md
│   └── ...
├── analysis/                             ← Phase 1: 深度分析记录
│   ├── product-a/
│   │   ├── 01-module-xxx.md
│   │   └── ...
│   └── ...
├── dimensions.md                         ← Phase 2: 维度框架
├── matrix/                               ← Phase 3: 对比矩阵
│   ├── 01-dimension-xxx.md
│   └── ...
└── report.md                             ← Phase 4: 最终报告
```

### 三组核心产出物的文件命名规范

Phase 4 的三组核心文件使用固定前缀+按需后缀的命名方式：

| 产出物 | 前缀 | 后缀规则 | 示例 |
|--------|------|---------|------|
| 逐模块分析 | `Liri_Module_Deep_Dive` | 若分拆：`_PartN` | `Liri_Module_Deep_Dive.md` |
| 不足分析 | `Liri_Deficiency_Report` | 若分拆：`_PartN` | `Liri_Deficiency_Report.md` |
| 参照分析补充 | `Reference_Analysis_Supplement` | 若分拆：`_PartN` | `Reference_Analysis_Supplement.md` |
| 细化对比矩阵 | `Detailed_Comparison_Matrix` | `_PartN`（按维度拆分） | `Detailed_Comparison_Matrix_Part1.md` |

### 文件结构组织原则

1. **扁平优先**：尽量平铺在日期目录下，仅在文件超过 8 个时才创建子目录
2. **命名直观**：文件名应自阐明内容，读者无需打开文件即可知道其内容
3. **避免 old/ 目录积累**：每次分析产出的文件都放在日期目录顶层，之前版本不删除但通过 old/ 归档
