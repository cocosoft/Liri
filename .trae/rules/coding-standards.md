# 编码铁律 / Coding Standards

> 规则格式：`[CS-ID] [强制级别] 描述`。强制级别：MUST（违反即拒绝）/ SHOULD（需说明理由） / MAY（建议）。
>
> 这些规则是 [PY_APP.md](./PY_APP.md) 和 [project_rules.md](./project_rules.md) 的补充和强化，聚焦于 AI 编码中最常见的反模式。

## CS01 归一化检查（MUST）—— 新增前先查已有

**在写任何新代码之前，必须先执行以下检查，禁止跳过直接写。**

### CS01-001 [MUST] 三步检查法

```
Step 1: 搜索代码库中是否已有相同或相似实现
  → 使用 SearchCodebase / Grep 搜索功能关键词
  → 搜索同名字段、同名函数、同名类型

Step 2: 确认已有代码是否能直接复用/扩展
  → 能复用 → 直接复用，不新增
  → 需扩展 → 在已有代码上扩展，不另起炉灶
  → 不能动 → 进入 Step 3

Step 3: 寻找根因方案
  → 这个问题的根本原因是什么？
  → 有没有从架构层面一次性解决的方案？
  → 临时方案必须标注 `// TODO: CS01-ROOTFIX` 并说明根因方案
```

### CS01-002 [MUST] 禁止重复造轮子检查清单

| 新增内容 | 先查哪里 |
|---------|---------|
| 类型定义 | `src/types/`、`client/src/types/` |
| 工具函数 | `src/utils/common.ts`、`client/src/utils/` |
| 错误类 | `src/error/types.ts` 标准错误类列表 |
| 缓存 | `src/utils/cache.ts`（TTLCache / LRUCache / MemoryCache） |
| 重试逻辑 | `src/utils/withRetry.ts` |
| 事件总线 | `src/core/events/EventBus.ts` |
| Logger | `src/monitoring/logs/Logger.ts` |
| 状态机 | `src/core/state/` |
| HTTP 端点 | `.trae/docs/api-spec.md` |
| 模块注册 | `src/modules/ModuleDefinitions.ts` |

**AI 自查问句**：我即将写的这段代码，能不能用已有的代码替代？如果能，为什么我还要写新的？

## CS02 状态检测禁止字符串匹配（MUST）

**状态判断必须基于持久化标记（布尔字段、枚举等），禁止用标题/名称等用户可见字符串做业务逻辑判断。**

### CS02-001 [MUST] 禁止字符串匹配做状态判断

```typescript
// ❌ 禁止：用标题字符串判断会话是否需要重命名
function isDefaultTitle(title: string): boolean {
  return title.startsWith("新会话") || title.startsWith("New Session");
}

// ✅ 正确：用持久化的 metadata 标记
function shouldAutoRename(session: Session): boolean {
  return session.metadata?.titleAutoGenerated === false;
}
```

**为什么禁止**：
- 字符串是用户可见的，随时可能变化（多语言、用户手动修改、产品迭代）
- 字符串匹配无法覆盖所有情况（"会话1234567"、"Untitled"、"New Chat" 等无穷无尽）
- 新字符串需要改代码，是脆弱的紧耦合

**替代方案**：
- 在数据模型中新增 `metadata: { titleAutoGenerated: boolean }` 等标记字段
- 在状态变更时同步更新标记（如 `renameSession` 时设 `titleAutoGenerated = true`）
- 前端通过标记判断，而非字符串匹配

**AI 自查问句**：我写的这个 `if` 条件，是在判断状态还是在判断内容？如果是状态，标记在哪里？

## CS03 回退策略最小化（MUST）

**代码是为正常运行而写的，不是为回退而回退。回退策略只在真正必要且概率可观的场景下存在。**

### CS03-001 [MUST] 回退策略必须有真实场景支撑

允许回退策略的场景（必须同时满足）：
1. 依赖的外部服务确实可能不可用（如网络请求、第三方 API）
2. 回退后的行为对用户有明确价值（降级可用 > 完全不可用）
3. 不可用的概率可观（> 1%），不是理论上的可能性

禁止回退策略的场景：
- 本地文件读写（除非磁盘满，否则不应失败）
- 内部模块调用（调用方和被调用方都是自己的代码）
- 本地数据库操作（SQLite 在本进程内，失败概率极低）
- "以防万一"的兜底（没有具体失败场景的假设）

```typescript
// ❌ 禁止：本地 store 操作不需要 try-catch 回退
async function renameSession(id: string, title: string): Promise<void> {
  try {
    await http.put(`/v1/sessions/${id}`, { title });
  } catch {
    // 回退到本地？为什么 HTTP 会失败？这个 catch 掩盖了真实问题
    localStore.rename(id, title);
  }
}

// ✅ 正确：HTTP 请求可以有 fallback，但应该是真正的降级方案
async function fetchModels(): Promise<Model[]> {
  try {
    return await http.get("/v1/models");
  } catch (error) {
    // 网络确实可能断开，用本地缓存降级
    logger.warn("无法获取最新模型列表，使用本地缓存", { error: String(error) });
    return localCache.getModels();
  }
}
```

### CS03-002 [MUST] 回退策略不能掩盖错误

```typescript
// ❌ 禁止：回退吞掉了所有错误信息，问题永远无法排查
try {
  await doSomething();
} catch {
  // 静默回退，没有任何日志
  await fallback();
}

// ✅ 正确：至少记录错误日志
try {
  await doSomething();
} catch (error) {
  logger.warn("主路径失败，执行回退", { error: String(error) });
  await fallback();
}
```

**AI 自查问句**：这个 catch 块是真的在保护用户体验，还是在掩盖一个我懒得处理的错误？

## CS04 Mock 数据零容忍（MUST）

**生产代码中严禁任何形式的 Mock 数据、假数据、硬编码示例数据。**

### CS04-001 [MUST] 零例外

```typescript
// ❌ 禁止：任何形式的 Mock 数据
const mockUsers = [{ id: 1, name: "张三" }];
const DEFAULT_SESSIONS = [{ id: "demo-1", title: "示例会话" }];
function getSessions(): Session[] {
  return sessions.length > 0 ? sessions : DEFAULT_SESSIONS; // 假的回退
}

// ✅ 正确：空就是空，没有就是没有
function getSessions(): Session[] {
  return sessions;
}
```

**AI 自查问句**：这行代码在用户真正使用时会被执行吗？如果会，它返回的是真实数据还是假数据？

## CS05 根因优先（MUST）

**遇到问题时，先找根因，再写代码。禁止用临时方案掩盖根因。**

### CS05-001 [MUST] 根因分析三步法

```
Step 1: 问题的表现是什么？
  → 会话标题始终显示 "Default Session" → 因为自动重命名没触发

Step 2: 自动重命名为啥没触发？
  → shouldAutoRename() 用 startsWith 匹配标题字符串
  → 但 "Default Session" 不在匹配列表中

Step 3: 根因是什么？
  → 用字符串匹配做状态判断本身就是错误的架构
  → 应该用持久化标记（metadata.titleAutoGenerated）
  → 修复：在数据模型中加标记字段，所有判断基于标记
```

### CS05-002 [MUST] 临时方案必须标注

如果确实需要临时方案（如紧急修复），必须标注：

```typescript
// TODO: CS05-ROOTFIX — 字符串匹配是临时方案，根因方案是 metadata.titleAutoGenerated 标记
// 预计在 v8.0 中完成根因修复
function isDefaultTitle(title: string): boolean { ... }
```

**AI 自查问句**：我是在解决这个问题的根本原因，还是在给问题贴创可贴？

## CS06 证据驱动：禁止空结果编造（MUST）

**工具返回空结果时，禁止编造内容填补空白。空 = 报告"未找到"，不是创作的许可证。**

这与 CS04（Mock 数据零容忍）一脉相承：CS04 禁止在代码中写假数据，CS06 禁止在分析中编造假结果。

### CS06-001 [MUST] 三不原则

| 工具 | 返回空时 | 禁止做 |
|------|---------|--------|
| `Read` | 文件不存在或为空 | 编造该文件的"内容"（如虚构函数签名、类定义） |
| `Glob` | 未匹配到文件 | 虚构"找到的文件列表" |
| `Grep` | 未搜索到匹配 | 编造"匹配的代码行" |
| `LS` | 目录为空或不存在 | 虚构"目录结构" |
| `SearchCodebase` | 无相关结果 | 编造"找到的实现" |

```typescript
// ❌ 禁止：Grep 返回空，但分析输出编造了结果
// AI 输出："搜索到 ChannelFactory 在 core/gateway/channel.py 中，代码如下..."
// 实际：Grep 返回了空，channel.py 根本不存在，是 AI 编造的

// ✅ 正确：空就是空，诚实报告
// AI 输出："Grep 搜索 'ChannelFactory' 在 app/src/ 下未找到匹配。"
//         "是否需要扩大搜索范围，或确认搜索关键词？"
```

### CS06-002 [MUST] 空结果不等于"假设存在"

```
# ❌ 禁止的推理链
工具返回空 → "可能是路径不对" → 用猜测的路径重试
  → 又返回空 → "可能是文件名不同" → 编造一个文件名
  → 返回空 → "可能内容大概是..." → 基于猜测继续分析

# ✅ 正确的推理链
工具返回空 → 报告用户 → 确认路径/文件名 → 重试
  → 仍然空 → 结论："该内容确实不存在于代码库中"
```

**核心原则**：工具是 AI 与现实世界之间的唯一桥梁。桥断了（返回空），AI 不应该画一座假桥。

**AI 自查问句**：我即将输出的这段分析中，有没有任何一句话来自我编造而非工具返回？

## CS07 依赖收敛前先扫全局命名空间裸用法（MUST）—— 删除/去重 `@types/*` 前必须做

**`@types/*` 的嵌套副本会经 type-reference「就近解析」把声明泄漏进全局命名空间。删掉或去重它之前，必须先扫全仓对相应全局命名空间的裸用法，否则会以"清冗余"之名打断编译。**

### CS07-001 [MUST] 三步检查法

```
Step 1: 定位被收敛的类型包，以及它**泄漏进全局的命名空间/全局变量**
  → 例：@types/react@18 声明全局 JSX；@types/node 声明 process / Buffer 等
Step 2: 扫全仓对**裸用法**的引用（不 import、直接使用）
  → Grep "\bJSX\.[A-Za-z]" / "\bBuffer\b" 等；统计文件数与命中点
Step 3: 处置（二选一，禁止"直接删了事"）
  → ① 逐点补齐**具名导入**（React 19 正规写法：`import type { JSX } from "react"`）后再删依赖
  → ② 确认该包确有消费者（如被依赖方的类型声明需要它）则保留，并记录理由
```

```ts
// ❌ 错误：先删依赖 / 先去重（overrides），再看编译报错
//    overrides: { "@types/react": "^19.3.0" }  → 嵌套的 React 18 类型消失
//    → TS2503: Cannot find namespace 'JSX'（5 个文件 / 9 处裸 JSX.X 一起崩）

// ✅ 正确：先补齐具名导入，再删依赖 / 去重
import type { JSX } from "react";   // 显式来源，不再依赖"蹭来的"全局声明
type RenderText = (text: string) => JSX.Element[];
```

**为什么禁止**：
- 全局命名空间是**隐式契约**：源码里看不见来源 ⇒ "编译通过" ≠ "依赖正确"
- 删除者看到的是"这个包没人引用"，看不到它在**别的包的类型声明里**被就近解析后注入的全局声明
- 报错出现在**与改动无关的文件**（本例 5 个 ChatArea 组件），会把排查方向带偏

**真实案例（2026-09-15）**：`@types/react-window@1.8.8` 自身的 `import … from "react"` 按就近解析命中其嵌套的 `@types/react@18.3.28`（React 18 声明全局 `JSX`）⇒ 全仓 5 文件 / 9 处裸 `JSX.X` 静默依赖这份"蹭来的"全局；`overrides` 去重后立即全数报 `TS2503`，补齐具名导入并删除该包后恢复绿。详见 `dev_docs/error_repairs/预存错误与待处理问题.md`（V-42 附注·依赖收敛段）。

**AI 自查问句**：我准备删除/去重的这个类型包，是否可能正在为**别的文件的全局命名空间**供血？我扫过裸用法了吗？
