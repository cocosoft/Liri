# 任务执行行为规则

> 解决"做到一半不说话"、"做完不汇报"、"输出分析文字但不落地"三类问题。
> 这些规则是 PY_APP.md §4（目标驱动执行）的强化，聚焦于工具调用与用户可见输出之间的节奏控制。

---

## TE01 工具调用上限（MUST）

**单次回复的并行/串行工具调用合计不超过 5 次。**

超过 5 次时，必须拆分为多轮回复，并在每轮之间输出文字说明进度：

```
"正在读取第 1 批文件（共 3 个）..."
"继续读取第 2 批（共 3 个）..."
"全部读完，开始分析。"
```

禁止的模式：
```
# ❌ 一条回复塞入 10+ 个 Read/Grep，然后沉默 60 秒
同时调用：Read × 8, Grep × 5
```

---

## TE02 静默超时主动报告（MUST）

**上一轮工具调用无用户可见输出后，本轮回复必须先报告进度。**

```
# ✅ 强制开场白
"上一轮读了 X 个文件，现在分析完毕，结论：..."

# ✅ 或简洁进度说明
"[2/3] 已检查 A 和 B，正在读 C..."
```

---

## TE03 执行粒度拆分（SHOULD）

**禁止"大量工具调用 → 沉默思考 → 一次输出"的模式。**

| 旧模式（黑盒） | 新模式（可见） |
|--------------|-------------|
| Read×8 → think 60s → 输出 | Read×3 → "已读3个" → Read×3 → "再读3个" → Read×2 → "读完，分析如下" → 输出 |
| 工具全在一轮 | 每 ≤5 次拆一轮，轮间夹文字 |

---

## TE04 自检清单（MUST — 仅交付前触发）

**仅在任务交付前跑清单，不在每步都跑。**

| 时机 | 是否触发 |
|------|:---:|
| 第一次回复（出计划） | ❌ |
| 中间执行步骤 | ❌ |
| 任务最终交付前 | ✅ |

清单内容：

```
☐ TodoWrite 与实际进度一致？（in_progress = 正在做，completed = 已落地）
☐ 写文件任务：file_write/edit 已全部完成？
☐ 运行命令任务：RunCommand 已执行且检查过退出码？
☐ 所有子步骤是否已处理？（对照用户原始指令逐条核查）
☐ 有需要用户确认的事项？（如有，明确标注）
☐ 以上全部 ☑ → 输出完成总结
```

---

## TE05 分析/执行区分（MUST — 仅复杂任务）

**仅当回复涉及工具调用时，标注当前状态。**

简单对话（无工具调用）不标注，避免噪音。

```
[分析中]  仅输出分析文字 → 结尾标注 "⚠ 以上为分析建议，是否开始执行？"
[执行中]  部分工具已落地 → 结尾报进度
[已完成]  全部工具落地   → 输出 TE06 完成总结
```

---

## TE06 完成总结模板（MUST）

**每次任务全部完成后，必须输出结构化总结：**

```
| 属性 | 内容 |
|------|------|
| 变更文件 | X 个（file1 / file2） |
| 仅读未改 | X 个（file3 — 原因） |
| 新建文件 | X 个（file4） |
| 待确认 | Z 项（xxx 需用户决定） |
| 提醒 | 注意事项 |

核心变更：
- 文件 A: 修改了 XXX（原因：YYY）
- 文件 B: 新增了 ZZZ
```

## TE08 工具结果完整性校验（MUST）

**工具调用返回空结果时，禁止编造内容。空 = 报告失败，不是创作的许可证。**

### TE08-001 [MUST] 读取类工具返回空时必须报告

```
Read 返回空  → 说 "文件不存在或为空：[路径]"，不要编造文件内容
Glob 返回 [] → 说 "未找到匹配 [pattern] 的文件"，不要虚构文件列表
Grep 返回空 → 说 "未搜索到 [pattern]"，不要编造匹配行
LS 返回 []   → 说 "目录为空或不存在：[路径]"，不要虚构目录结构
```

禁止的模式：
```
# ❌ Glob 返回 []，但 AI 输出：
"找到了 channels/ 目录，包含 wechat.py, dingtalk.py..."

# ❌ Read 返回空，但 AI 输出：
"ChannelFactory 类管理渠道实例，代码如下：..."

# ✅ Glob 返回 []，AI 正确输出：
"Glob 搜索 'channels/*' 返回空，该路径下没有匹配文件。当前工作目录是 X，是否需要调整搜索路径？"
```

### TE08-002 [MUST] 工具返回错误必须停止当前链路

如果工具返回了错误（非预期错误码、权限拒绝等），必须：
1. 停止当前分析/执行链路
2. 向用户报告具体错误
3. 提出替代方案或请求用户确认

禁止忽略错误继续执行，禁止用"可能"、"假设"开头的推测替代错误报告。

### TE08-003 [MUST] 写入类工具必须验证写入结果

```
Write/Edit 之后 → 立即 Read 该文件关键行验证内容已落盘
RunCommand  之后 → 检查 exit code，exit code ≠ 0 时报告失败
```

**AI 自查问句**：我刚读到的这个工具结果，是真实返回的数据，还是我推测/编造的内容？

## TE09 路径解析收敛协议（MUST）

**文件路径解析失败时，必须在 2 次尝试内收敛。禁止无限循环猜测路径。**

### TE09-001 [MUST] 三步收敛法

```
Step 1: 检查环境变量中的工作目录
  → 查看 system-reminder 中的 Primary working directory
  → 查看 project_memory.md 中的正确路径记录

Step 2: 单次重试
  → 如果 Step 1 的路径失败，检查 project_memory.md 的已知错误路径
  → 用正确路径重试一次

Step 3: 上报用户
  → 两次都失败 → 停止猜测
  → 向用户报告："尝试了路径 A 和 B 均失败，请确认正确路径"
  → 附带 project_memory.md 中已知的正确路径供用户参考
```

禁止的模式：
```
# ❌ 连续尝试 7 个不同盘符/路径
C:\...\PY_APP → 空 → D:\...\PY_APP → 空 → E:\ → 空
→ C:\Users\...\worktrees\PY_APP → 空 → E:\PY\ → ...
# 这是路径赌博，不是路径解析
```

### TE09-002 [MUST] 发现正确路径后立即更新 project_memory.md

当通过用户告知或其他方式确认了正确路径后，必须立即更新 `project_memory.md` 的 Lessons Learned 部分，记录：
- 正确路径
- 已知的混淆路径（如残留的 `worktrees\PY_APP` 目录）

**AI 自查问句**：我是不是在同一个错误上试了两次以上？如果是，该问用户了。

## TE10 中断后上下文恢复（MUST）

**Socket 断开、超时、空响应等中断发生后，必须先恢复上下文再继续。**

### TE10-001 [MUST] 上下文恢复三步法

```
Step 1: 读取 project_memory.md
  → 获取项目根路径、技术栈、已知约束

Step 2: 报告中断状态
  → "[恢复中] 上一轮在 [具体步骤] 被中断，正在恢复上下文..."
  → 给用户明确的进度信号，不自顾自地重新开始

Step 3: 重读最后操作的文件
  → 根据 summary 中的 Recent file 列表，重新 Read 最后一个被操作的文件
  → 确认文件当前状态后再继续
```

禁止的模式：
```
# ❌ 中断后静默重启，假装什么都没发生
# ❌ 不读 project_memory，从错误的路径重新开始探索
# ❌ 不告诉用户发生了什么，用户看到的是重复的劳动
```

### TE10-002 [MUST] 中断前后衔接检查

中断恢复后，执行第一轮工具调用前，必须检查：
- TodoWrite 列表是否仍然准确？（可能有已完成但未标记的任务）
- 最后一个操作的文件状态是否与预期一致？
- Summary 中的 Pending Tasks 是否仍然相关？

**AI 自查问句**：用户给我的 summary 里说了什么？我是不是在重复已经做过的事？
