## 1. 问题（为什么必须换来源）

O1 = A7 的"本仓纯函数派生"题源。流水线本身可用（13 条规格、干跑 13/13 `ready`、防泄题路径屏蔽已落地），
但**实测结论是负面的、且可证伪**：

| 批次 | 条数 | answered 口径实测（`deepseek-v4-flash`，k=4） |
|---|---|---|
| 第二批 | 10 | **8 条 answered 100%**；仅 `strip-bare-exploration`（answered 2 中过 1）与 `compute-unified-diff`（answered 4 中过 1，规格其后又修过 ⇒ 数值待复测）有区分度 |
| 第三批（按"逻辑复杂"新选） | 3 | **3 条全部 answered 100%** |

⇒ **结论**：靠"在本仓纯函数里换更难的题"**提高不了区分度**。资格线（零依赖 / 参数与返回值可 JSON 化 /
输入小 / 行为能用散文无歧义写清）本身把题目限制成"照着规格实现一个小纯函数"，**恰是当前模型最稳的区间**
（完整推导见 [`tasks/source-derived.ts`](../../app/src/evals/tasks/source-derived.ts) 头注释"第三批实测"）。

⇒ 另一处缺口：**A2 的三个行为指标已实现但不参与判定** ⇒ 现有题目对"过程"完全不区分，而过程恰是
Agent 的关键面（合规、自验证、探索收敛）。

## 2. 目标与验收（可证伪）

- **G1（主目标）**：新增来源中**至少 3 条**在 `deepseek-v4-flash`、k=4 实测下 answered 口径
  `pass^1 ∈ (0, 1)`（真有区分度），且样本内**结论稳定**（不因单次波动翻转）。
  **✅ 口径已裁定（2026-09-26，用户选"选项 A"）**：把 `pass^1 = 0%` 的"**地板型**"（模型恒做不到，
  失败均为**真红断言**）**计入**"有区分度"—— 理由是它对信号基线有价值（任何改进都会 0 → 正）。
  ⇒ **判定：G1 达成**（`fix-7035f271` 50% + `fix-50576842` 0% + `fix-4fc17ee1` 0% = **3 条**）；
  **G3 止损未触发**（本来源并非全零区分度）。地板登记见 `baseline.json`。

- **G3（止损条款，防"再换几条续命"）**：若某来源经**一次 10 题选材 + k=4 实测**仍证零区分度
  ⇒ **如实登记为不可用并停止投入**，不得靠继续换题掩盖。

## 4. 设计要点

### 4.1 S1 的防泄题（**本项目核心风险，必须先做变异验证**）

起点快照里**不得存在任何形式的答案**。与 A7 的"运行期屏蔽路径"不同，S1 要求**从构造期消除**（CS05）：

1. **快照用 `git archive <commit>` 导出**（不是 `git worktree` / `clone`）⇒ 天然**不含 `.git`**。
   否则 `git log` / `git show` / `git diff` 会把修复 diff 直接交给模型。
2. **覆盖测试文件**（判据）到快照：测试是"判据"不是"答案"（SWE-bench 同做法）。
3. 复用既有 `scanSourceLeaks()` 扫 `dist/` / `node_modules/` 下的同名副本（可能是**修复后**版本）。
4. **远程拉取面（未验，T2 必须实测）**：若沙箱内可访问公网且远端仓库公开，模型可 `curl` / `git clone`
   取到修复 ⇒ 需确认 B2 的网络策略（`DockerNetworkPolicy` 声明层）在评测沙箱里的**实际生效**情况；
   若不成立 ⇒ 必须显式限制。
5. **变异验证（验收条件）**：先在**未净化**快照（含 `.git`）上证明"能读到答案"，再在净化后证明
   "读不到" ⇒ 证明屏蔽的**必要性**与有效性（可证伪）。**不做这一步不得进入 T3**。

### 4.2 S1 的选材口径（机械筛 + 人工确认）

- 机械筛：`fix:` / 修复类 subject；`git show --stat` 显示**源码 ≥1 且测试 ≥1**（或目标模块有既有测试可复用）；
  单 commit 改动量落在可用区间。
- 人工确认：修复语义**可由测试判定**（非纯文案/配置改动）；快照体积可控；**起点态必失败**（跑测试应为红）。
- **不得凭空断言"有多少条可用"** ⇒ T1 产出**候选表**（触及文件数 / 是否带测试 / 体积 / 起始态红绿实测）
  作为证据（CS06）。

**T1 实测产出（2026-09-26，真实仓库，零模型）**：全量 **1314** commit ⇒ 机械筛 **45 条** ⇒ 前 35 条**双实测**
⇒ **11 条准入**（例：`254b4776` 起点 `tests=2 failures=2`；`04a0102e` 起点 `tests=4 failures=2`；
`4fc17ee1` 起点 `tests=31 failures=1`；`7035f271` 起点 `tests=18 failures=3` —— 全部「起点红 ⇒ 修复绿」）。

❗**拒绝成因分布（比通过数更重要）**：**多数因"起点 `unrunnable`"被拒**，两种成因均**实测**：
① **父提交树本身不可解析**（`b009711e^` 的 `AgentTool.ts` 静态 import 了当时**尚未入库**的 `SettlementOutbox.ts`）；
② **该提交新增的测试 import 了"修复后才存在"的导出** ⇒ 起点一加载就失败。
⇒ **"起点必须能跑到断言"是 S1 的硬门槛**；它筛掉的不是"难题"，而是"起点根本跑不起来"的提交。
另有少数 **起点 `green`**（该测试在修复前已通过 ⇒ 判据不指向这次修复）⇒ 零区分度，正确拒绝。
⇒ 故 **S1 可直接用率约 30%**（35 条里 11 条）—— 选材**必须按双实测筛**，不能按 commit 元数据判断。

### 4.3 S1 的判据与隔离

- 判据：新增"运行外部命令"类断言（**L1 环境终态**的推广）——真实执行该仓测试命令，读**真实退出码**
  （沿用 B4 教训：**不用异常推断**成功/失败）。
- 隔离：每任务一份独立快照（沿用 A3-b 的**任务级隔离**思路），跑完即删；快照落 `resolveTempDir()`
  （❌ `process.cwd()` 拼路径）。
- **fail-closed**：快照或测试命令缺失 ⇒ **拒跑**（不静默降级为"共享仓库"）。
- ⚠️ **等待上限必须 ≥ S1 的合法耗时（2026-09-26 实测教训）**：用 `--task-timeout-ms=120000` 跑
  1 条 × k=4 时，**6/6 请求全在 120s 被中止**（`执行异常：超时`）—— 全是**基建噪声**，不产出任何能力结论。
  S1 任务（读判据测试 → 读源码 → 改 → 自验）**远重于** A7 的纯函数（后者实测最长**合法**尝试 62.4s）
  ⇒ S1 的等待上限应按**分钟级**设（建议 ≥300s），并在报告中**显式标注所用上限**。
- **判据不可篡改**：`assert` 跑测试前**重放**该提交的测试文件（覆盖被测者对测试的任何改动）——
  与 SWE-bench 同做法（测试是判据，不是解题材料）。已由合成仓库用例验证（把测试改成"恒通过"仍判失败）。

### 4.4 S2 的过程断言

- 新增面：`EvalTask.assertProcess?`，判据**只读已落盘的 `toolCallsDetail`**（A1 已实现逐值截断）
  ⇒ 可**离线重算**。
- 候选谓词（每条都必须有"离线 A/B"：构造合规 / 违规 trace 各一）：
  - P-a 交付前自验证（写完后至少一次读回或执行验证）；
  - P-b 同一资源重复读 ≤N（对应 `ReActToolLoop` steering 的观测物）；
  - P-c 未尝试访问被屏蔽路径（**当前观测恒真**：10/10 运行模型都不去翻仓库 ⇒ 若无区分度，
    须**如实登记为"当前模型不做弊"**）；
  - P-d 首轮先观察后动手。
- 取向与 A2 / A5 一致：**默认只观测、不进退出码**；门禁化留待实测有区分度后再议。

### 4.5 T2 机制探针实测（2026-09-26 已完成；暴露 3 项必须处置的约束）

用 `b009711e`（`fix(tools): 代码执行器改用进程组终止，消除孙进程残留` —— **M 1 源码 + A 1 测试**）做机制验证：

| 项 | 实测结果 | 结论 / 处置 |
|---|---|---|
| 快照无 `.git` | `git archive <sha>^ app/src app/tests app/package.json app/tsconfig.json` ⇒ 4262 文件 / **26.9 MB**，`Test-Path .git` = **False** | ✅ 构造期消除 `.git` **成立** |
| 中文路径 | 全量导 `app` 时 `tar.exe` 在 `app/docs/工具参考/**` 等中文目录上**报错**（`Invalid empty pathname`），文件静默缺失 | 快照**只取 ASCII 子树**（`app/src` / `app/tests` / 配置），并把"文件数"纳入自检 |
| 依赖供给 | 用 junction 指向真实 `app/node_modules` 后测试**能起**（bun 解析成功） | 可用，但有**平台差异**（见下） |
| **起始态跑测试** | 退出码 1（"红"），但**原因是 `Cannot find module '../../chat/yield/SettlementOutbox'`** | ❗**红因必须 = 断言失败**；否则会把"快照不可运行"误判成"起始态必失败 ✓"（与 A7 的桩缺陷**同型**） |

**❗根因（已定位，可复核）**：`b009711e^` 树内的 `app/src/tools/AgentTool/AgentTool.ts` **静态 import**
`../../chat/yield/SettlementOutbox`，而该文件**只在其后 1 秒的 `c1b95909` 才被加入版本库**
（`git log --diff-filter=A` 仅此一条；两 commit 时间戳 20:37:36 / 20:37:37）⇒ **该 commit 的树本身不可解析**
（当时该文件属"未入库文件"）。本仓工作区**长期存在未入库文件**（本轮新增的 `evals/*.ts` 亦全为 `??`）。
⇒ **处置（T2 待落）**：S1 快照必须过 **"可运行性自检"（fail-closed）** —— ① 起始态的红必须是**断言失败**，
② 修复态必须**绿**；**不得**只看"退出码非 0"。区分"断言失败"与"加载/解析错误"应优先用**机器可读**结果
（如 `bun test` 的 JUnit/JSON 报告；**具体支持情况待实测**），而非匹配日志文案（CS02）。

**链接方式的平台差异（更正我先前的假设）**：实测本机（Windows）`fs.realpathSync('<snap>/app/node_modules/../src/…')`
**仍解析到快照内路径**（先做词法 `..`）⇒ junction **未**造成越界，我先前"junction ⇒ 必然越界"的判断**不成立**。
但**POSIX 语义下 `..` 会穿出符号链接**（业界已知语义；本机为 Windows，**无法在此实测**）⇒ 若评测在 Linux/容器内
运行，**禁止**用 symlink/junction 供给依赖，应改为**物理拷贝**，或"快照置于仓内 + 整仓屏蔽 + 快照白名单"
（后者需给 `pathShield` 增加**例外**能力，属新增能力，**未做**）。
**✅ 已落地（2026-09-26）：POSIX ⇒ 物理拷贝**（`supplyDeps` 的 `copy` 分支 + 体积闸 `POSIX_DEPS_MAX_COPY_BYTES` 默认 1 GiB，超限 **fail-closed 拒绝**并把出路写进原因）；`removeRepoSapshot` 已**区分两种供给方式**（链接 ⇒ `rmdirSync` **不跟随**；真目录 ⇒ 递归删）。
⚠️ 该修正是**由新用例实测抓出**的：对**拷贝目录**用 `rmdirSync` 会报 `ENOTEMPTY`（原实现只考虑 junction）。"仓内快照 + 白名单例外"仍未做（现有方案已够）。

**三项处置已落地（2026-09-26，零模型）**：

| 处置 | 交付物 |
|---|---|
| ASCII 子树快照 + 完整性自检 | `evals/repoSnapshot.ts`：`existingTreePaths()`（路径存在性按**被导出的父提交**判定 —— fix 提交新增的目录在父提交里可能不存在，按 fix 判会让 `git archive` **整体失败**，合成仓库测试实测到该缺陷）/ `createRepoSapshot()` / `overlayFromCommit()`（**只覆盖测试=判据**，源码修复不覆盖）/ `countFiles()` 完整性自检 |
| fail-closed 可运行性自检 | `evals/repoTestJudge.ts`：`parseJunitSummary()` + `classifyRepoTestRun()`（三态 `green` / `red` / **`unrunnable`**）+ `judgeS1Eligibility()`（起始态必须**真红**、修复态必须**绿**）+ `runRepoTest()`（真实子进程 + **JUnit 机器可读报告**，不做文案匹配） |
| 依赖供给平台分流 | `supplyDeps()`：win32 ⇒ junction；**其它平台 fail-closed 拒绝**（理由写入返回值，不静默降级）；`removeRepoSapshot()` 用 `rmdirSync` 删链接 —— 实测 `rmSync(recursive:false)` 对 junction 报 **EFAULT**，而 `recursive:true` 有**递归进目标**的风险 |

**验证（可证伪，全部零模型）**：新增 `tests/evals/repoPatchSnapshot.test.ts` **6 例**（合成 git 仓库，真跑 git/tar/bun）：
① 闭环：起始态 `red`（JUnit `failures=1`）→ 写入修复 ⇒ `green` → 准入通过，且快照 `hasGitDir=false`；
② **未净化对照**：含 `.git` 的树 `git show` **可直读答案**（证明净化的必要性）；
③ **fail-closed**：起始态因缺模块跑不起来 ⇒ `unrunnable` ⇒ **拒绝准入**；
④ 判据边界（无报告 / 零用例 / 非零退出但无断言失败一律 `unrunnable`）；⑤ 起始态 `green` 必须拒；
⑥ 依赖供给平台分流 + 删除**不跟随**链接。
**A/B（变异）**：把 `classifyRepoTestRun` 改成"无报告即 `red`"（只看退出码的朴素写法）⇒ **恰 2 红**（③④），其余 4 绿；还原 ⇒ 6/6 绿。另：`rmSync → rmdirSync` 的修复由用例 ⑥ **先红后绿**验证。
