### 1.2 裁定

**触发条件**：① 出现**实际案例**——手工/外部 API 写入产生端点不符脏边且影响查询结果；② 或 OTel 指标在部署环境不可达（无 collector）而需日志/接口侧替代。

## 2. P2-6 · D4 存量边处置（"人工挑选"是否执行？）

### 2.1 取证

| 事实 | 证据 |
|---|---|
| 决策记录为「**人工挑选**」 | `知识图谱可维护性设计方案.md` §（决策表）：`D4 存量边处置 = 人工挑选（回滚手段已就位，可执行）`（2026-09-11 用户拍板） |
| **但同文档 §3.5.1 已证否该路径** | 「**"逐条人工挑选"不可行**：988 个类型、3042 条边，逐条点击的收益极低（**60% 的类型只有 1 条边**）」 |
| §3.5.2 给出的**实际路径** | ① **默认保留**存量边（不自动删除任何数据）；② 建议在「本体」页提供**类型处置面板**（白名单外类型按条数降序，三动作：加入白名单 / 删除该类全部边 / 保持不变）；③ 批量删除须二次确认 + 走 `kg_edge_audit` + 提示先整库导出 |
| 存量数据实测特征 | **3026/3042 条边的端点 ID 冒号数为 0**（裸 slug，早于 `{domain}:{kind}:{slug}` 约定）⇒ **端点约束对存量数据不生效**（D7 语义：只告警不删除） |
| 「类型处置面板」**未实现** | `client/src` 内**无**本体/类型处置面板（grep 命中仅 `CustomRulesPanel` 等无关组件） |

### 2.2 裁定

**✅ 维持「默认保留」；「类型处置面板」不立项。**
理由：① D4 的实际落地即 §3.5.2 第 1 条「默认保留」——**零删除、零风险**，已满足"存量不丢数据"的底线；② 决策表所写的「人工挑选」**被同一文档证明不可行**（988 类型/3042 边），属**未采纳路径**，**非"未执行"的欠账**；③ 「类型处置面板」是**产品功能**（需 UI + 白名单语义 + 审计联动），收益未证（CS03）。
**触发条件**：用户/产品提出「**按类型/白名单处置存量边**」的明确诉求（届时按 §3.5.2 的 2–3 步实施，并强制"二次确认 + 审计 + 先导出"）。

### 3.2 裁定
