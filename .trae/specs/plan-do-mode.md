# Spec：Plan/Do 工作模式（V-18 ⑤）根因修复设计

> 状态：**设计待评审**（本文件只定义契约与步骤，不含实现）
> 触发：`dev_docs/error_repairs/预存错误与待处理问题.md` → V-18 ⑤（`activeWorkItem` 恒空 → plan/do 从未到达后端）
> 关联：V-18 ②（UI 状态分层结论）、§1.6.1 接口清单（api-spec.md）、V-17（门禁协同）

## 0. 结论速览

V-18 ⑤ 的表层现象是"`activeWorkItem` 恒空 ⇒ `resolveWorkMode()` 恒返回 `undefined`"。取证后**根因有三条，且都不是"缺入口"这么简单**：

| # | 根因 | 性质 |
|---|------|------|
| R1 | **两个工作项模型互不认识**：`mode` 存在 `workStore`，工作项存在 `root-store.worktrees[*].workItems`；`resolveWorkMode()` 读的是前者中一个**永远为 null** 的字段 | 模型分裂 |
| R2 | **后端不读 `work_mode`**：客户端全链路会发 `body.work_mode`，但后端 `app/src` 内**零读取点** ⇒ 该参数是**空投**（发了也不产生语义） | 契约空转 |
| R3 | **层级错配**：后端把 mode 存在**会话 metadata**（`workMode`）中，前端却存成**全局内存态**（不分会话/工作空间、不持久化、不同步） | 归属层级不一致 |

**推荐方向（方案 A）**：**mode 归属"会话"，事实来源在后端**（沿用已有 `metadata.workMode`）；前端删除 `workStore.mode` 的独立事实权，改为当前会话的投影；同时**要么让后端真正消费 `work_mode`，要么前端停止发送**（二选一，禁止继续空投）。

### 1.3 一句话现状

**两端各自建了大半条链路，却在中间断成两截**：后端把 mode 放在"会话"，前端把 mode 放在"全局内存"；发送侧用 `activeWorkItem` 当作开关，而真正的工作项活在另一个 store 里。

## 2. 根因（对应 §0 的 R1–R3）

```
聊天请求 → resolveWorkMode() → workStore.activeWorkItem（永远 null）✗
                                     ↑
                          真正的工作项在 root-store.worktrees[*].workItems（有后端同步）
                                     ↓
                            body.work_mode ──→ 后端：无读取点 ✗（空投）
```

- **R1 模型分裂**：同一个业务概念（"当前工作项"）在 `workStore` 与 `root-store` 各有一份，且字段名不同（`activeWorkItem` vs `workItems`）。
- **R2 契约空转**：`work_mode` 是"发送即遗忘"的参数——比"没实现"更糟，因为它让代码**看起来**已经支持。
- **R3 层级错配**：mode 的天然宿主是**会话**（后端已如此），前端却按"应用全局状态"建模。

## 3. 设计目标与不变量

| 目标 | 说明 |
|------|------|
| G1 单一事实来源 | mode 的权威值只能有一处，且**跨刷新/跨进程可复现**（§1.5 数出同源） |
| G2 无空投 | 前端发往后台的每个字段，后台必须有读取点；否则不发 |
| G3 层级自洽 | mode 的宿主层级 = 其语义作用域（会话？工作项？工作空间？见 §4 需决策） |
| G4 出口可达 | 用户能从界面**改变** mode（当前 `toggleMode` 无调用方） |
| **I1** | 任一时刻"当前会话的 mode"可被唯一确定（不允许"前端说 plan、后端存 do"） |
| **I2** | `mode` 只影响它应当影响的层（不得绕过权限/门禁；与 V-17 正交） |

## 4. 方案对比（含需产品决策的分歧点）

### 方案 A：mode 归属**会话**，后端为事实来源（**推荐**）

- 前端在会话加载/切换时，从会话数据读出 `metadata.workMode` → 作为唯一 mode 视图；删除 `workStore.mode` 的独立事实权
- 发送 `work_mode` 时取"当前会话的 mode"（不再依赖 `activeWorkItem`）
- 后端**必须**为 `work_mode` 定义语义（见 §5.3），否则退化为方案 C
- **优点**：与后端既有设计一致；mode 天然随会话持久化/可复盘；改动集中
- **代价**：需要后端配合（不能只改前端）

### 方案 B：mode 归属**工作项**

- 把 mode 作为 work item 的属性（"这个工作项处于 plan 还是 do 阶段"），进入工作项即进入对应模式
- **优点**：与 `WorkItem.status`（pending/running/…）语义邻近；"进入工作模式"入口天然绑定工作项
- **代价**：需要新增 work item 字段 + 迁移；会话与工作项多对一，"当前 mode"在无工作项时无定义

### 方案 C：**收敛删除**（若判定无真实需求）

- 删除 `workStore.mode`/`toggleMode`/`activeWorkItem`/`setActiveWorkItem`、前端停止发送 `work_mode`、`DeliverableCard` 的"进入工作模式"按钮一并移除（或明确标注未实现）
- **优点**：立即消除"看起来支持其实不支持"的假象（符合 CS04/§2 简洁优先）
- **代价**：丢弃 plan/do 产品意图（需产品明确否决）

### 需产品决策（本 Spec 不能替你决定）

| # | 问题 | 选项 |
|---|------|------|
| Q1 | mode 的宿主层级 | A 会话 / B 工作项 / C 删除 |
| Q2 | `work_mode` 在后端的**语义**是什么？ | ① 注入不同系统提示词（plan：只产出计划；do：允执行）② 门禁（plan 模式禁用写类工具）③ 仅记录/遥测（不改变行为） |
| Q3 | "进入工作模式"入口是否要保留 | 保留（接上 `DeliverableCard.onEnterWorkMode` → 建/绑工作项 + 建 workspace 会话 + 跳转）／移除 |
| Q4 | 工作项创建入口 | 由交付物卡片自动创建 / 工作区页显式"新建工作项" / 两者都要 |

> **推荐组合**：Q1=A、Q2=①（提示词差异，风险最低且可回滚；②门禁与 V-17 纠缠，建议二期）、Q3=保留、Q4=先做"工作区页显式新建"（可验证、无隐式副作用）。

## 5. 推荐方案（A + Q2① + Q3保留 + Q4 显式入口）的契约设计

### 5.1 类型与不变量

```ts
/** 工作模式（沿用后端既有取值，勿改名） */
export type WorkMode = "plan" | "do";

/** 事实来源：会话 metadata.workMode（后端持久化） */
// SessionRecord.metadata.workMode?: WorkMode
```

- **I1**：`resolveWorkMode()` 从"当前会话"派生；**缺省 = `plan`**（2026-09-14 用户决定：只要两态、聊天默认 plan）——无会话/未设置一律回落 `plan`，故请求体**始终携带** `work_mode`
- **I2**：前端**不得**再持有独立的 mode 事实（`workStore.mode` 删除或降级为纯派生视图）
- **I3**：切换 mode 的唯一 UI 入口 = **输入区两态开关**（emoji 按钮之后，单击切换，无文字确认）；写入唯一入口 = `PATCH /v1/sessions/{id}/meta { work_mode }`

### 5.2 数据流（目标态）

```
用户在输入区切换 mode（WorkModeToggle，单击 → plan ⇄ do）
  → PATCH /v1/sessions/{id}/meta { work_mode }（后端为事实来源；非法值 400）
  → 后端广播 session:meta_updated → 前端 loadSessions 回填（跨页面/多端一致）
  → 聊天发送时 body.work_mode = 当前会话 mode（未设置 → plan）
  → 后端按 §5.3 语义消费
```

### 5.3 后端语义（Q2① 的最小实现）

- 读 `body.work_mode`；`plan` → 使用"规划"系统提示段（要求先出计划、不得直接产出最终交付物）；`do` → 现行为
- **必须 fail loud**：取值非 `plan|do` → 按 §1.9 抛 `AppError`（不得静默忽略；当前"无读取点"正是静默的极端形式）
- 与 V-17（门禁）**正交**：本模式不新增权限旁路

### 5.4 `workStore` 的收敛

| 字段/动作 | 处置 |
|---|---|
| `mode` / `toggleMode` | **删除**（交由会话 metadata） |
| `activeWorkItem` / `setActiveWorkItem` | **删除**（与 `root-store.worktrees[*].workItems` 重复，保留后者） |
| `contentView` / `workTabs` | 保留（工作区内部态，见 V-18 ③） |

### 5.5 入口（Q3/Q4）

- `DeliverableCard.onEnterWorkMode`：接上 → 创建/绑定工作项（`root-store.createWorkItem`）→ 创建 workspace 会话（`workspaceService.createSession`，`mode: "do"`）→ 跳转 `/work`
- 工作区页：显式"新建工作项"入口（调用同一 `createWorkItem`）
- i18n：启用既有 `workspace.planDoToggle/plan/do`

## 7. 验收标准

1. 打开一个**带 mode 的会话** → 发消息 → 请求体含 `body.work_mode`，且值与后端会话 metadata 一致 —— ✅ **浏览器实测通过（2026-09-14，见下方实测记录）**
