# 会话消息割裂问题排查报告

> 排查日期:2026-06-01
> 排查范围:前后端全链路(app/ + client/)

---

## 问题描述

切换会话后,AI 回复消息(尤其是含工具调用的消息)的 blocks 结构与消息内容割裂:
- 工具调用信息没有与其关联的 AI 回复在同一个气泡中显示
- 未达到"新建时自动显示、再次查看时自动折叠"的预期效果
- 切换会话后,后端保存的 blocks 结构无法正确恢复

---

## 根因分析

### 根因 1:blocks 保存与读取的路径不一致(核心问题)

**后端存储路径** (`ChatManagerImpl._loadSessionsFromGateway`):
- 从 `SessionGateway` 加载消息时,将 `m.blocks` 映射到了 `Message.blocks`(第 768 行)
- 但 `getSessionMessages()` 通过 `this.sessionManager.getSession(sessionId)` 获取的是**内存缓存**,不是从 `SessionGateway` 重新加载

**前端读取路径** (`sessionService.getMessages`):
- 通过 HTTP GET `/v1/sessions/${sessionId}/messages` 调用
- 后端 `CoreAPIImpl.getSessionMessages()` 从 `this.sessionManager.getSession(sessionId)` 读取
- 这里读取的是 `ChatManagerImpl` 的内存 `_chatSessions`,**不是持久化存储**

**关键问题**:`ChatManagerImpl` 启动时 `_loadSessionsFromGateway()` 从持久化存储加载了消息(含 blocks),但后续 `ChatManagerImpl.sendMessage()` / `streamMessage()` 产生的消息**只存在于内存** `_chatSessions`。当通过 API 读取消息时,如果该会话还没有被 `_loadSessionsFromGateway` 加载过(例如跨进程),blocks 就会丢失。

### 根因 2:blocks 保存时机过晚

`chatStore.ts` 中 blocks 的保存发生在**流结束后**:

```typescript
// chatStore.ts 第 160-172 行
// 流结束后才保存 blocks
if (sessionId && finalBlocks.length > 0) {
  await chatService.updateMessageBlocks(sessionId, assistantId, finalBlocks);
}
```

但在此之前,如果用户**立即切换会话**(在流结束后、API 保存完成前),blocks 就会丢失。

### 根因 :getSessionMessages 返回的数据缺少 blocks 字段

`CoreAPIImpl.getSessionMessages()` 中:

```typescript
// CoreAPIImpl.ts 第 243-244 行
return (session.messages || []).map((msg) => {
  // ...
  return {
    id: msg.id,
    role: msg.role.toLowerCase(),
    content,
    timestamp: ...,
    tool_calls: ...,
    toolCallId: ...,
    blocks: msg.blocks,  // ← 这行存在,但 msg.blocks 来自内存
  };
});
```

问题在于 `session.messages` 来自 `ManagerImpl` 的 `_chatSessions` 内存缓存。如果:
1. 应用重启
2. 或 `_loadSessionsFromGateway` 尚未执行完毕
3. 或该会话在内存中被清除

则 blocks 字段不存在。

### 根因 4:前端 setMessages 重建 blocks 的逻辑不完整

`chatStore.setMessages()` 中重建 blocks 的逻辑:

```typescript
// chatStore.ts setMessages()
if (msg.blocks && msg.blocks.length > 0) {
  return { ...msg, blocks: msg.blocks.map((b) => ({ ...b, isStreaming: false })) };
}

// 否则自动重建 blocks
const newBlocks: MessageBlock[] = [];
if (msg.content) {
  newBlocks.push({ id: generateBlockId(), type: 'text', content: msg.content, isStreaming false });
}
if (msg.tool_calls && msg.tool_calls.length > ) {
  msg.tool_calls.forEach((tc) => {
    newBlocks.push({ id: generateBlockId(), type: 'tool_call', content: '', toolCall: tc, isStreaming: false });
  });
}
```

这里**只重建了 text 和 tool_call 两种 block 类型**,缺少 `thinking` 和 `status` 类型的重建。

### 根因 5:后端 toSessionMsgType 导致工具消息分类错误

`ChatManagerImpl.toSessionMsgType()` 中:

```typescript
if (message.role === MessageRole.ASSISTANT && message.tool_calls?.length)
  return SessionMessageType.TOOL_USE;
```

这导致包含 `tool_calls` 的 assistant 消息被标记为 `TOOL_USE` 类型。当从持久化存储读取时,类型转换不一致可能导致 blocks 结构混乱。

### 根因 6:持久化存储的 blocks 类型不匹配

`UnifiedMessage.blocks` 定义为 `FrontendMessageBlock[]`,但 `ChatManagerImpl.persistMessage()` 和 `updateMessageBlocks()` 中:

```typescript
blocks: message.blocks as unknown as FrontendMessageBlock[] | undefined,
```

这里的类型断言可能导致序列化/反序列化时字段丢失。

## 解决方案

### 方案一:修复 getSessionMessages 从持久化存储读取(推荐)

**核心思路**:`getSessionMessages()` 不应从内存缓存读取,而应从 `SessionGateway`(持久化存储)读取,确保 blocks 完整。

#### 修改 1:CoreAPIImpl.ts - getSessionMessages

```typescript
// 修改前:从内存缓存读取
async getSessionMessages(sessionId: string): Promise<...> {
  const session = this.sessionManager.getSession(sessionId);
  if (!session) return [];
  return (session.messages || []).map((msg) => { ... });
}

// 修改后:从持久化存储读取
async getSessionMessages(sessionId: string): Promise<...> {
  // 优先从持久化存储读取
  try {
    const storedMessages = await this.chatManager.getSessionGateway().getMessages(sessionId);
    if (storedMessages && storedMessages.length > 0) {
      return storedMessages.map((m) => ({
        id: m.id,
        role: m.role,
        content: typeof m.content === 'string' ? m.content : '',
        timestamp: m.timestamp,
        tool_calls: m.metadata?.tool_calls as Array<Record<string, unknown>> | undefined,
        toolCallId: m.metadata?.toolCallId as string | undefined,
        blocks: m.blocks as Array<Record<string, unknown>> | undefined,
      }));
    }
  } catch {
    // fallback to memory
  }
  
  // fallback: 从内存缓存读取
  const session = this.sessionManager.getSession(sessionId);
  if (!session) return [];
  return (session.messages || []).map((msg) => { ... });
}
```

#### 修改 2:ChatManagerImpl - 暴露 SessionGateway

在 `ChatManagerImpl` 中添加方法:

```typescript
public getSessionGateway(): SessionGateway {
  return this.sessionGateway;
}
```

#### 修改 3:前端 setMessages - 完善 blocks 重建逻辑

```typescript
setMessages: (messages: Message[]) => {
  const enhancedMessages = messages.map((msg) => {
    if (msg.role !== 'assistant') return msg;
    
    // 如果后端已保存 blocks,直接
    if (msg.blocks && msg.blocks.length > 0) {
      return { ...msg, blocks: msg.blocks.map((b) => ({ ...b, isStreaming: false })) };
    }

    // 否则自动重建 blocks
    const newBlocks: MessageBlock[] = [];

    if (msg.content) {
      newBlocks.push({
        id: generateBlockId(),
        type: 'text',
        content: msg.content,
        isStreaming: false,
      });
    }

    if (msg.tool_calls && msg.tool_calls.length > 0) {
      msg.tool_calls.forEach((tc) => {
        newBlocks.push({
          id: generateBlockId(),
          type: 'tool_call',
          content: '',
          toolCall: tc,
          isStreaming: false,
        });
      });
    }

    // 从 metadata 恢复 status 信息(如果有)
    if (msg.metadata?.tool_statuses) {
      const statuses = msg.metadata.tool_statuses as string[];
      statuses.forEach((status) => {
        newBlocks.push({
          id: generateBlockId(),
          type: 'status',
          content: status,
          isStreaming: false,
        });
      });
    }

    return { ...msg, blocks: newBlocks };
  });

  set({ messages: enhancedMessages });
},
```

### 方案二:流式保存 blocks(实时持久化)

在 `chatStore.ts` 的流处理循环中,**每接收到一个 chunk 就更新 blocks 并保存**,而不是等到流结束才保存。

```typescript
// 在每个 chunk 处理完成后,立即持久化 blocks
// 避免在流结束前切换会话导致 blocks 丢失

// 在流处理循环内,每次更新 msg 后:
if (sessionId && updatedMsg.blocks && updatedMsg.blocks.length > 0) {
  // 使用防抖,避免过于频繁的 API 调用
  debouncedSaveBlocks(sessionId, assistantId, updatedMsg.blocks);
}
```

### 方案三:修复消息类型映射

```typescript
// ChatManagerImpl.ts - toSessionMsgType
private toSessionMsgType(message: Message): SessionMessageType {
  if (message.role === MessageRole.USER) return SessionMessageType.USER;
  // 所有 assistant 消息统一标记为 ASSISTANT,不再区分 TOOL_USE
  if (message.role === MessageRole.ASSISTANT) return SessionMessageType.ASSISTANT;
  if (message.role === MessageRole.TOOL) return SessionMessageType.TOOL_RESULT;
  return SessionMessageType.SYSTEM;
}
```

### 方案四:前端 blocks 渲染增强

在 `renderBlocksWithGroups` 中,当 blocks 为空但 `tool_calls` 存在时,自动创建 tool_call block:

```typescript
// ChatMessage.tsx - AssistantMessage
function AssistantMessage({ message, isStreaming }: { message: Message; isStreaming?: boolean }) {
  // 如果 blocks 为空但有 tool_calls,自动构建 blocks
  if (!message.blocks || message.blocks.length === 0) {
    if (message.tool_calls && message.tool_calls.length > 0) {
      const autoBlocks: MessageBlock[] = [];
      if (message.content) {
        autoBlocks.push({
          id: generateBlockId(),
          type: 'text',
          content: message.content,
          isStreaming: false,
        });
      }
      message.tool_calls.forEach((tc) => {
        autoBlocks.push({
          id: generateBlockId(),
          type: 'tool_call',
          content: '',
          toolCall: tc,
         Streaming: false,
        });
      });
      message.blocks = autoBlocks;
    }
  }
  
  // 后续渲染逻辑...
}
```
