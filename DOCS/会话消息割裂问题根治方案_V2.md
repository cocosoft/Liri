## 一、根因分析

### RC1：renderBlocksWithGroups 将所有连续 tool 相关块合并为一组

**代码位置**：[ChatMessage.tsx:L330-L340](file:///e:/PY/CODES/PY_APP/client/src/components/ChatArea/ChatMessage.tsx#L330-L340)

```typescript
// 当前逻辑：只要 isToolRelatedBlock 为 true，就不分组
while (i < blocks.length && isToolRelatedBlock(blocks[i])) {
    toolBlocks.push(blocks[i]);
    i++;
}
```

**问题场景**：当两次工具调用之间没有文本块时（LLM 在一次回复中连续调用多个工具），blocks 如下：

```
[text①, status(Running A), status(参数), tool_call(A), status(Completed A),
 status(Running B), tool_call(B), status(Completed B), text②]
```

`isToolRelatedBlock` 不区分工具调用 A 和 B，因为 `type === 'status' || type === 'tool_call'` 对两者都返回 `true`。结果：6 个块被合并为 1 个 `ToolExecutionGroup`，用户看到两次工具调用挤在一个折叠框里。

### RC2：MessageBlock 类型缺少标识工具调用归属的字段

**代码位置**：[types/index.ts:L28-L35](file:///e:/PY/CODES/PY_APP/client/src/types/index.ts#L28-L35)

```typescript
export interface MessageBlock {
    id: string;
    type: 'text' | 'thinking' | 'tool_call' | 'status';
    content: string;
    toolCall?: ToolCall;
    status?: string;
    isStreaming?: boolean;
    // ❌ 没有 toolCallId 字段
}
```

`status` 类型的 block 没有 `toolCallId`，渲染器无法判断它属于哪次工具调用。

### RC3：历史记录 fallback 将全部 tool_calls 放在末尾

**代码位置**：[chatStore.ts setMessages](file:///e:/PY/CODES/PY_APP/client/src/stores/chatStore.ts) 中的 fallback 重建逻辑

```typescript
if (msg.content) {
    newBlocks.push({ type: 'text', content: msg.content });  // 全部文字
}
if (msg.tool_calls && msg.tool_calls.length > 0) {
    msg.tool_calls.forEach((tc) => {
        newBlocks.push({ type: 'tool_call', toolCall: tc }); // 全部工具调用
    });
}
```

fallback 没有 `status` 块，且把所有 tool_call 排在 text 之后。但只要 RC1+RC2 修好，`renderBlocksWithGroups` 可以按 `toolCall.id` 正确分组。

### 修改 3：renderBlocksWithGroups 按 toolCallId 分组

**文件**：`client/src/components/ChatArea/ChatMessage.tsx`

```typescript
/**
 * 将 blocks 中的连续工具相关 blocks 按 toolCallId 分组
 */
function renderBlocksWithGroups(blocks: MessageBlock[], isStreaming?: boolean): React.ReactNode[] {
  const result: React.ReactNode[] = [];
  let i = 0;

  while (i < blocks.length) {
    const block = blocks[i];

    if (!isToolRelatedBlock(block)) {
      result.push(<BlockRenderer key={block.id} block={block} isStreaming={isStreaming} />);
      i++;
      continue;
    }

    const toolBlocks: MessageBlock[] = [];
    let lastToolCallId: string | undefined;

    while (i < blocks.length && isToolRelatedBlock(blocks[i])) {
      const currentBlock = blocks[i];

      // 遇到新的 tool_call（不同 ID），结束当前分组
      if (currentBlock.type === 'tool_call' && currentBlock.toolCall?.id) {
        if (lastToolCallId && currentBlock.toolCall.id !== lastToolCallId) {
          break;
        }
        lastToolCallId = currentBlock.toolCall.id;
      }

      toolBlocks.push(currentBlock);
      i++;
    }

    result.push(
      <ToolExecutionGroup key={`tool-group-${toolBlocks[0]?.id || i}`}
        blocks={toolBlocks} isStreaming={isStreaming} />
    );
  }

  return result;
}
```

## 三、数据流验证

### 新会话流式传输

```
Chunk 顺序：
  text("我来帮你")  → ChronologicalBlockBuilder.addText → text①
  status("Running read_file")  → addStatus(toolCallId=null, 此时 currentToolCallId 仍为 null)
  status("参数: path=xxx")     → addStatus(...)
  tool_call(read_file, id=A)  → addToolCall → currentToolCallId=A, hasToolCallSinceLastText=true
  status("✅ Completed")      → addStatus(toolCallId=A) — 归属 read_file
  status("Running search")    → addStatus(toolCallId=A) — 仍为 A（search 尚未到来）
  tool_call(search, id=B)     → addToolCall → currentToolCallId=B
  status("✅ Completed")      → addStatus(toolCallId=B) — 归属 search
  text("基于结果...")         → addText → text②

Blocks 结果：
  [text①, status(Running), status(参数), tool_call(A), status(Completed, A),
   status(Running), tool_call(B), status(Completed, B), text②]

renderBlocksWithGroups 分组：
  Group1: [status(Running), status(参数), tool_call(A), status(Completed, A)]
          — tool_call(A) 遇到 tool_call(B) 时 break
  Group2: [status(Running), tool_call(B), status(Completed, B)]
          — 下一次遇到非 tool-related 块 text② 时结束
  text② → 独立渲染
```

**⚠️ 注意**：两次工具调用之间的 `status(Running search)` block 会在 `addToolCall(search)` 之前生成，此时 `currentToolCallId` 仍为 A。该 status block 会被归入 Group1。

**要解决这个**，需要在上一个工具调用完成后重置 `currentToolCallId`，或者在收到新的 running status 时预判。

最简洁的修复：在 `addToolCall` 中，当发现新的 toolCall.id 时，检查前面的 status blocks 中是否有上一组的，不做迁移（Group1 带一个多余的 status 可以接受，折叠态下不会显示内部细节）。

**但更干净的方案**：在 `ChronologicalBlockBuilder` 中，当 text 到来时重置 `currentToolCallId = null`，然后当第一个 status（Running）到来时，它没有 `toolCallId`。当 tool_call 到来时设置 `toolCallId`，后续的 status 带正确的 `toolCallId`。

实际上，`status(Running search)` 被归入 Group1 并不会造成显著体验问题，因为 ToolExecutionGroup 折叠后只显示第一个 tool_call 的名称。但为了完美，可以在工具调用完成后，在收到新的 "Running" status 时触发分组边界。

**最终决策**：接受 Group1 多一个 status block 的轻微不完美，因为 ToolExecutionGroup 折叠态下不显示内部 blocks 细节，用户感知不到。重点解决的是"两次工具调用合并为一组"这个核心问题。
