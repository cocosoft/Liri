## 一、问题来源与用户反馈

### 1.1 用户原话

> "请继续执行HTML生成的任务。另外，**如果遇到任务中断这类的异常，现在好像被吞了，不能显示出来给用户知道吗？**请先完成任务，然后再分析。"（2026-08-24 17:47）

### 1.2 场景复现

1. AI 回复 **"我来处理：先提取这份 docx 的完整正文……"**（有正文）
2. 任务被中断（用户推测"后端代码变更"）
3. 前端 **不显示任何中断提示**，用户反复询问："你是执行完了？还是还在执行中？"

### 1.3 核心问题

**任务中断时前端无任何可见提示**。用户无法区分「执行中 / 已完成 / 已中断」。

## 二、现状代码链路分析

### 2.1 中断信号的三类来源（关键区分）

| 中断原因 | 信号 | 前端表现 |
|---------|------|---------|
| 用户点击停止 | `controller.signal.aborted = true` | 无专门提示（被吞） |
| SSE 断开（网络/后端重启） | 不 abort；`chatService` yield error chunk（CONNECTION_RESET）→ 聚合器生成 `assistant/status` error 块 | **有提示**（"连接已断开"） |
| 静默结束（幽灵块检测：30s 无 chunk + 后端报告流已结束） | 幽灵块检测调用 `controller.abort()` | 无专门提示（被吞） |

> 结论：**`signal.aborted` ≠ 所有中断**。它只覆盖"用户停止"与"幽灵块检测"；SSE 断开走 error chunk 路径（已有提示）。真正被吞的是 **abort 类**场景（用户停止 / 幽灵块 / 后端静默中断）。

### 2.2 中断信息链路（后端已完整，前端 4 处断裂）

| # | 环节 | 位置 | 状态 |
|:-:|------|------|:---:|
| 1 | 后端 abort → 消息落盘 `finishReason='abort'` | `ChatManager._finalizeStreamMessage` L3640-3642 | ✅ |
| 2 | 后端落盘 `turn/end` 事件（`finishReason=canceled`） | `streamMessageFlow.ts` L1053-1069 | ✅ |
| 3 | 前端聚合器 `endTurn` 生成带 finishReason 的 turn/end 事件 | `EventBasedStreamAggregator.ts` L572-578 | ✅ |
| 4 | `deriveConversationBlocks` turn/end case **丢弃 finishReason** | `deriveConversationBlocks.ts` L275-278 | ❌ |
| 5 | 消息类型 `finishReason` 枚举**缺 abort/canceled/error** | `client/types/message.ts` L266 | ❌ |
| 6 | `ChatMessage` 中断提示**只看「无正文+有思考」，不看 finishReason** | `ChatMessage.tsx` L1186-1215 | ❌ |
| 7 | 流式实时路径：abort 时无 done chunk → 聚合器不生成 turn/end → 流式消息**拿不到 finishReason** | `chat-message-stream.ts` L621-726 | ❌ |

### 2.3 前端已覆盖的中断场景（与缺口区分）

| 场景 | 处理 | 位置 |
|------|------|------|
| 工具调用未完成（tool_call 块 running） | `⚠️ 任务中断：以下工具未完成` status 块 | `chat-message-stream.ts` P3-1 |
| 思考了但无正文（thinking-only） | "生成中断"提示 text 块 | `ChatMessage.tsx` H-FIX-2 |
| SSE 断开 | "连接已断开"提示（error chunk → status 块） | `chatService.ts` / 聚合器 |
| abort 行为 | 不播完成音、不覆盖后端数据 | `chat-message-stream.ts` L768/827 |

**缺口**：「有正文但被中断」（用户停止 / 幽灵块检测 / 后端静默中断），完全无提示。

### 2.4 根因结论

后端已完整落盘中断信息，前端存在 **5 处断裂**（v3 补第 5 处）：
- 事件→消息映射丢弃 finishReason（回放路径）
- 消息类型不认中断枚举（类型层）
- 中断提示不读 finishReason（组件层）
- 流式实时路径无中断信号来源（流式路径）
- **响应式更新断裂（v3 新增）**：前端 store 为 Zustand，直接改消息对象属性（`msg.finishReason = ...`）**不触发组件重渲染**——即使前 4 处修复完成，最后一步"改 store 不触发渲染"仍会白做。所有 finishReason 更新必须走 `set()` 不可变更新（新数组/新对象引用）。

## 三、修复方案（v2，5 处 + 1 姊妹项）

### 3.1 消息类型：finishReason 枚举扩展（含来源核对）

**文件**：`client/src/types/message.ts` L266

```typescript
finishReason?:
  | "stop"
  | "length"
  | "max_tokens"
  | "tool_calls"
  | "tool_use"
  | "canceled"
  | "abort"
  | "error";
```

**枚举值来源核对（避免死分支）**：

| 值 | 来源（已核实） |
|----|--------------|
| `abort` | `ChatManager._finalizeStreamMessage`（aborted ? 'abort' : 'stop'） |
| `canceled` | `streamMessageFlow.ts` turn/end 落盘（finalResponse.finishReason） |
| `error` | `streamMessageFlow.ts` L982（异常时 finalResponse = { finishReason: 'error' }） |
| `tool_use` / `tool_calls` | `ChatManager.ts` L3011 / `ReActToolLoop.ts` |

> 展示层统一收敛：`isInterrupted(fr) = fr === 'canceled' || fr === 'abort' || fr === 'error'`，组件只认一个判定。

### 3.2 事件→消息映射：turn/end 透传 finishReason（回放路径）

**文件**：`client/src/stores/chat/deriveConversationBlocks.ts` L275-278

**要点（v2 修正时序假设）**：`turn/end` 到达时 `state.current` 可能已被 flush（消息提前结束）。需维护"最近一条 assistant 消息"引用 `lastAssistantMsg`，turn/end 时挂到它上面：

```typescript
// BuilderState 增加：lastAssistantMsg: Message | null
case "turn/end": {
  const data = event.data as { finishReason?: string };
  const target = state.current ?? state.lastAssistantMsg;   // 修正：不依赖 current 必然存在
  // v3：条件赋值——data.finishReason 为空时不清掉已有值
  //（否则会覆盖 3.5 后端派生已补的 finishReason，导致验收 3 失败）
  if (target && data.finishReason) {
    target.finishReason = data.finishReason as Message["finishReason"];
  }
  flushCurrent(state);   // flush 时同步 lastAssistantMsg = current
  break;
}
```

### 3.3 流式实时路径：异常结束判据 + finishReason 落盘（v2 核心修正）

**文件**：`client/src/stores/chat/chat-message-stream.ts`

**v2 修正①——判据从 `signal.aborted` 泛化为"流未正常结束"**：

```typescript
// 流式期间维护两个标志（在 processChunk 内同步）
let receivedDone = false;      // 收到 done/turn/end chunk
let receivedError = false;     // 收到 error chunk（SSE 断开等，已有可见提示）

// 流结束处（原 L628 无内容兜底之后）：
const abnormallyEnded = !receivedDone && !receivedError;
if (abnormallyEnded || controller.signal.aborted) {
  // 流结束但从未正常收尾（用户停止 / 幽灵块 / 后端静默中断 / SSE 断开）
  // → 只落盘 finishReason（提示渲染统一交 3.4，见下）
  // messages 最后一条 assistant 消息设置 finishReason = "abort";
}
```

> 这样验收"SSE 断开 / 静默中断"全部由 3.3 保证，不再依赖 abort 单一信号。已收到 error chunk（有可见提示）时不重复提示。

**v3 修正③——`receivedError` 置位点必须覆盖 catch 分支（关键）**：

SSE 断开时，`chatService.ts` 的 error chunk 是在 **fetch catch 分支合成的**（CONNECTION_RESET 映射，L1174-1189），**不经过 processChunk 解析路径**。若 `receivedError` 只在 processChunk 内置位，SSE 断开时它**永远为 false** → 落入 `abnormallyEnded` → 落 `'abort'` + 双提示（3.4 的"该回复已中断" + 已有的"连接已断开"status 块）。

```typescript
// 置位点①：processChunk 内（正常 error chunk 路径）
// 置位点②：chatService yield error chunk 处同步置位（catch 分支），
//   或将 receivedError 提升为聚合器/流上下文共享标志，由 error 生成点统一置位
```

**v3 修正④——响应式更新机制（隐藏的第 5 处断裂）**：

前端 store 为 Zustand，**直接改消息对象属性不触发组件重渲染**。3.3 落 finishReason 必须走不可变更新：

```typescript
// ❌ 直接改属性：不触发渲染，3.4 不会显示
// const msg = get().messages.at(-1); msg.finishReason = "abort";

// ✅ 走 set() 不可变更新（新数组引用 → 触发 ChatMessage 重渲染）
if (abnormallyEnded || controller.signal.aborted) {
  const msgs = get().messages;
  const lastAssistantIdx = ...; // 定位最后一条 assistant
  if (lastAssistantIdx >= 0) {
    const next = msgs.map((m, i) =>
      i === lastAssistantIdx
        ? { ...m, finishReason: "abort" as const }
        : m,
    );
    set({ messages: next });   // Zustand set → 组件感知
  }
}
```

**v3 修正⑤——评估时机**：只在 SSE 连接真正关闭处评估**一次**（fetch `finally`），多轮工具调用（tool_use → 结果 → 继续生成）之间不评估，避免把正常多轮误判为中断。`receivedDone` 置位覆盖所有正常收尾 chunk（done / turn/end）。

**v2 修正②——3.3 与 3.4 去重（方案甲，推荐）**：

- **流式路径只落盘 `finishReason`，不写提示块**；提示块统一由组件层（3.4）按 finishReason 生成
- 职责单一：流式/回放路径天然一致，无双提示
- 保留现有 P3-1（工具未完成）不并入——它是独立语义（工具中断，非整条回复中断），但 3.4 渲染时可识别该 status 块避免重复

### 3.4 中断提示判断：组件层统一渲染（v2）

**文件**：`client/src/components/ChatArea/ChatMessage.tsx` L1186-1215

```typescript
const isInterrupted = (fr?: Message["finishReason"]) =>
  fr === "canceled" || fr === "abort" || fr === "error";

// 统一入口：finishReason 判定优先；thinking-only 兜底保留
if (!isStreaming && isInterrupted(message.finishReason)) {
  blocks = [
    {
      id: "fb_interrupted_hint_" + message.id,
      type: "text",
      content: hasTextBlock
        ? "⚠️ **该回复已中断（任务被中止），未继续完成。** 下方为中断前已生成的内容。"
        : "⚠️ **该回复生成中断，未完成最终输出。** 下方「💭 思考过程」标签中保留了模型当时的推理草稿，可点击展开查看。",
      isStreaming: false,
      groupId: "fb_interrupt_" + message.id,
    },
    ...blocks,
  ];
} else if (!isStreaming && !hasTextBlock && hasThinkBlock && contentEmpty) {
  // 原有 H-FIX-2（thinking-only，兼容 finishReason 未落盘的存量消息）
}
```

> 消息若已有 P3-1 的"任务中断：工具未完成"status 块，3.4 先检测该块存在则跳过追加（防御双重提示）。

**v3 修正⑥——error 场景去重**：SSE 断开时已存在"连接已断开"status 块（error chunk 生成），3.4 对 `finishReason='error'` 的消息**不再追加提示块**（避免双提示）。判定收敛为：

```typescript
const isInterrupted = (fr?: Message["finishReason"]) =>
  fr === "canceled" || fr === "abort";   // error 已有"连接已断开"status 块，不重复提示
```

**v3 修正⑦——thinking-only 文案统一**：`finishReason='abort'` 且 thinking-only（无 text 有 think）时，isInterrupted 分支与 H-FIX-2 文案语义重叠，统一走 H-FIX-2 单一路径（先查是否有 text 块：无 → 沿用 H-FIX-2 原文案；有 → 用"该回复已中断"），避免两处文案漂移。

### 3.5 后端事件派生补 finishReason（v2 提为必做）

**文件**：`app/src/session/storage/EventMessageDeriver.ts`

v1 标为"可选"导致验收 3 依赖"投影通常带 finishReason"的不确定前提。**v2 提为必做**：

- 聚合循环读到 `turn/end` → 记录 `lastTurnFinishReason`
- 消息 push（含投影覆盖分支）时：若 `finishReason` 为空且该消息所属 turn 的 finishReason 为中断值 → 补充

```typescript
// 聚合循环外维护
let lastTurnFinishReason: string | undefined;
// turn/end 事件处：
lastTurnFinishReason = (event.data as { finishReason?: string }).finishReason;
// 消息落盘（聚合分支 & 投影覆盖分支）：
finishReason:
  agg 或 proj 的 finishReason ??
  (lastTurnFinishReason === "canceled" || lastTurnFinishReason === "error"
    ? lastTurnFinishReason
    : undefined),
```

> 验收 3（回放识别）从此不依赖"投影通常带"前提，事件派生路径同样成立。

### 3.6 姊妹问题（v2 补充）：工具执行中无进度反馈

本方案解决"中断后提示缺失"，但"任务被吞"还有另一半：**工具执行中（如 docx 转换）无任何进度反馈**，用户只能干等。已知根因：`emitToolProgress` 无调用点、`onProgress` 回调未接线。

- 前端：聚合器 `assistant/progress` 事件已支持 execution_phase 块，接线 `onProgress` 即可渲染"正在执行 xxx"实时状态

## 九、v3 三轮评审修订

### 9.1 数据流图：3.2 与 3.5 职责边界（v3 修正④）

两条路径并行，职责不同，不重复实现：

```
实时路径：SSE chunk → EventBasedStreamAggregator → turn/end(带 finishReason)
          → deriveConversationBlocks（3.2：turn/end 透传 finishReason）
          → ChatMessage（3.4：isInterrupted 渲染）
回放路径：events.jsonl → EventMessageDeriver（3.5：补 finishReason）
          → getSessionMessages → 前端 setMessages
          → ChatMessage（3.4：isInterrupted 渲染）
```

- **3.5 负责回放落盘**（派生消息带 finishReason）
- **3.2 负责实时事件→消息映射**（turn/end 透传）
- 两者覆盖不同数据流，3.2 输入是原始事件流（不经 3.5）；3.2 条件赋值（v3 修正②）保证不回清 3.5 已补值

## 十、补充修复：FileReadTool 大文档分段读取（2026-08-24）

**背景**：长程任务检查发现核心遗留——docx 大文档（如 18 万字符白皮书）转换后经 `truncateConvertOutput` 截断为 30K（前 2.1 万 + 后 0.9 万），中间内容永远读不到，是大文档精读类任务卡住的根源。

**修复**（`app/src/tools/FileReadTool/FileReadTool.ts`）：
- `execute()` 二进制分支透传 `offset/limit` 给 `convertFile`
- `convertFile(filePath, onProgress, offset?, limit?)`：指定 offset/limit 时**按行切片**（与文本文件 `readFile` 的行语义一致），系统提示返回行段范围（"共 N 行，当前第 X-Y 行，可继续读取后续段落"）；未指定时保持原截断行为（防 tokenize/GC 阻塞）

**真实数据验证**（白皮书 V4.4.docx，共 1142 行）：
- 无 offset/limit：30K 截断（含提示，保留头尾）——原行为不变 ✓
- `offset=100&limit=50`：返回第 100-149 行（50 行，854 字符，无截断提示），可连续分段读完全文 ✓

**效果**：模型可逐段 `offset/limit` 读取大文档全文，大文档精读类长程任务不再因信息缺失中断。
