# Liri 模块开发规范

## 1. 概述

本文档定义了Liri项目的模块开发规范，旨在建立统一的模块开发标准，确保代码质量、可维护性和团队协作效率。

## 2. 模块分类标准

### 2.1 模块分类

所有模块必须按照以下分类进行组织：

```typescript
export enum ModuleCategory {
  // 核心模块
  CORE = 'core',                 // 核心功能模块
  INFRASTRUCTURE = 'infrastructure', // 基础设施模块
  
  // 功能模块
  AI = 'ai',                     // AI相关模块
  AGENT = 'agent',               // 代理模块
  BRIDGE = 'bridge',             // 桥接模块
  
  // 界面模块
  UI = 'ui',                     // 用户界面模块
  CLI = 'cli',                   // 命令行界面模块
  
  // 工具模块
  TOOLS = 'tools',               // 工具管理模块
  COMMANDS = 'commands',         // 命令模块
  
  // 数据模块
  MEMORY = 'memory',             // 记忆管理模块
  CACHE = 'cache',               // 缓存模块
  
  // 系统模块
  SECURITY = 'security',         // 安全模块
  PERFORMANCE = 'performance',   // 性能模块
  MONITORING = 'monitoring',     // 监控模块
  
  // 其他模块
  OTHER = 'other'                // 其他功能模块
}
```

### 2.2 模块命名规范

#### 2.2.1 目录命名
- 使用小写字母
- 使用连字符分隔单词（如：`memory-management`）
- 避免使用缩写，除非是广泛认可的

#### 2.2.2 文件命名
- 使用PascalCase（如：`MemoryManager.ts`）
- 接口以`I`开头（如：`IMemoryService.ts`）
- 工具类以`Utils`结尾（如：`StringUtils.ts`）

## 3. 模块结构规范

### 3.1 标准模块结构

每个模块必须遵循以下目录结构：

```
模块名称/
├── index.ts              # 模块入口文件（必须）
├── types/                # 类型定义
│   ├── index.ts
│   └── 具体类型.ts
├── services/             # 服务层
│   ├── index.ts
│   └── 具体服务.ts
├── components/           # 组件（UI模块专用）
│   ├── index.ts
│   └── 具体组件.tsx
├── utils/                # 工具函数
│   ├── index.ts
│   └── 具体工具.ts
├── tests/                # 测试文件
│   ├── unit/
│   └── integration/
└── README.md             # 模块文档（必须）
```

### 3.2 模块入口文件规范

每个模块必须有一个`index.ts`文件作为入口：

```typescript
/**
 * 模块名称模块
 * 模块功能描述
 * 
 * @packageDocumentation
 */

// 导出类型
export * from './types';

// 导出服务
export * from './services';

// 导出工具
export * from './utils';

// 导出主类
export { 主类 } from './主类文件';

// 默认导出（可选）
export default 主类;
```

## 4. 代码规范

### 4.1 导入导出规范

#### 4.1.1 导入路径
必须使用别名路径：

```typescript
// ✅ 正确 - 使用别名
import { Agent } from '@modules/agent';
import { AI } from '@modules/ai';

// ❌ 错误 - 使用相对路径
import { Agent } from '../../agent/agent.ts';
```

#### 4.1.2 导出规范
- 优先使用命名导出
- 避免默认导出与命名导出混用
- 导出必须包含类型信息

```typescript
// ✅ 正确
import { ModuleDefinition, moduleRegistry } from './ModuleRegistry';

export { ModuleDefinition, moduleRegistry };
export { MODULE_DEFINITIONS } from './ModuleDefinitions';

// ❌ 错误
export default moduleRegistry;
export const MODULE_DEFINITIONS = require('./ModuleDefinitions');
```

### 4.2 类型定义规范

#### 4.2.1 接口定义
```typescript
/**
 * 模块定义接口
 */
export interface ModuleDefinition {
  // 基本信息
  id: string;                    // 唯一标识
  name: string;                  // 模块名称（英文）
  displayName: string;           // 显示名称（中文）
  version: string;               // 版本号
  
  // 功能信息
  category: ModuleCategory;      // 模块分类
  description: string;           // 模块描述
  
  // 依赖信息
  dependencies: string[];        // 依赖模块ID
  optionalDependencies: string[]; // 可选依赖
}
```

#### 4.2.2 类型导出
所有类型必须通过`types/index.ts`统一导出：

```typescript
// types/index.ts
export * from './ModuleDefinition';
export * from './ImportOptions';
export * from './MigrationAnalysis';
```

### 4.3 错误处理规范

#### 4.3.1 错误类型
```typescript
/**
 * 模块错误类型
 */
export class ModuleError extends Error {
  constructor(
    message: string,
    public moduleId: string,
    public errorCode: string
  ) {
    super(`[${moduleId}] ${message}`);
    this.name = 'ModuleError';
  }
}
```

#### 4.3.2 错误处理
```typescript
// ✅ 正确 - 使用自定义错误
export async function initializeModule(moduleId: string): Promise<void> {
  try {
    await module.initialize();
  } catch (error) {
    throw new ModuleError(
      `初始化失败: ${error.message}`,
      moduleId,
      'INIT_FAILED'
    );
  }
}
```

## 5. 模块注册规范

### 5.1 模块定义

每个模块必须在`ModuleDefinitions.ts`中定义：

```typescript
export const MODULE_DEFINITIONS: Record<string, ModuleDefinition> = {
  'core': {
    id: 'core',
    name: 'core',
    displayName: '核心模块',
    version: '1.0.0',
    category: ModuleCategory.CORE,
    description: '应用核心功能模块，提供基础架构和生命周期管理',
    dependencies: [],
    optionalDependencies: []
  },
  // ... 其他模块定义
};
```

### 5.2 依赖管理

#### 5.2.1 依赖声明
必须明确声明所有依赖：

```typescript
'agent': {
  id: 'agent',
  name: 'agent',
  displayName: '代理模块',
  version: '1.0.0',
  category: ModuleCategory.AGENT,
  description: 'AI代理功能模块，提供代理管理和执行',
  dependencies: ['core', 'ai'],        // 必须依赖
  optionalDependencies: ['memory']     // 可选依赖
}
```

#### 5.2.2 循环依赖检查
禁止循环依赖，开发时必须运行依赖检查：

```bash
# 检查依赖关系
npm run check-dependencies
```

## 8. 版本管理规范

### 8.1 版本号规则

使用语义化版本号：`主版本号.次版本号.修订号`

- **主版本号**: 不兼容的API修改
- **次版本号**: 向下兼容的功能性新增
- **修订号**: 向下兼容的问题修正

### 8.2 版本更新

模块版本更新必须在`ModuleDefinitions.ts`中同步更新：

```typescript
'core': {
  id: 'core',
  name: 'core',
  displayName: '核心模块',
  version: '1.1.0',  // 更新版本号
  // ... 其他属性
}
```

## 9. 开发流程规范

### 9.1 新模块开发流程

1. **设计阶段**
   - 编写设计文档
   - 确定模块分类和依赖关系
   - 评审设计文档

2. **实现阶段**
   - 创建模块目录结构
   - 实现核心功能
   - 编写单元测试

3. **集成阶段**
   - 在`ModuleDefinitions.ts`中注册模块
   - 编写集成测试
   - 更新文档

4. **验收阶段**
   - 代码审查
   - 性能测试
   - 发布准备

### 9.2 模块修改流程

1. **影响分析**
   - 分析修改对依赖模块的影响
   - 更新版本号（如果需要）

2. **实现修改**
   - 实现功能修改
   - 更新测试用例

3. **回归测试**
   - 运行所有相关测试
   - 验证依赖模块功能

## 11. 附录

### 11.1 最佳实践

1. **单一职责原则**: 每个模块只负责一个明确的功能
2. **依赖倒置原则**: 依赖抽象而不是具体实现
3. **接口隔离原则**: 定义专门的接口而不是通用接口
4. **开闭原则**: 对扩展开放，对修改关闭

### 11.2 常见问题

#### Q: 如何确定模块的分类？
A: 参考第2章模块分类标准，根据模块的主要功能确定分类。

#### Q: 如何处理模块间的循环依赖？
A: 重构模块设计，提取公共功能到新模块，或使用依赖注入。

#### Q: 模块版本号何时需要更新？
A: 参考第8章版本管理规范，根据修改的性质决定版本号更新。
