# 沙箱后端降级对照（6 种后端）

> **本文目的**：回答外部审计者最难自己拼出来的问题 —— **6 种沙箱后端在「平台不支持 / 依赖缺失 / 初始化失败」时各自会怎么降级，以及降级后是不是 fail-closed**。
>
> **事实源**：**以代码为准**，行号基线 **2026-10-29**（issue #6）。本文不含设计意图，只记录代码当前的实际行为；与代码冲突时以代码为准并同步本文。
>
> **维护约定**：新增/移除后端、改动 `failClosed` / `bashEnabled` 默认值、或改变某条降级分支 ⇒ **必须同步本文**，否则视为文档失同步。

## 2. 逐后端说明

### 2.1 Landlock（Linux）

- **默认值**：`enabled=true`、`failClosed=false`、`bashEnabled=false`（`sandbox/landlock/config.ts:74-80`）。
- **`code_run` 的判定链**（纯函数 `decideCodeRunnerLandlock`，`tools/CodeRunner/LinuxSandboxRunner.ts:117-141`）：
  - `enabled=false` ⇒ `plain`（`master-off`）；
  - 非 Linux ⇒ `plain`（`platform-unsupported`）——**故意不 refuse**：跨平台执行器是合法执行器，否则会把 Windows/macOS 的 `code_run` 直接打死（同文件 `:112-115` 注释）；
  - 能力不可用：`failClosed=true` ⇒ `refuse`；否则 ⇒ `plain`（`capability-unavailable`）。
- **初始化失败（exit 125）**：唯一权威信号是退出码 125（`isSandboxInitFailure`），`failClosed=true` ⇒ 拒绝执行，默认 ⇒ `fallback` 到跨平台执行器（`resolveSandboxInitFailure`，`:165-186`）。
- **`bash` 的判定链**（`decideBashLandlockGate`，`tools/bash/bashLandlockExec.ts:253-321`）：
  - `enabled=false` ⇒ `plain`；`bashEnabled=false`（**默认**）⇒ `plain`（`switch-off`）—— 即**默认 bash 完全不在沙箱内**；
  - `evalForced`（`ENV_EVAL_BASH_LANDLOCK`，评测专用）⇒ 能力可用走 `landlock`，否则**回退 plain、绝不 refuse**（`:273-278`）；
  - `bashEnabled=true` 且能力不可用 ⇒ **refuse**（`capability-unavailable`，`:309-318`）。
- **能力探测口径**：未探测出结果时按"不可用"处理（`sandbox/sandboxExecutionSignal.ts:89-94`），避免用"计划要走 Landlock"冒充隔离证据。

### 2.2 macOS Seatbelt

- 只认一条硬事实：`/usr/bin/sandbox-exec` 是否存在（`MacOSSandboxDetector.ts:26-37`；Apple 已标 deprecated 但仍随系统提供）。
- 执行器与 landlock **同形**（超时 / 输出上限 / 取消即进程树强杀），差异是**没有 exit-125 协议** ⇒ `sandboxInitFailed` 恒 `false`，profile 语法错误会以非 0 退出 + stderr 暴露（`runWithSandboxExec.ts:23-31,63-65`）。
- 首版只做**写隔离**（读 / 网络不收紧）。

### 2.3 Windows Low IL + Job Object

- `code_run` 在 win32 上先走它（`LinuxSandboxRunner.ts:300-306` 的平台分发）。
- 两处降级点都吃同一个 `sandbox.landlock.failClosed`（`WindowsSandboxRunner.ts:119-165`）：helper 不可用、以及 `icacls` 打不上 Low 完整性标签 —— 失败时若 `failClosed=false` 则回退跨平台执行器。
- helper 的退出码协议：`126` = helper 自身初始化失败（**不等于**目标程序失败）、`124` = 超时（`win/runWithWinSandbox.ts:29-34`）。
- `bash` 在 Windows 上**没有** OS 级兜底：`bashEnabled=true` ⇒ 直接 `refuse`（`platform-unsupported`，`bashLandlockExec.ts:298-307`）。

### 2.4 Docker 容器

- 初始化顺序：`docker info` 探活 → 镜像存在性检查（缺则拉取）→ 建容器（`DockerSandbox.ts:104-115`）。
- 探活失败直接抛 `AppError(..., 'DEPENDENCY_UNAVAILABLE')`（`:419-429`），**不**静默改用宿主目录。
- 网络策略额外一条 fail-closed：配置了端口白名单但仓内没有宿主侧执行器时，**不静默降级**（`docker/NetworkPolicyEngine.ts:16`）。

### 2.5 SSH 远端工作区

- `fallbackHost` 只做"换一台主机再试一次"（`SSHSandbox.ts:64,144-148,314`），**不是**降级成非隔离执行。
- 工作区解析抛异常时，`workspaceIsolation` 返回 `null` / 空映射，即"没有隔离证据"（`workspaceIsolation.ts:37-41,53-56`）。

### 2.6 Local / PTY（无隔离基线）

- `WorkspaceBase.isolationMode()` 默认 `'local'`（`WorkspaceBase.ts:163-165`）；文件类工具只有 `container` / `ssh` 且**有挂载映射**时才算隔离（同文件 `:167-174` 与 `workspaceIsolation.ts:12-16`）。
- 在本地工作区上，沙箱信号 `mode` 一律 `none`（无隔离证据），文件类能力**不豁免**（`sandboxExecutionSignal.ts:102-129,148-157`）。

## 3. 两个「默认 fail-open」的事实（审计重点）

> 这两条不是 bug，是**2026-08-25 用户确认的「兼容优先」决策**；但外部审计最容易误判成"沙箱已开启即受约束"，所以单独列出来。

1. **`sandbox.landlock.failClosed` 默认 `false`** ⇒ helper 退出码 125（沙箱初始化失败）或能力缺失时，`code_run`（含 Windows 分支）会**回退到无内核约束的执行器**。
   - 需要"开启即真受限"的场景，必须显式设 `sandbox.landlock.failClosed=true`。
2. **`sandbox.landlock.bashEnabled` 默认 `false`** ⇒ **`bash` 工具默认根本不在沙箱内**（`plain`），也**不**调用 Landlock / Seatbelt。
   - 打开后：Linux ⇒ Landlock、macOS ⇒ Seatbelt、**Windows ⇒ 拒绝执行**；能力不可用 ⇒ 拒绝（不静默降级）。
3. （评测专用，生产不生效）`ENV_EVAL_BASH_LANDLOCK` 强制分支是 **capability-gated**：能力不可用 ⇒ 回退 `plain`，**绝不 refuse**（`bashLandlockExec.ts:273-278`）。

### 3.1 运行时怎么知道自己「受不受约束」（issue #7，2026-10-29）

不看源码也能判断当前进程的姿态，有两个出口：

- **启动日志**：`sandbox:posture` 模块输出一行 `沙箱姿态（本次进程）`（含 `mode` / `permissionLevel` / `landlock.{enabled,bashEnabled,failClosed,available}`），并对**实际存在**的每条 fail-open 各打一条 `warn`（`沙箱 fail-open（2026-08-25 兼容优先的既定决策，非缺陷）`）。
  - 实现：`app/src/sandbox/sandboxPosture.ts` 的 `describeSandboxPosture()`（纯描述，不改任何判定/默认值），在组合根 `app/src/entrypoints/spiWiring.ts` 的 sandbox 段调用。
- **`GET /v1/sandbox/status`**：`runtimeIsolation` 字段即 `resolveSandboxExecutionSignal().mode`（`none` = 无隔离证据）；`settings` / `constraints` 原样透出运行时设置。

判定口径（与 §1 表一致）：`mode` 为 `none` ⇒ 本次执行**不受内核级约束**；`landlock.failClosed=false` ⇒ 初始化失败时会**静默回退**无约束执行器；`landlock.bashEnabled=false` ⇒ **bash 默认不在沙箱内**。

## 5. 已知缺口（如实记录）

1. **`sandbox-exec` 无 exit-125 协议** ⇒ macOS 上"沙箱初始化失败"与"目标命令失败"在结果结构上无法区分（`sandboxInitFailed` 恒 `false`）。
2. **Windows 只在 `code_run` 上接入**；`bash` 在 Windows + `bashEnabled=true` 时直接拒绝，没有 OS 级兜底。
3. **`failClosed` 是单一开关**，同时作用于 Linux（125 / 能力缺失）与 Windows（helper 不可用 / 打标签失败）两条路径；两者语义一致但耦合在同一配置键上。
