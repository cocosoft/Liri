##一、逻辑混乱 (3 处)

### 🔴 P1. 两条数据源并存 — `sessions` vs `chatSessions`

**文件**: `stores/root-store/sessionSlice.ts` (L62-68) + `stores/sessionStore.ts` (L36-55)

```
┌──────────────────────┐
│   rootStore           │
│  ├─ sessions:         │ ← SessionRecord[] (SessionHub 新格式)
│  │   SessionRecord[]  │   模块隔离，按 worktreeId 筛选
│  ├─ chatSessions:     │ ← Session[] (从 sessionService.list() 获取)
│  │   Session[]        │   旧格式，从后端加载
│  └─ currentSessionId  │
└──────────┬───────────┘
           │ subscribe
           ▼
┌──────────────────────┐
│  sessionStore         │ ← Mirror: deriveState() 从 rootStore 投影
│  ├─ sessions:            取 root.chatSessions
│  └─ currentSession    │    取 root.chatSessions.find(id)
└──────────────────────┘
```

**问题**: `SessionHistorySidebar.tsx` 从 `useSessionStore().sessions` 列表后，又用 `useRootStore().sessions` 的 `moduleType` 来过滤非 chat 会话。前者是 `Session[]`，后者是 `SessionRecord[]` — 如果两者不同步，过滤逻辑失效。

**影响**: 若后端创建了 session 但 `createChatSession` 未同步到 `sessions`（SessionRecord），sidebar 中来自其他模块（media/office/calendar）的 session 会混入聊天列表。

**修复建议**: 统一用一个数据源，废弃 `chatSessions`。sideBar 的过滤逻辑改为一次查询。

## 二、FileLink 污染 (2 处)

### 🟡 P4. 每切换会话 → 所有 InlineCodeLink 重新路径

**文件**: `components/ChatArea/markdown/InlineLink.tsx` (L75)

```typescript
useEffect 的依赖: [codeContent, knownFilePaths, checking, sessionId]
```

`sessionId` 来自 `useSessionStore((s) => s.currentSession?.id)`，切换会话时 `sessionId` 变化 → 所有 `InlineCodeLink` 实例的 effect 重新触发 → 向 `/api/file/resolve-path` 发起批量请求。

**影响**: 如果一个历史会话包含 30+ 文件引用，切换回该会话时会瞬间发起 30 个 API 请求。虽然有 `pathResolvePending` 去重，但请求还是批发出去了。

**修复建议**: 添加 `sessionId` 变化时的缓存保留策略，`setMessages` 时不清空路径缓存，或延迟 500ms 后批量验证。

## 三、工具链调用异常 (3 处)

### 🔴 P6. 模块级全局锁 `_sessionSwitchLock` 泄漏风险

**文件**: `stores/chat/chat-message.slice.ts` (L63-67)

```typescript
let _sessionSwitchLock = false;
let _pendingSwitchChunks: Array<{
  sessionId: string;
  assistantId: string;
  blocks: MessageBlock[];
}> = [];
```

**问题**: `setMessages()` 在 `try` 开始时设置 `_sessionSwitchLock = true`，在结束/异常时 `finally`/catch 中释放。但如果 catch 中的 `set({ messages: [] })` 本身又触发 Zustand 的 subscribe 回调 -> 再次调用 `setMessages`，锁会覆盖。

**风险**: 如果锁泄漏，后续流式 chunk 会永远被挂起到 `_pendingSwitchChunks`，导致 "消息发送了但界面不显示"。

**修复建议**: 使用 `try/finally` 确保锁释放，并添加 `lockOwner` 标识来检测嵌套调用。

### 🟡 P7. `sendMessage` 与 `streamMessage` 两条路径

**文件**: `/chat/chat-message.slice.ts` + `stores/use-cases/send-message.ts`

- `sendMessage()` — 非流式路径，调用 `chatService.sendMessage()`，用 `ChronologicalBlockBuilder`？**不，它不用**，它直接把后端返回的 `response` 对象作为完整消息塞进去。这意味着非流式路径完全没有 blocks 分割/重建。
- `streamMessage()` — 流式路径，有完整的 blocks 构建、防抖落盘、版本号机制。

**影响**: 非流式发送的消息，其 blocks 完全依赖于后端返回是否包含 blocks 字段。如果后端返回了带有 `content` 但无 `blocks` 的消息，前端会走 `buildFallbackBlocks()` 重建，但重建逻辑捕获不到 `thinking`/`question`/`todo` 等特殊 block 类型。

**文件**: `stores/chat/chat-message.slice.ts` (streamMessage > ghostCheckTimer)

## 四、前端渲染混乱 (3 处)

### 🟡 P9. `ChatMessage` 的 memo 比较器引用相等性检查过于严格

**文件**: `components/ChatArea/ChatMessage.tsx` (L323-335)

```typescript
const prevBlocks = prevProps.message.blocks;
const nextBlocks = nextProps.message.blocks;
if ((prevBlocks?.length ?? 0) !== (nextBlocks?.length ?? 0)) return false;
if (prevBlocks !== nextBlocks) return false;
```

**问题**: `prevBlocks !== nextBlocks` 是引用比较。虽然 J4 批量更新机制对此做了优化，但当 `setMessages` 全量替换 `messages` 数组时，所有消息的 blocks 引用都会被重建，导致所有消息重渲染。

**影响**: 在有 50+ 条消息的会话中，每次流式 chunk 更新都会触发所有消息的 memo 比较。对于历史消息，`prevBlocks === nextBlocks` 通常为 true（因为旧消息的 blocks 没有变化），但全量 `set({ messages: [...] })` 会创建新引用。

## 五、Store 持久化与数据一致性 (2 处)

### 🟡 P12. `sessionStore` 与 `rootStore` 双 persist 竞态

**文件**: 
- `stores/sessionStore.ts` — persist 到 `liri-sessions`
- `stores/root-store/index.ts` — 到 `liri-root-store`

**问题**: 页面加载时，两个 `persist` 中间件会独立 rehydrate。`rootStore`  persist 包含 `chatSessions` 和 `sessions` 字段。`sessionStore` 的 `onRehydrateStorage` 回调将旧数据迁移到 rootStore。

**竞态**: 如果 `sessionStore` 先 rehydrate，`rootStore.chatSessions` 还是 `[]` → 迁移成功。如果 `rootStore` 先 rehydrate（已有 `chatSessions``sessionStore` 的迁移条件 `root.chatSessions.length === 0` 不满足 → 不会迁移。两者结果不同。

### 🟢 P13. `switchChatSession` 中 `currentSessionId` 在数据未就绪时已更新

**文件**: `stores/root-store/sessionSlice.ts` (switchChatSession 方法)

```typescript
// 第 1 处（数据未加载完）:
set({ currentSessionId: id });  // 触发 React 渲染
get().createSession("chat", session.title, id);

// ... 
// 第 2 处（finally 块）:
set({ switching false });
```

`currentSessionId` 在消息数据设置完成后设置，这个顺序是合理的。但 `set({ switching: false })` 在 `finally` 中执行——如果数据加载失败（catch 中），`switching` 会置 `false`，但currentSessionId` 可能没有恢复到 `prevId`（仅在 catch 中恢复）。
