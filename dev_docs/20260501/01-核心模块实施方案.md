## 2. 适用项目规则

### 2.1 模块管理规则（来源：`.trae/rules/module_management_rules.md`）

| 规则 | 要求 | 本模块适用说明 |
|------|------|---------------|
| 别名路径导入 | 必须使用 `@modules/模块名` 格式 | 所有新增代码必须使用 `@modules/core`、`@modules/config` 等别名导入 |
| 模块注册 | 新模块必须在 `ModuleDefinitions.ts` 中注册 | 新增子模块无需注册，但新增顶层模块需注册 |
| 模块分类 | 必须按照8个标准分类组织 | core属于核心模块，config属于其他模块 |
| 依赖声明 | 必须明确声明所有依赖关系 | 新增功能需声明对core/infrastructure的依赖 |

### 2.2 开发规范（来源：`.trae/rules/project_rules.md`）

| 规则 | 要求 | 本模块适用说明 |
|------|------|---------------|
| 严禁重复造轮子 | 先学习CC源码，直接复用成熟方案 | 补充常量时直接参考CC源码的常量定义 |
| 仅学习CC源码 | 严禁修改 `cc_code/` 下的任何文件 | 所有修改仅限 `backend/src/` 目录 |
| 先设计后开发 | 先完成详细设计，确认后再编码 | 每个任务先输出设计要点 |
| 不删除现有代码 | 仅新增或修改，不删除 | 保持向后兼容 |
| 学习-执行-测试-标注 | 四步流程 | 每个任务严格执行 |

### 2.3 代码规范（来源：`.trae/rules/PY_APP.md`）

| 规则 | 要求 |
|------|------|
| 简洁优先 | 最小代码解决问题，不做推测性设计 |
| 精准修改 | 只改必须改的，匹配现有风格 |
| 目标驱动 | 定义成功标准，循环验证 |

### 2.4 架构哲学（来源：`.trae/rules/project_rules.md` §6）

| 原则 | 适用说明 |
|------|----------|
| 启动时序优化策略 | 补充MDM/Keychain预读取时参考T0-T4并行预加载策略 |

## 3. 实施原则

```
学习CC源码对应实现 → 理解设计思路 → 执行编码 → 测试验证 → 标注完成
```

1. 保持现有系统正常运行
2. 在现有基础上逐步增强
3. 每个阶段独立可交付
4. 分阶段验证，降低风险

- 🔴 高：核心功能缺失，影响基本使用
- 🟡 中：功能增强，提升用户体验
- 🟢 低：优化改进，锦上添花

## 6. 风险评估

| 风险 | 影响 | 概率 | 应对方案 |
|------|------|------|----------|
| 常量值与CC源码不一致 | 功能异常 | 低 | 逐项比对CC源码常量值 |
| Session ID冲突 | 会话混乱 | 低 | 使用UUID v4生成 |
| State统一导致回归 | 状态管理异常 | 高 | 渐进式迁移，保留Zustand适配层 |
| Provider与Zustand冲突 | 状态管理异常 | 中 | 充分测试兼容性，渐进式引入 |
| Config子系统整合冲突 | 配置丢失 | 中 | 先建立统一接口，再逐个接入 |
| Settings多源优先级错误 | 配置覆盖异常 | 中 | 严格按user→project→local→policy优先级 |
| 启动预读取失败 | 启动延迟 | 中 | 预读取设置超时，失败不阻塞 |
| 条件编译不兼容 | 构建失败 | 中 | 先评估可行性，不强制接入 |
