## 1. Core 模块

### 1.1 CC源码实现

CC源码没有独立的 `core/` 模块目录，核心功能分散在根级文件和多个子目录中：

| 文件/目录 | 功能 |
|-----------|------|
| `main.tsx` | 主入口，使用Commander.js定义CLI命令 |
| `setup.ts` | 环境初始化 |
| `src-shim.ts` | 源码路径映射 |
| `bootstrap/state.ts` | 启动状态管理 |
| `state/AppState.tsx` | 应用状态（React Context） |
| `state/AppStateStore.ts` | 状态存储定义 |
| `state/store.ts` | 状态创建函数 |
| `state/selectors.ts` | 状态选择器 |

CC源码的核心架构特点：
- 使用 `bun:bundle` 的 `feature()` 实现条件编译
- 使用 React Context + 自定义 Store 管理应用状态
- 启动流程包含MDM预读取、Keychain预读取等优化
- 使用 `@commander-js/extra-typings` 定义CLI命令

### 1.2 PY_APP实现

PY_APP将核心功能整合到 `src/core/` 模块中：

| 文件 | 功能 |
|------|------|
| `AppCore.ts` | 应用核心类（单例模式） |
| `DIContainer.ts` | 依赖注入容器 |
| `PluginSDK.ts` | 插件SDK |
| `Coordinator.ts` | 协调器 |
| `featureFlags.ts` | 功能开关 |
| `index.ts` | 统一导出 |
| `auth/AuthManager.ts` | 认证管理器 |
| `config/index.ts` | 配置管理 |
| `lazy/index.ts` | 懒加载支持 |
| `loop/TAORLoop.ts` | TAOR循环 |
| `state/Store.ts` | 状态存储 |
| `state/AppState.ts` | 应用状态 |
| `task/index.ts` | 任务服务 |
| `theme/index.ts` | 主题管理 |

### 1.3 对比分析

| 维度 | CC源码 | PY_APP | 差异评估 |
|------|--------|--------|----------|
| 架构模式 | 扁平化，功能分散 | 模块化，AppCore单例 | PY_APP更结构化 |
| 依赖注入 | 无 | DIContainer | PY_APP新增 |
| 状态管理 | React Context + 自定义Store | Zustand | 技术选型不同 |
| 功能开关 | `bun:bundle feature()` | 自实现 `feature()` | CC源码有编译时优化 |
| 插件系统 | PluginSDK内嵌 | 独立PluginSDK类 | PY_APP更独立 |
| 协调器 | 无独立实现 | Coordinator类 | PY_APP新增 |
| 启动优化 | MDM/Keychain预读取 | 简单的profileCheckpoint | CC源码更完善 |

### 1.4 差距与建议

**差距**:
1. CC源码的启动优化（MDM预读取、Keychain预读取）在PY_APP中缺失
2. CC源码使用 `react/compiler-runtime` 进行React编译优化，PY_APP未采用
3. PY_APP的 `feature()` 函数缺少编译时条件加载能力

**建议**:
1. 补充启动预读取优化机制
2. 考虑引入React编译器优化
3. 评估接入 `bun:bundle feature()` 的可行性

### 8.2 State模块双系统问题

PY_APP存在**两套并行的状态管理系统**，这是核心架构问题：

| 系统 | 位置 | 技术选型 | 状态类型 | 使用场景 |
|------|------|----------|----------|----------|
| Zustand系统 | `state/AppState.ts` + `state/AppStateStore.ts` | Zustand | 简单（3个字段） | React组件 |
| CC源码Store系统 | `core/state/Store.ts` + `core/state/AppState.ts` + `core/state/AppStateStore.ts` | 自实现Store | 完整（288行类型定义） | 核心逻辑 |
| 增强状态系统 | `state/StateManager.ts` + `state/core/StateStore.ts` + `state/index.ts` | StateManager | 完整（含持久化/事件/快照） | 全局管理 |

**问题**:
1. 三套系统状态类型不统一（`types/state.ts` vs `core/state/types.ts` vs `core/state/AppState.ts`）
2. Zustand的`AppState`只有3个字段（companionReaction、companionPetAt、footerSelection），严重不足
3. `core/state/AppState.ts`有完整的288行类型定义，但与Zustand系统不连通
4. `state/selectors.ts`基于Zustand，但选择器引用的字段（sessionId、toolPermissionContext等）在Zustand Store中不存在

**建议**: 以`core/state/AppState.ts`的完整类型定义为基础，统一三套系统。
