## 1. 方案决策

### 1.1 BUG-02 双轨制收敛：选方案 A

| 维度 | 方案 A（推荐） | 方案 B |
|------|:-----------:|:------:|
| 做法 | 关闭 `_truncateApiMessages` 中的 ContextCompressor，仅做兜底截断 | QueryEngine 压缩后直接修改 `session.messages` |
| 压缩入口 | **QueryEngine 唯一入口** | 两个入口并行 |
| 压缩方式 | AI 摘要（QueryEngine） + 兜底截断（ChatManager） | AI 摘要（QueryEngine） + AI 语义压缩（ChatManager） |
| 优点 | 单一真相源，无冗余压缩，逻辑清晰 | ChatManager 的语义压缩能力保留 |
| 缺点 | 丢失 ContextCompressor 的语义压缩能力 | 两次 AI 压缩浪费 token，结果不协调 |

**决策理由**：
1. QueryEngine 的 `checkAndPerformCompact()` 已实现 3 级压缩策略（60% / 75% / 90%），覆盖了 ContextCompressor 的 `triggerRatio: 0.8` 场景
2. ContextCompressor 每次调 LLM 做摘要，本身就是 token 消耗，在"快超限"场景下雪上加霜
3. 修复 BUG-01 后，QueryEngine 的压缩将真正裁剪消息列表，ChatManager 的兜底截断仅在极端超限时触发
4. 兜底截断中的"短 user 消息保护"（`SHORT_USER_MSG_THRESHOLD`）和"跨轮决策摘要注入"逻辑可保留

### 1.2 BUG-03 recentMessageCount 动态化：选按比例计算

`recentMessageCount` 从固定 `6` 改为 `Math.max(6, Math.floor(totalNonSystem * 0.3))`，效果：

| 消息总数 | 旧值 | 新值（30%） |
|---------|:---:|:--------:|
| 20 | 6 (30%) | 6 |
| 50 | 6 (12%) | 15 |
| 100 | 6 (6%) | 30 |
| 300 | 6 (2%) | 90 |

**文件**：[ChatManager.ts](file:///E:/PY/CODES/PY_APP/app/src/chat/ChatManager.ts)

移除 L1051-L1112 的 ContextCompressor 调用块（"优先尝试 AI 摘要压缩"部分），保留：

```typescript
// 简化后的 _truncateApiMessages 流程
private async _truncateApiMessages(
  apiMessages: Record<string, unknown>[],
  maxContextTokens: number,
  sessionId?: string
): Promise<void> {
  if (maxContextTokens <= 0) return;

  const RESPONSE_BUFFER_TOKENS = Math.round(maxContextTokens * 0.15);
  const SAFE_LIMIT = maxContextTokens - RESPONSE_BUFFER_TOKENS;

  const estimatedTokens = roughTokenCountForMessages(
    apiMessages as { content?: string | unknown; role?: string }[]
  );
  if (estimatedTokens <= SAFE_LIMIT) return;

  // 由 QueryEngine 的 checkAndPerformCompact() 在主循环中提前压缩，
  // 此处仅在极端超限时做兜底截断

  logger.warn(
    `上下文超限: 估算 ${estimatedTokens} tokens (上限 ${SAFE_LIMIT})，执行兜底截断`
  );

  // ── 兜底截断：保护 system msg + 最近 30% 消息 ──
  const systemMsg = apiMessages.find((m) => m.role === 'system');
  const nonSystemMessages = apiMessages.filter((m) => m.role !== 'system');

  const protectedCount = Math.max(
    20,
    Math.min(100, Math.round(nonSystemMessages.length * 0.3))
  );

  const SHORT_USER_MSG_THRESHOLD = 200;
  let currentTokens = estimatedTokens;
  let dropCount = 0;
  const toDrop = new Set<number>();

  for (let i = 0; i < nonSystemMessages.length - protectedCount; i++) {
    if (currentTokens <= SAFE_LIMIT) break;
    const msg = nonSystemMessages[i] as Record<string, unknown>;
    const isShortUserMsg =
      msg.role === 'user' &&
      typeof msg.content === 'string' &&
      msg.content.length < SHORT_USER_MSG_THRESHOLD;
    if (isShortUserMsg) continue;
    const msgTokens = roughTokenCountForMessages([
      msg as { content?: string | unknown; role?: string },
    ]);
    currentTokens -= msgTokens;
    toDrop.add(i);
    dropCount++;
  }

  const keptNonSystem = nonSystemMessages.filter((_, i) => !toDrop.has(i));
  apiMessages.length = 0;
  if (systemMsg) apiMessages.push(systemMsg);
  for (const msg of keptNonSystem) apiMessages.push(msg);

  logger.warn(
    `兜底截断完成: 移除 ${dropCount} 条旧消息，估算剩余 ${currentTokens} tokens`
  );

  this._sanitizeApiMessages(apiMessages);

  // ── 跨轮决策摘要注入（保留） ──
  if (sessionId) {
    const session = this._chatSessions.get(sessionId);
    if (session?.metadata?.contextSummary) {
      const summaryContent = session.metadata.contextSummary as string;
      const insertIdx =
        apiMessages.length > 0 && apiMessages[0].role === 'system' ? 1 : 0;
      apiMessages.splice(insertIdx, 0, {
        role: 'system',
        content: `[跨轮决策摘要 — 以下为之前对话中用户已做出的关键决策]\n${summaryContent}`,
      });
    }
  }
}
```

### 3.4 P2 — BUG-04：QueryEngine 工具循环重复 user 消息

**目标**：后续迭代不再创建相同内容的 user 消息。

**文件**：[QueryEngine.ts](file:///E:/PY/CODES/PY_APP/app/src/query/QueryEngine.ts)

#### 3.4.1 在主循环中区分首次和后续迭代

当前主循环（L641-L658）：

```typescript
while (iteration < maxIterations) {
  iteration++;
  // ...
  const response = await this.callAPI(prompt, sessionId || '');
```

**修改方案**：不是修改 `callAPI` 签名，而是在 `callAPI` 的 `sendMessage` 调用前加判断。由于核心问题是 `sendMessage()` 每次都创建新的 user 消息，我们可以在第 2 次及之后的迭代中用 `tool_result` 角色或继续指令替代。

但 `sendMessage` 的签名设计可能不支持"不创建 user 消息"的调用方式。优先方案是：**在 `callAPI` 中，首次调用传原始 prompt，后续调用传继续指令前缀**。

```typescript
// 修改 callAPI 方法，增加 isFirstCall 参数
private async callAPI(
  prompt: string,
  sessionId: string,
  isFirstCall: boolean = true
): Promise<{...}> {
  // ...
  // 在 sendMessage 调用处
  let messageContent = prompt;
  if (!isFirstCall) {
    // 后续迭代：使用"继续执行"前缀，避免模型误解为重新开始
    messageContent = `[继续执行] ${prompt}`;
  }
  const message = await this.chatManager.sendMessage(messageContent, {
    sessionId,
  });
```

```typescript
// 主循环中
let isFirstCall = true;
while (iteration < maxIterations) {
  iteration++;
  // ...
  const response = await this.callAPI(prompt, sessionId || '', isFirstCall);
  isFirstCall = false;
```

> **替代方案（更彻底但改动更大）**：使用"无 user 消息的继续模式"——给 `sendMessage` 增加 `skipUserMessage: true` 参数，后续迭代直接调用 LLM（等同于 continuation）。需要评估 ChatManager 是否支持此模式。

#### 3.5.1 修改 `trim-tool-results` 策略

当前逻辑（L239-L269）对所有超过 500 字符的 tool 消息无差别截断到 200 字符。

**方案**：在截断前提取关键路径字段，完整保留，其余内容截断。

```typescript
// compact/index.ts — trim-tool-results 策略改进

// 关键字段模式：匹配 JSON 中的路径/URL 字段
const PRESERVE_KEY_PATTERN = /"(filePath|localUrl|inputPath|outputPath|url|path|imageUrl)":\s*"([^"]+)"/g;

compress: async (ctx: CompactionContext): Promise<CompactionResult> => {
  const messages = ctx.messages.map((m) => {
    if (m.role === 'tool' && m.content.length > 500) {
      // 提取关键字段值
      const preservedFields: string[] = [];
      let match;
      while ((match = PRESERVE_KEY_PATTERN.exec(m.content)) !== null) {
        preservedFields.push(`${match[1]}: ${match[2]}`);
      }

      // 截断其余内容，但保留关键字段
      const maxSnippetLen = 200;
      let truncated = m.content.slice(0, maxSnippetLen);

      if (preservedFields.length > 0) {
        truncated += `\n[关键路径]\n${preservedFields.join('\n')}`;
      }

      truncated += `\n... [截断 ${m.content.length - maxSnippetLen} 字符]`;

      return {
        ...m,
        content: truncated,
        tokenCount: Math.ceil(truncated.length / 4),
      };
    }
    return m;
  });
  // ... 其余不变
},
```

#### 3.5.2 修改 `summarize-oldest` 策略

当前逻辑（L204-L237）每条消息只保留 100 字符。

**方案**：在摘要中优先保留文件路径/ID 等标识信息。

```typescript
// compact/index.ts — summarize-oldest 策略改进
compress: async (ctx: CompactionContext): Promise<CompactionResult> => {
  // ...
  const summaryContent = removed
    .filter((m) => m.role !== 'system')
    .map((m) => {
      // 提取关键路径信息
      const pathExtracts = extractKeyPaths(m.content);
      const base = `[${m.role}]: ${m.content.slice(0, 100)}`;
      if (pathExtracts.length > 0) {
        return `${base}\n  路径: ${pathExtracts.join(', ')}`;
      }
      return base;
    })
    .join('\n');
  // ...
},

/** 从内容中提取文件路径/URL/ID 等关键标识 */
function extractKeyPaths(content: string): string[] {
  const paths: string[] = [];
  const patterns = [
    /(?:filePath|localUrl|inputPath|outputPath|path|url)["\s:=]+([^\s",}]+)/g,
    /([A-Za-z]:\\[^\s"',}]+\.\w{2,5})/g,  // Windows 绝对路径
    /\/[^\s"',}]+\.\w{2,5}/g,               // Unix 绝对路径
  ];
  for (const pattern of patterns) {
    let match;
    while ((match = pattern.exec(content)) !== null) {
      paths.push(match[1] || match[0]);
    }
  }
  return [...new Set(paths)].slice(0, 5);  // 去重，最多 5 条
}
```

#### 3.6.1 新增 `ToolCallTracker` 内部类

```typescript
// QueryGuard.ts — 新增 ToolCallTracker

interface ToolCallKey {
  toolName: string;
  paramsHash: string;  // JSON.stringify(params) 的简单哈希
}

interface ToolCallRecord {
  key: ToolCallKey;
  firstCalledAt: number;
  totalCalls: number;
  failures: number;
  lastError: string;
}

class ToolCallTracker {
  private records = new Map<string, ToolCallRecord>();
  private readonly MAX_RETRIES_PER_KEY = 3;

  /** 记录一次工具调用 */
  record(toolName: string, params: unknown, success: boolean, error?: string): void {
    const key = this.hashKey(toolName, params);

    if (!this.records.has(key)) {
      this.records.set(key, {
        key: { toolName, paramsHash: key },
        firstCalledAt: Date.now(),
        totalCalls: 0,
        failures: 0,
        lastError: '',
      });
    }

    const record = this.records.get(key)!;
    record.totalCalls++;

    if (success) {
      record.failures = 0;  // 同一工具+参数成功时只清零该工具的错误计数
    } else {
      record.failures++;
      record.lastError = error || '未知错误';
    }
  }

  /** 检查是否应触发熔断 */
  shouldCircuitBreak(toolName: string, params: unknown): { break: boolean; reason?: string } {
    const key = this.hashKey(toolName, params);
    const record = this.records.get(key);

    if (record && record.failures >= this.MAX_RETRIES_PER_KEY) {
      return {
        break: true,
        reason: `该操作已连续失败 ${record.failures} 次: ${record.lastError}。请检查配置或换用其他方式。`,
      };
    }

    return { break: false };
  }

  /** 清除指定工具的跟踪记录 */
  clear(toolName: string, params: unknown): void {
    const key = this.hashKey(toolName, params);
    this.records.delete(key);
  }

  /** 重置所有跟踪 */
  reset(): void {
    this.records.clear();
  }

  private hashKey(toolName: string, params: unknown): string {
    const paramsStr = JSON.stringify(params ?? {}, Object.keys(params ?? {}).sort());
    return `${toolName}:${simpleHash(paramsStr)}`;
  }
}

// 简单哈希函数（不引入外部依赖）
function simpleHash(str: string): string {
  let hash = 0;
  for (let i = 0; i < str.length; i++) {
    const char = str.charCodeAt(i);
    hash = ((hash << 5) - hash) + char;
    hash |= 0;
  }
  return Math.abs(hash).toString(36);
}
```

```typescript
for (const toolCall of toolCalls) {
  // 熔断检查
  const circuitCheck = this.queryGuard.shouldCircuitBreak(toolCall.name, toolCall.params);
  if (circuitCheck.break) {
    // 返回熔断提示作为 tool result，让 Agent 读到来停止重试
    results.push({

    toolCall.params,

    result.error
  );

}
```
