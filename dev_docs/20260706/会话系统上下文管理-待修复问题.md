# 会话系统上下文管理 — 待修复问题

> **日期**：2026-07-06
> **来源**：10轮以上对话 / 上下文压缩后 AI "失忆"问题根因分析
> **涉及模块**：`ChatManager`、`QueryEngine`、`CompactService`、`ContextCompressor`

---

## 问题现象

10轮以上对话或在发生上下文压缩后，AI 忘记最新对话内容，只记得第一轮的任务。行为完全倒置——应该记住最新内容、淡忘旧内容，实际却变成了记住旧内容、遗忘新内容。

---

## 根因列表（共 4 项）

---

### BUG-01 压缩结果 `messagesToKeep` 从未被消费

| 属性 | 值 |
|------|-----|
| **严重度** | HIGH |
| **类型** | 架构缺陷 — 数据流断裂 |
| **影响** | 压缩后 `session.messages` 未被裁剪，旧消息持续累积，压缩形同虚设 |

**涉及文件**：
- [CompactService.ts](file:///E:/PY/CODES/PY_APP/app/src/services/compact/CompactService.ts#L278-L321) — `compactConversation()` 正确返回 `messagesToKeep`，但下游无人消费
- [QueryEngine.ts](file:///E:/PY/CODES/PY_APP/app/src/query/QueryEngine.ts#L1280-L1298) — `performLightCompact()` 只提取 `summaryMessages`，丢弃 `messagesToKeep`
- [AutoCompactService.ts](file:///E:/PY/CODES/PY_APP/app/src/services/compact/AutoCompactService.ts#L70-L130) — `performAutoCompact()` 只传递 `summaryMessages` / `boundaryMarker`
- [CompactOrchestrator.ts](file:///E:/PY/CODES/PY_APP/app/src/services/compact/CompactOrchestrator.ts#L125-L256) — `compact()` 只看 token 前后变化，不裁剪消息

**详细描述**：

```
压缩流程：
  QueryEngine.checkAndPerformCompact()
    → performLightCompact / performMediumCompact / performDeepCompact
      → CompactService.compactConversation() / partialCompactConversation()
        → 返回 CompactionResult {
            summaryMessages,    ← 仅此字段被使用
            messagesToKeep,     ← 从未被消费！
            boundaryMarker,
            ...
          }
```

在 [CompactService.ts L306-L308](file:///E:/PY/CODES/PY_APP/app/src/services/compact/CompactService.ts#L306)：
```typescript
const messagesToKeep = messages.slice(-messagesCountToKeep).map((m) => m.id);
```

`messagesToKeep` 正确包含了应保留的消息 ID（最近 N 条），但整个调用链中无人使用该字段裁剪 `session.messages`。

**后果**：压缩生成了摘要（存为 artifacts），但 `session.messages` 数组保持原样。下一次 `sendMessage()` 时，`session.messages` 仍包含全部旧消息。

**修复方向**：在压缩完成后，将 `messagesToKeep` 应用到 `session.messages`，真正裁剪消息列表。关键代码位置在 QueryEngine 的 compact 方法返回后。

### BUG-02 QueryEngine 压缩与 ChatManager 截断是两条独立且不协调的路径

| 属性 | 值 |
|------|-----|
| **严重度** | HIGH |
| **类型** | 架构缺陷 — 双轨制 |
| **影响** | 两次压缩独立运行，结果不协调，QueryEngine 的压缩产物不传递给 ChatManager |

**涉及文件**：
- [QueryEngine.ts](file:///E:/PY/CODES/PY_APP/app/src/query/QueryEngine.ts#L1184-L1256) — `checkAndPerformCompact()` 压缩入口（QueryEngine 路径）
- [ChatManager.ts](file:///E:/PY/CODES/PY_APP/app/src/chat/ChatManager.ts#L1032-L1194) — `_truncateApiMessages()` 截断入口（ChatManager 路径）

**详细描述**：

存在两套独立的上下文管理机制，分别在不同时机触发，使用不同的压缩方式，且不共享结果：

| | QueryEngine 路径 | ChatManager 路径 |
|---|---|---|
| 触发时机 | TAORLoop 每轮检查 token 预算 | 每次 `sendMessage()` 发送前 |
| 入口函数 | `checkAndPerformCompact()` | `_truncateApiMessages()` |
| 压缩方式 | AI 摘要 + 消息分组边界检测 | AI 语义压缩（ContextCompressor）→ 降级截断 |
| 修改对象 | 生成 artifacts（不修改消息列表） | **原地修改 apiMessages** |
| 配置 | 3 级压缩（60% / 75% / 90% token 使用率） | `recentMessageCount=6`, `maxTokens=128000` |

**数据流冲突**：

1. QueryEngine 压缩完成 → artifacts 存储 → **session.messages 未变**
2. 下一次 ChatManager.sendMessage() → 从 `session.messages` 读取**完整消息列表**
3. ChatManager._truncateApiMessages() 再次独立执行压缩/截断
4. QueryEngine 的压缩产物（摘要、关键信息）被忽略

**修复方向**：统一压缩入口。两种方案：
- A) 关闭 `_truncateApiMessages` 中的 ContextCompressor，让它仅做兜底截断，主要压缩逻辑由 QueryEngine 完成
- B) QueryEngine 压缩后直接修改 `session.messages`，ChatManager 的 `_truncateApiMessages` 仅做安全兜底

### BUG-03 ContextCompressor 仅保留最近 6 条消息，摘要质量不可控

| 属性 | 值 |
|------|-----|
| **严重度** | MEDIUM |
| **类型** | 配置缺陷 — 固定值不合理 |
| **影响** | 工具调用密集场景下仅覆盖 1~2 轮对话，摘要过度强调首轮任务 |

**涉及文件**：
- [ContextCompressor.ts](file:///E:/PY/CODES/PY_APP/app/src/agent/ContextCompressor.ts#L34-L43) — `DEFAULT_COMPRESSION_CONFIG`
- [ContextCompressor.ts](file:///E:/PY/CODES/PY_APP/app/src/agent/ContextCompressor.ts#L165-L194) — `takeRecent()` 取最近消息
- [ContextCompressor.ts](file:///E:/PY/CODES/PY_APP/app/src/agent/ContextCompressor.ts#L201-L213) — `getCompressibleMessages()` 确定压缩范围

**详细描述**：

```typescript
const DEFAULT_COMPRESSION_CONFIG: ContextCompressionConfig = {
  recentMessageCount: 6,  // ← 固定值，不随消息总数变化
  maxTokens: 128000,
  triggerRatio: 0.8,
};
```

在工具调用密集的对话中，每轮可能产生 user + assistant + tool×N（N≥3），**6 条消息仅覆盖 1~2 轮对话**。其余所有历史被压缩成一条 AI 摘要。

压缩后结构：
```
[systemMessages..., summaryMessage, ...recentMessages(最近6条)]
```

**问题**：
- 绝对数量而非比例：100 条消息保留 6 条（6%），300 条消息也保留 6 条（2%），比例失衡
- AI 摘要不可控：如果摘要过度强调第一轮任务描述，模型行为退化为"只做第一轮的活"
- 压缩 prompt（[ContextCompressor.ts L37-L38](file:///E:/PY/CODES/PY_APP/app/src/agent/ContextCompressor.ts#L37)）未明确要求保留"当前进展状态"

**修复方向**：
- `recentMessageCount` 从固定值改为按比例动态计算（如 `Math.max(6, Math.floor(total * 0.3))`）
- 改进压缩 prompt，增加"必须保留当前进展状态和最新决策"的约束

### BUG-04 QueryEngine 工具循环中重复发送相同 user 消息

| 属性 | 值 |
|------|-----|
| **严重度** | MEDIUM |
| **类型** | 逻辑缺陷 — 重复消息累积 |
| **影响** | 会话中累积内容相同但 ID 不同的 user 消息，模型可能将重复指令解释为"重新开始" |

**涉及文件**：
- [QueryEngine.ts](file:///E:/PY/CODES/PY_APP/app/src/query/QueryEngine.ts#L641-L658) — 主循环调用 `callAPI(prompt, sessionId)`
- [QueryEngine.ts](file:///E:/PY/CODES/PY_APP/app/src/query/QueryEngine.ts#L805-L832) — `callAPI()` 调用 `chatManager.sendMessage(prompt, {sessionId})`
- [ChatManager.ts](file:///E:/PY/CODES/PY_APP/app/src/chat/ChatManager.ts#L1444-L1450) — `sendMessage()` 创建新的 user 消息并追加到 session

**详细描述**：

在 [QueryEngine.ts L641-L658](file:///E:/PY/CODES/PY_APP/app/src/query/QueryEngine.ts#L641)：
```typescript
while (iteration < maxIterations) {
    const response = await this.callAPI(prompt, sessionId || '');
    // ↑ 每次迭代用同一个 prompt 调用 sendMessage()
}
```

`sendMessage()` 每次都会创建新的 user 消息（[ChatManager.ts L1444-L1450](file:///E:/PY/CODES/PY_APP/app/src/chat/ChatManager.ts#L1444)）：
```typescript
const userMessage = this.messageService.createUserMessage(content, { sessionId });
this._addAndPersistMessage(session.id, userMessage);
```

**结果**：当 LLM 在第 N 次迭代中看到又一个与自己上一轮输出内容相同（指 user 消息内容）的指令，而它在第 N-1 次已经执行过部分任务，模型可能误解"需要重新开始"。

示例（3 次工具迭代后 session.messages）：
```
user: "请帮我创建一个 React 组件"       ← 第1次 sendMessage
assistant: "好的，我先检查项目结构..."    ← LLM 响应
tool: [read_file 结果]                 ← 工具执行

user: "请帮我创建一个 React 组件"       ← 第2次 sendMessage（相同内容！）
assistant: "我先创建组件文件..."         ← LLM 响应（可能重新开始）
tool: [write_file 结果]                ← 工具执行

user: "请帮我创建一个 React 组件"       ← 第3次 sendMessage（相同内容！）
assistant: "我需要确认组件需求..."       ← LLM 可能又从头开始
```

**修复方向**：在工具循环中，后续迭代应使用 `tool_result` 角色消息或系统指令消息，而非重复创建相同内容的 user 消息。或者，如果必须使用 user 消息，内容应体现"继续执行"而非"重新开始"。

### BUG-05 多层字符截断叠加，损坏工具结果中的结构化数据（文件路径、ID、URL）

| 属性 | 值 |
|------|-----|
| **严重度** | HIGH |
| **类型** | 架构缺陷 — 截断策略无内容感知 |
| **影响** | 文件路径、工具调用 ID、URL 等结构化数据被从中切断，Agent 凭残缺信息"猜测"完整路径 → 反复出错 → 死循环 |
| **发现来源** | 2026-07-06 图片生成测试会话日志 `logs/chat-export-1783338181095.md` |

**涉及文件**：
- [compact/index.ts](file:///E:/PY/CODES/PY_APP/app/src/agent/compact/index.ts#L239-L269) — `trim-tool-results` 策略：tool 消息 > 500 字符 → 截断到 200 字符
- [compact/index.ts](file:///E:/PY/CODES/PY_APP/app/src/agent/compact/index.ts#L204-L237) — `summarize-oldest` 策略：每条消息截断到 100 字符
- [ContextCompressor.ts](file:///E:/PY/CODES/PY_APP/app/src/agent/ContextCompressor.ts#L265-L283) — `fallbackSummary()`：每条消息截断到 150 字符
- [SlidingWindow.ts](file:///E:/PY/CODES/PY_APP/app/src/query/SlidingWindow.ts#L130-L136) — 摘要中每条消息截断到 100 字符
- [toolLimits.ts](file:///E:/PY/CODES/PY_APP/app/src/constants/toolLimits.ts#L48) — `TOOL_RESULT_PREVIEW_MAX_LENGTH = 500`

**详细描述**：

存在 **5 层独立的截断层**，每一层以字符数为单位粗暴切割内容：

| 截断层 | 触发条件 | 截断策略 |
|--------|---------|---------|
| L0 工具结果预览 | 始终 | 截断到 500 字符 |
| L1 trim-tool-results | tool 消息 > 500 字符 | 截断到 200 字符 + `[truncated]` |
| L2 summarize-oldest | token > 128000 | 每条消息保留 100 字符 |
| L3 ContextCompressor fallback | AI 摘要失败时 | 每条消息截断到 150 字符 |
| L4 SlidingWindow | 消息数 > 100 | 每条消息截断到 100 字符 |

这些截断是**字符级而非语义级**的。当工具返回：

```json
{"filePath": "E:\\PY\\CODES\\PY_APP\\app\\data\\pyapp\\media\\images\\f_mr94q1fy_9efa95cb_generated_1783336862151.png", ...}
```

经截断后变成：

```
E:\PY\CODES\PY_APP\app\data\pyapp\media\images\f_mr94q1f...
```

Agent 只能凭记忆补全路径 → 拼错 → 报错 → 重试 → 产生更多上下文 → 触发更深层截断 → 路径进一步退化。

**恶性循环**：

```
image_generate 成功 → 返回完整路径
  → L0 截断（500 字符）
  → 上下文超限 → L1 trim-tool-results（200 字符）
  → 路径损坏 → Agent 猜路径 → 拼错
  → 重试 → 更多上下文 → L2 summarize-oldest（100 字符）
  → 路径信息完全丢失 → Agent 只能盲猜
```

**修复方向**：
- 在截断策略中增加**内容感知**——识别 `filePath`、`localUrl`、`inputPath`、`url` 等关键字段，完整保留；只截断纯文本描述部分
- 或将关键路径字段在截断前提取为独立的元数据字段，不在 content 中截断

### BUG-06 `QueryGuard.recordSuccess()` 无条件清零，循环控制在"半成功"模式下失效

| 属性 | 值 |
|------|-----|
| **严重度** | HIGH |
| **类型** | 逻辑缺陷 — 错误计数策略过于粗糙 |
| **影响** | Agent 在"成功→失败→成功→失败"模式下永远不触发 abort，形成无限重试循环 |
| **发现来源** | 2026-07-06 图片生成测试会话日志 `logs/chat-export-1783338181095.md` |

**涉及文件**：
- [QueryGuard.ts](file:///E:/PY/CODES/PY_APP/app/src/utils/QueryGuard.ts#L71-L73) — `recordSuccess()` 在任何成功时清零 `consecutiveErrors`

**详细描述**：

```typescript
// QueryGuard.ts L71-73
recordSuccess(): void {
  this.consecutiveErrors = 0;  // ← 任意一次成功就清零，不管整体任务是否完成
}
```

在本次会话中的实际模式：

```
image_generate 成功 → recordSuccess() → consecutiveErrors = 0
image_analysis 失败 → recordError()    → consecutiveErrors = 1
image_generate 成功 → recordSuccess() → consecutiveErrors = 0  ← 清零！
image_analysis 失败 → recordError()    → consecutiveErrors = 1
... 永动循环
```

`maxConsecutiveErrors = 5`（[QueryGuard.ts L17](file:///E:/PY/CODES/PY_APP/app/src/utils/QueryGuard.ts#L17)）永远达不到，因为**每两次调用中就有一次成功**重置计数器。

**修复方向**：
- 方案 A：`recordSuccess()` 只在用户原始请求的所有步骤都完成时才清零（需要感知任务完成状态）
- 方案 B：改为**工具级错误跟踪**——同一工具名称 + 相同参数组合连续失败超过 N 次（如 3 次）时触发中止
- 方案 C：增加独立的"总工具调用次数硬上限"——单次用户请求触发超过 N 次工具调用时强制终止

### BUG-07 缺少同类工具/同参数重复调用熔断检测

| 属性 | 值 |
|------|-----|
| **严重度** | MEDIUM |
| **类型** | 功能缺失 — 无熔断机制 |
| **影响** | Agent 对同一文件路径反复调用 `image_analysis` 失败十余次，无任何机制终止或提示 |
| **发现来源** | 2026-07-06 图片生成测试会话日志 `logs/chat-export-1783338181095.md` |

**涉及文件**：
- [QueryGuard.ts](file:///E:/PY/CODES/PY_APP/app/src/utils/QueryGuard.ts) — 当前只跟踪连续错误数，不跟踪工具/参数重复
- [TAORLoop.ts](file:///E:/PY/CODES/PY_APP/app/src/query/TAORLoop.ts) — 循环控制应接入熔断检测

**详细描述**：

当前没有任何机制检测"Agent 对同一个工具、用相同参数反复调用但持续失败"的模式。

在本次会话中，Agent 对同一张图片的路径反复调用 `image_analysis` 十余次，每次报错 `Provider not found: google`——这是一个**确定性失败**（配置缺失，不是临时故障），重试多少次都不会成功。但系统没有任何检测逻辑。

**修复方向**：
- 在 `QueryGuard` 中增加 `ToolCallTracker`：
  - 跟踪每次工具调用的 `{ toolName, paramsHash }` 键值对
  - 同一键值对连续失败超过 3 次 → 触发熔断 → 输出明确提示："该操作已连续失败 3 次，原因：{error}，请检查配置或换用其他方式"
  - 熔断提示应与普通 tool result 格式一致，让 Agent 能"读懂"并停止重试
- 熔断应在 TAORLoop 的 `checkBudget()` 之后、下次迭代之前检查

### BUG-08 压缩摘要无任务边界标记，旧任务在摘要中压倒新任务

| 属性 | 值 |
|------|-----|
| **严重度** | **CRITICAL** |
| **类型** | 提示词缺陷 — 摘要缺少任务切换感知 |
| **影响** | 上下文压缩后，摘要中旧任务（占 90% 消息量）的权重压过新任务（仅 10%），导致 AI 退回到早已结束的旧任务，完全忘记当前正在进行的工作 |
| **发现来源** | 2026-07-06 会话日志 `logs/chat-export-1783357080293.md` |

**涉及文件**：
- [ContextCompressor.ts](file:///E:/PY/CODES/PY_APP/app/src/agent/ContextCompressor.ts#L37-L38) — `compressionPrompt`：未要求区分已完成任务和当前任务
- [compact/index.ts](file:///E:/PY/CODES/PY_APP/app/src/agent/compact/index.ts#L230-L232) — `summarize-oldest` 摘要：无"已完成"标记
- [ContextCompressor.ts](file:///E:/PY/CODES/PY_APP/app/src/agent/ContextCompressor.ts#L265-L283) — `fallbackSummary()`：无任务边界

**详细描述**：

当用户从 100+ 轮"生图"话题切换到"分析 ChatManager 拆分方案"时：

1. 上下文压缩触发 → 生成摘要
2. 压缩 prompt 要求"保留关键决策与用户需求"，但 90% 对话是生图，仅 10% 是新话题
3. 摘要中"生成旗袍美女图"的描述占主导，新话题"分析 ChatManager 拆分顺序"可能只有 1~2 条被保留
4. AI 读到摘要后，看到大量生图内容 + 末尾几句模糊的代码分析 → **倾向于回到摘要中"被强调"的生图任务**
5. 结果：00:52 AI 在分析 ChatManager 源码时突然"醒悟"说"等等，用户要我先生图！"

**根因**：
```
压缩 prompt 缺少以下关键指令：
  ❌ 检测话题切换 → 不知道生图和代码是两个独立任务
  ❌ 标注"已完成任务" → 摘要把已完成的生图当"当前任务"
  ❌ 明确优先级 → 最晚消息权重应高于摘要描述
```

**修复方向**：
- 修改压缩 prompt，增加：①识别任务/话题切换点 ②标记已结束任务 ③强调最近消息为当前活跃任务
- `summarize-oldest` 摘要头加前缀："⚠️ 以下为历史任务记录，当前任务见最近消息"
- `fallbackSummary` 同加前缀
