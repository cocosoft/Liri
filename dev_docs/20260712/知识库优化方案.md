## 1. 背景与代码层深度分析

### 1.1 当前架构现状

知识库系统位于 `app/src/knowledge/`，包含 **20+ 核心模块**，覆盖摄入→编译→索引→搜索→工具→质量的全流程。

### 1.2 代码层关键发现（逐文件审查）

通过逐文件审查代码，发现以下 `logs/app.md` 中未覆盖的深层问题：

#### 发现 A：SemanticStore 已完整实现持久化向量存储，但 KnowledgeRouter 完全不使用

这是**最严重的性能瓶颈**。

- [`knowledge/semantic/store.ts`](file:///e:/PY/CODES/PY_APP/app/src/knowledge/semantic/store.ts)（L110-261）：`SemanticStore` 已实现 JSONL 持久化的向量存储 + 余弦相似度搜索（`search()` 方法 L169-188），支持增量追加和全量加载
- [`knowledge/SemanticIndexUpdater.ts`](file:///e:/PY/CODES/PY_APP/app/src/knowledge/SemanticIndexUpdater.ts)（L71-182）：已监听 `knowledge:changed` 事件，在文件变更时自动分块→嵌入→增量追加到 SemanticStore
- [`knowledge/KnowledgeRouter.ts`](file:///e:/PY/CODES/PY_APP/app/src/knowledge/KnowledgeRouter.ts)（L413-451）**`semanticSearch()` 完全无视 SemanticStore**：每次语义搜索时逐文档调用 `embedmentManager.embedOne()` 实时生成嵌入向量，N 篇文档 = N 次 Embedding API 调用

> **影响**：10 篇文档的语义搜索需要 10+1 次 Embedding API 调用（耗时数秒），而使用 SemanticStore 只需 1 次查询嵌入 + 内存级矩阵运算（耗时 < 100ms）。

同样的问题也存在于 [`AutoRagService.semanticSearch()`](file:///e:/PY/CODES/PY_APP/app/src/knowledge/AutoRagService.ts)（L189-248），它是第三处重复实现逐文档实时嵌入的地方。

#### 发现 B：KnowledgeWriteTool 未连接 EventBus，写链路通知断裂

[`KnowledgeWriteTool.ts`](file:///e:/PY/CODES/PY_APP/app/src/knowledge/tools/KnowledgeWriteTool.ts)（L81）创建 `KnowledgeBaseWriter` 时：

```typescript
this.writer = new KnowledgeBaseWriter();  // ← 未传入 eventBus
```

而 [`KnowledgeBaseWriter.writeEntry()`](file:///e:/PY/CODES/PY_APP/app/src/knowledge/KnowledgeBaseWriter.ts)（L101-104）依赖 `eventBus` 发布 `knowledge:changed` 事件：

```typescript
this.eventBus?.publish('knowledge:changed', { action, filePath });
```

**结果**：通过 AI 工具写入知识时，`knowledge:changed` 事件**永不触发**，导致 `SemanticIndexUpdater` 无法增量索引、`IndexManager` 无法刷新 `index.md`。

#### 发现 C：IndexManager.listPages() 不递归，index.md 内容不完整

[`IndexManager.listPages()`](file:///e:/PY/CODES/PY_APP/app/src/knowledge/IndexManager.ts)（L347-362）只扫描知识库根目录平层 `.md` 文件：

```typescript
const entries = await readdir(this.knowledgeRoot);
return entries.filter(e => e.endsWith('.md') && e !== 'index.md' && ...).sort();
```

而 `KnowledgeCompiler.generateManyPages()`（L487-505）会将 Wiki 页面按 `kind` 分类写入子目录（`summary/`、`concept/`、`entity/`）。这些子目录中的页面**不出现在 index.md 中**。

对比 [`KnowledgeLinter.collectDocFiles()`](file:///e:/PY/CODES/PY_APP/app/src/knowledge/KnowledgeLinter.ts)（L162-183）已正确实现递归扫描。

#### 发现 D：三份重复的余弦相似度实现

| 文件 | 位置 |
|------|------|
| `KnowledgeRouter.ts` | L393-405 |
| `AutoRagService.ts` | L253-268 |
| `semantic/store.ts` | L249-261 |

三处实现逻辑完全相同，违反编码铁律 [CS01](file:///e:/PY/CODES/PY_APP/.trae/rules/coding-standards.md)（归一化检查）。

#### 发现 E：两份重复的停用词列表

| 文件 | 位置 |
|------|------|
| `KnowledgeRouter.ts` | L51-164（`COMMON_STOP_WORDS`） |
| `AutoRagService.ts` | L357-409（`extractKeywords` 内 `stopWords`） |

两个停用词集有大量重叠但不完全一致，各有遗漏。

#### 发现 F：KnowledgeGraph 孤儿边清理从未触发

[`KnowledgeGraph.cleanupOrphans()`](file:///e:/PY/CODES/PY_APP/app/src/knowledge/graph/KnowledgeGraph.ts)（L546-609）方法已完整实现，但在整个代码库中**没有任何调用点**。当知识文档被删除时，关联的图边成为永久悬挂数据。

#### 发现 G：KnowledgeRouter 不监听 knowledge:changed，内存索引过时

`KnowledgeRouter.buildIndex()`（L220-237）只在启动和显式调用时重建内存中的 `this.docs` 数组。当 `KnowledgeBaseWriter` 写入新文档后（且假设 EventBus 修复），Router 的内存索引不会自动刷新，直到下一次 `buildIndex()` 调用。

## 3. P0-1 — 语义搜索接入 SemanticStore（最高优先级）

### 3.1 问题分析

**现状**：`KnowledgeRouter.semanticSearch()` 每次搜索时对所有文档逐条调用 `embeddingManager.embedOne()`（[L426-429](file:///e:/PY/CODES/PY_APP/app/src/knowledge/KnowledgeRouter.ts#L426-L429)）：

```typescript
for (const doc of this.docs) {
  const text = `${doc.title}\n${doc.content}`.substring(0, 8000);
  const docVec = await this.embeddingManager.embedOne(text);  // ← N 次 API 调用
  // ...
}
```

**磁盘上已有**：`SemanticStore`（[store.ts](file:///e:/PY/CODES/PY_APP/app/src/knowledge/semantic/store.ts)）已持久化所有文档的嵌入向量，`SemanticIndexUpdater`（[SemanticIndexUpdater.ts](file:///e:/PY/CODES/PY_APP/app/src/knowledge/SemanticIndexUpdater.ts)）已在增量维护这些向量。

### 3.2 优化方案

**让 `KnowledgeRouter.semanticSearch()` 直接调用 `SemanticStore.search()` 而非重新嵌入**：

```
当前:
  semanticSearch(query)
    → embedOne(query)                     ← 1 次 API 调用
    → for each doc: embedOne(docContent)  ← N 次 API 调用
    → cosineSimilarity                    ← N 次本地计算

优化后:
  semanticSearch(query)
    → embedOne(query)                     ← 1 次 API 调用
    → store.search(queryVec, topK, minScore)  ← 仅本地向量运算
```

**具体变更**（[`KnowledgeRouter.ts`](file:///e:/PY/CODES/PY_APP/app/src/knowledge/KnowledgeRouter.ts)）：

1. 构造函数接受可选的 `SemanticStore` 实例：

```typescript
constructor(
  providers: FileDocsProvider | FileDocsProvider[],
  embeddingManager?: EmbeddingManager,
  knownUsernames?: string[],
  hybridConfig?: HybridConfig,
  semanticStore?: SemanticStore  // ← 新增
)
```

2. `semanticSearch()` 方法改为调用 `SemanticStore.search()`：

```typescript
private async semanticSearch(query: string, maxResults: number): Promise<KnowledgeRoute[]> {
  if (!this.semanticStore || this.semanticStore.empty) {
    // 回退：SemanticStore 不可用时降级为空语义结果
    return [];
  }

  this.embeddingManager.initialize();
  const queryVec = await this.embeddingManager.embedOne(query);
  if (queryVec.length === 0) return [];

  const hits = this.semanticStore.search(
    new Float32Array(queryVec),
    maxResults,
    this.hybridConfig.semanticThreshold
  );

  return hits.map(hit => ({
    docPath: hit.entry.path,
    title: hit.entry.path.replace(/\.md$/, ''),
    score: Math.round(hit.score * 100) / 100,
    category: '',
    snippet: hit.entry.text.slice(0, 120),
    matchType: 'semantic' as const,
    isKnowledgeDoc: true,
  }));
}
```

3. **降级策略**（符合 [CS03](file:///e:/PY/CODES/PY_APP/.trae/rules/coding-standards.md)）：`SemanticStore` 不可用（空或未初始化）时，语义通道返回空数组，搜索自动降级为纯关键词搜索（已有 `KnowledgeRouter.search()` L538-543 的 catch 兜底逻辑）。

### 3.3 影响范围

| 文件 | 变更 |
|------|------|
| `knowledge/KnowledgeRouter.ts` | `semanticSearch()` 改为读 SemanticStore；新增 `semanticStore` 字段 |
| `knowledge/KnowledgeRouter.ts` | `keywordSearch()` 保留不变 |
| 初始化代码（调用 `new KnowledgeRouter()` 处） | 注入 `SemanticStore` 实例 |

### 3.4 验收标准

- [ ] 100 篇文档的语义搜索从 N+1 次 API 调用降为 1 次 API 调用
- [ ] 搜索结果质量不低于实时嵌入版本（使用现有语义搜索的结果集做对比）
- [ ] `SemanticStore` 为空时语义通道返回空，不报错
- [ ] `KnowledgeRouter` 已有 catch 逻辑（L538-543）确保降级到纯关键词搜索

### 3.5 风险提示：SemanticStore 路径一致性

`KnowledgeRouter` 将读取 `SemanticStore` 的 JSONL 持久化文件，而 `SemanticIndexUpdater` 负责写入同一文件。**如果两者配置的 `indexDir` 路径不一致，会出现"写了但搜不到"的问题。**

实施时必须验证：

```typescript
// 两处必须指向同一 indexDir
// SemanticIndexUpdater 的 options.indexDir（默认 ~/.pyapp/data/semantic-index/）
// SemanticStore 的 constructor(this.indexDir, ...)
// → 统一从 resolveDataSubDir('semantic-index') 获取
```

**建议**：在 `KnowledgeRouter` 构造函数中接受 `SemanticStore` 实例（而非自行创建），确保与 `SemanticIndexUpdater` 共享同一个 store 引用，从架构层面杜绝路径不一致。这也是 3.2 节优化方案中推荐的注入方式。

## 5. P0-3 — 倒排索引 + 增量更新

> **前置依赖**：[P0-2 EventBus 贯通](#4-p0-2--eventbus-贯通写链路) — EventBus 链路必须先修通，倒排索引的增量刷新（`knowledge:changed` 事件驱动）才能生效。

### 5.1 问题分析

**当前代码** ([`KnowledgeDeleteTool.ts`](file:///e:/PY/CODES/PY_APP/app/src/knowledge/tools/KnowledgeDeleteTool.ts) L108-115)：

```typescript
const docs = await knowledgeDocsProvider.buildIndex();
const doc = docs.find(
  (d) => d.title.toLowerCase() === lowerTitle || ...
);
```

`buildIndex()` 每次调用都从文件系统完整重建索引，`Array.find()` 做 O(n) 全量遍历。同样的问题存在于 `KnowledgeRouter.buildIndex()`（[L220-237](file:///e:/PY/CODES/PY_APP/app/src/knowledge/KnowledgeRouter.ts#L220-L237)）。

**额外发现**（[发现 G](#发现-gknowledgerouter-不监听-knowledgechanged内存索引过时)）：`KnowledgeRouter` 不监听 `knowledge:changed` 事件，内存索引在写入后过时。**P0-2 修复后，EventBus 链路打通，Router 才能通过事件驱动自动刷新索引。**

### 6.2 优化方案

**在 `KnowledgeRouter` 中引入内存级 titleIndex 和 tokenIndex**：

```
优化后 KnowledgeRouter 内部结构:
  this.docs: WeightedDoc[]                              ← 保留（全量列表）
  this.titleIndex: Map<lowerTitle, WeightedDoc>         ← 新增 O(1) 标题查找
  this.tokenIndex: Map<token, Set<docIdx>>              ← 新增 O(k) 关键词查找
```

**新增方法**：

```typescript
findByTitle(title: string): WeightedDoc | undefined;  // O(1)
addToIndex(doc: WeightedDoc): void;                    // 增量添加
removeFromIndex(docPath: string): void;                // 增量移除
refreshIndex(): Promise<void>;                         // 重建全量（启动时一次）
```

**事件驱动刷新**：`KnowledgeRouter` 构造函数接受 `EventBus`，监听 `knowledge:changed` 事件自动调用 `addToIndex` / `removeFromIndex`（依赖 P0-2 完成后 EventBus 链路通畅）。

### 6.3 影响范围

| 文件 | 变更 |
|------|------|
| `knowledge/KnowledgeRouter.ts` | 新增 `titleIndex`、`tokenIndex`、增量方法、EventBus 监听 |
| `knowledge/tools/KnowledgeDeleteTool.ts` | `buildIndex().find()` → `router.findByTitle()` |
| `knowledge/KnowledgeBaseWriter.ts` | 写入后通过 EventBus 自动触发（P0-2 修复后生效） |

### 5.4 验收标准

- [ ] `KnowledgeDeleteTool` 删除不再调用 `buildIndex()`
- [ ] 1000 篇文档场景下 `findByTitle` 耗时 < 1ms
- [ ] 写入新文档后 Router 索引自动更新（EventBus 驱动，**依赖 P0-2 完成**）
- [ ] `keywordSearch()` 使用 `tokenIndex` 交集查找而非全量遍历

## 4. P0-2 — EventBus 贯通写链路

### 4.1 问题分析

## 7. P1-1 — IndexManager 递归扫描修复

### 7.1 问题分析

见 [发现 C](#发现-cindexmanagerlistpages-不递归indexmd-内容不完整)。

[`IndexManager.listPages()`](file:///e:/PY/CODES/PY_APP/app/src/knowledge/IndexManager.ts)（L347-362）只扫描平层，`KnowledgeCompiler` 写入子目录的页面（`summary/`、`concept/`、`entity/`）在 `index.md` 中不可见。

### 7.2 优化方案

将 `listPages()` 改为递归扫描（参照 `KnowledgeLinter.collectDocFiles()` L162-183 的实现）：

```typescript
async listPages(): Promise<string[]> {
  const files: string[] = [];
  await this.walkDir(this.knowledgeRoot, files);
  return files
    .map(f => relative(this.knowledgeRoot, f))
    .filter(f => f.endsWith('.md') && !f.includes('index.md') && !f.includes('log.md'))
    .sort();
}

private async walkDir(dir: string, files: string[]): Promise<void> {
  const entries = await readdir(dir, { withFileTypes: true });
  for (const e of entries) {
    if (e.name.startsWith('.')) continue;
    const full = join(dir, e.name);
    if (e.isDirectory()) await this.walkDir(full, files);
    else if (e.isFile()) files.push(full);
  }
}
```

### 7.3 验收标准

- [ ] `index.md` 包含子目录中的 Wiki 页面
- [ ] 递归扫描不包含 `.` 开头的隐藏目录
- [ ] 递归扫描不包含 `index.md` 和 `log.md` 自身
