## 一、现状分析

### 1.1 架构总览

当前上下文管理模块分为 4 层：

```
src/context/                        → 基础设施层（Store / Isolator / Injector / Sharing）
src/query/context/                  → 压缩引擎层（Default / Hybrid / Truncator / Summarizer）
src/agent/ContextCompressor.ts      → AI 驱动压缩层
native/src/context.rs               → Rust FFI 原生压缩层
```

| 层级 | 目录 | 核心组件 |
|------|------|---------|
| 基础设施层 | `src/context/` | ContextStore, ContextManager, ContextInjector, AsyncContextStorage, ContextIsolator, ContextSharingManager, LifecycleManager, ContextCacheService, ContextBuilder |
| 压缩引擎层 | `src/query/context/` | DefaultContextEngine, HybridEngine, TruncatorEngine, SummarizerEngine, ContextTracker |
| AI 压缩层 | `src/agent/ContextCompressor.ts` | AI 驱动的智能摘要生成 |
| Rust FFI 层 | `native/src/context.rs` | compress_messages_impl, estimate_message_tokens |

### 1.2 核心数据流

```
用户输入 → ContextBuilder 构建上下文
  → ContextStore 存储 (TTL + LRU)
  → ContextInjector 注入目标对象
  → 压缩引擎 (Default/Hybrid/Truncator/Summarizer) 控制 token 预算
  → ContextCompressor (AI) 生成摘要
  → Rust FFI 原生压缩 (drop策略)
  → LifecycleManager 生命周期管理
```

## 二、问题清单与优化方案

### 🔴 P0 — 严重问题（影响正确性/可靠性 + 关键能力缺口）

#### 2.1 AsyncContextStorage.clearStore() 语义错误

**问题**：

```ts
// 当前实现 — 语义不对
clearStore(): void {
  this.storage.run({}, () => {});  // 新建空 store 但不影响已有异步上下文
}
```

`AsyncLocalStorage.run()` 创建一个新作用域下的空 store，但不影响当前调用链中已存在的 store。同一 async 链中后续 `getStore()` 拿到的仍是旧数据。

**根因**：`AsyncLocalStorage` 没有真正的 clear API。

**方案**：

1. **短期**（推荐）：废弃 `clearStore()`，改用 `enterWith({})` 覆盖当前 store（Node.js 20+）。
2. **长期**：记录初始化时的空 store 引用，在需要清理时重新进入，或使用 Symbol 标记需重置的 store 实例。

```ts
// 修复方案
resetStore(): void {
  this.storage.enterWith({});  // Node.js 20+ 立即替换当前 store
}
```

**影响范围**：

- 影响文件：`src/context/AsyncContextStorage.ts`（1 文件）
- 调用方：需搜索所有 `clearStore()` 引用点，确认调用场景是否需要改为 `resetStore()`
- 风险：低（仅在明确需要清空 store 时调用，不会影响正常路径）

#### 2.2 Rust FFI CString 内存泄漏

**问题**：

```rust
CString::new(result).unwrap_or_default().into_raw()
```

`into_raw()` 将堆内存所有权转移给了调用方（Python/JS），但 crate 中**没有对应的 free 函数**暴露给调用方。每次调用都会泄漏一块堆内存。

**方案**：

在 `context.rs` 同模块中暴露释放函数：

```rust
/// 释放由 compress_messages 返回的字符串内存
/// 调用方必须在获取结果后调用此函数
#[no_mangle]
pub extern "C" fn py_free_string(ptr: *mut c_char) {
    if !ptr.is_null() {
        unsafe { let _ = CString::from_raw(ptr); }
    }
}
```

同时在文档/接口注释中明确调用契约。

**影响范围**：

- 影响文件：`native/src/context.rs`（新增 `py_free_string`）+ JS 侧 FFI 绑定
- 风险：低（新增函数，不改变现有行为）。JS 侧需使用 `FinalizationRegistry` 或手动调用释放

#### 2.3 LifecycleManager.destroyAll() 中途抛异常导致残留

**问题**：

```ts
// destroy() 找不到 entry 会 throw
destroy(id: string): void {
  const entry = this.entries.get(id);
  if (!entry) throw new AppError(...);
  // ...
}

// destroyAll() 用 Promise.all 并行，一个失败全挂
async destroyAll(): Promise<void> {
  const ids = Array.from(this.entries.keys());
  await Promise.all(ids.map(id => this.destroy(id)));
}
```

垃圾清理时一个损坏的 entry 会阻塞所有后续清理。

**方案**：

`destroy()` 中找不到 entry 改为 silent skip（非错误场景），或 `destroyAll()` 用 `Promise.allSettled` + 汇总错误。

```ts
destroy(id: string): void {
  const entry = this.entries.get(id);
  if (!entry) return;  // 已清理，静默跳过
  // ...
}

async destroyAll(): Promise<void> {
  const results = await Promise.allSettled(
    Array.from(this.entries.keys()).map(id => this.destroy(id))
  );
  const failures = results.filter(r => r.status === 'rejected');
  if (failures.length > 0) {
    logger.warn('destroyAll 部分失败', { count: failures.length });
  }
}
```

**影响范围**：

- 影响文件：`src/context/LifecycleManager.ts`（1 文件）
- 风险：低（仅改变异常处理方式，从 throw 变为 warn + partial 成功）

#### 2.4 [对标新增] 缺少分级压缩体系（对标 PilotDeck、cc_code）

**问题**：当前仅有一种压缩路径（AI Full Compaction），任何上下文溢出都直接触发重量级 LLM 摘要调用。参考项目中：

- **PilotDeck** 有三级体系：MicroCompact → Snip → Full，先做低成本操作再 escalation
- **cc_code** 有 MicroCompact（缓存编辑）+ SessionMemory + Full 三种策略
- **openclaw** 有 Preemptive / MemoryFlush / Full 三级

**方案**：

引入三级压缩体系（参考 PilotDeck 设计）：

```
Tier 1: MicroCompact — 将旧 tool_result 替换为占位符（零 LLM 调用，O(n) 复杂度）
  → 触发条件：TTL 过期（如 > 5min 的工具结果）或 token 使用 > 60%

Tier 2: Snip — 裁剪中间轮次，保留头部 2 轮 + 尾部 4 轮（零 LLM 调用）
  → 触发条件：MicroCompact 后仍超预算

Tier 3: Full Compaction — LLM 摘要（当前已有，需增强反抖动）
  → 触发条件：Snip 后仍超预算或 token 使用 > 80%
```

**新增文件**：

```
src/context/compaction/MicroCompactionEngine.ts   — Tier 1
src/context/compaction/SnipEngine.ts               — Tier 2
src/context/compaction/AutoCompactionPolicy.ts     — 触发策略（warn 80%, block 95%）
src/context/compaction/toolPairIntegrity.ts        — 工具配对完整性保护
```

**反抖动机制**（参考 hermes-agent）：连续 2 次 Full Compaction 各节省 < 10% 则跳过本次。

**对标适配说明**：

| 对标项 | 原值 | 适配调整 | 理由 |
|--------|------|---------|------|
| PilotDeck `warn/block` 阈值 | 80% / 95% | Phase 2 暂用 **85% / 92%**，Phase 3 根据实际数据调优 | 避免过于激进的压缩触发，需积累运行数据后校准 |
| PilotDeck Snip `head/tail` | 2 / 4 turns | 沿用 | 2+4 是通用安全值 |
| hermes-agent 反抖动 | 2 次各 < 10% | 沿用 | 平衡保护与响应 |
| PilotDeck MicroCompact TTL | 5 分钟 | Phase 2 暂用 5 分钟 | 可通过环境变量 `CONTEXT_MICRO_TTL_MS` 动态调整 |

**结构化日志**（每个 Tier 触发时输出）：

```ts
logger.info('Compaction triggered', { tier: 1, reason: 'TTL expired', beforeTokens: 75000 });
logger.info('Compaction triggered', { tier: 2, reason: 'budget exceeded', droppedRounds: 10 });
logger.info('Compaction triggered', { tier: 3, reason: 'snip insufficient', savingPercent: 62 });
```

#### 2.7 [对标新增] 实现持久化（对标 hermes-agent、PilotDeck）

> **原 2.11，由 P2 升级至 P0**。对标分析确认纯内存存储是所有项目中最薄弱的环节。

**问题**：`ContextStore` 纯内存存储，进程重启后全部丢失。无 `toJSON()` / `fromJSON()` 等序列化接口。参考项目全部有持久化：

- hermes-agent: SQLite + FTS5 全文搜索
- PilotDeck: JSONL transcript + `TranscriptEntry` 判别联合类型
- codex: JSONL `~/.codex/history.jsonl`

**方案**：

```ts
interface ContextPersistence {
  save(snapshot: ContextSnapshot): Promise<void>;
  load(): Promise<ContextSnapshot | null>;
}

// Phase 1: JSONL 文件存储（参考 PilotDeck TranscriptEntry）
// Phase 2: SQLite + FTS5（参考 hermes-agent）
```

`ContextStore` 增加 `serialize()` / `hydrate()` 方法，结合应用关闭/启动生命周期自动持久化。

**风险与注意事项**：

1. **数据完整性**：`Context` 接口当前用 `as unknown as Context` 绕过类型检查（见 2.12），反序列化时需增加 `ContextSnapshotSchemaVersion` 版本字段 + 结构验证，不能直接 `as unknown as Context`。
2. **循环引用**：`Context` 对象中可能存在 `ctx.parent → ctx` 等循环引用，JSON 序列化会抛异常。需评估并设计引用扁平化方案。
3. **I/O 性能**：ContextStore 是纯内存 LRU Map，JSONL 序列化 I/O 量取决于 store 大小。建议先做 1000 条 context 的序列化 benchmark 评估。
4. **Date/Map/Set 等非 JSON 原生类型**：需自定义 `replacer`/`reviver` 或在 `ContextSnapshot` 中统一序列化格式。

```ts
// 增强版持久化接口
interface ContextPersistence {
  readonly schemaVersion: number;
  save(snapshot: ContextSnapshot): Promise<void>;
  load(): Promise<ContextSnapshot | null>;
  validate(snapshot: ContextSnapshot): ValidationResult;
}

interface ContextSnapshot {
  schemaVersion: number;
  createdAt: string;  // ISO 8601
  entries: SerializedContextEntry[];
  metadata: { totalCount: number; storeConfig: StoreConfig };
}
```

#### 2.14 ContextInjector 的 `__context__` 模式

**问题**：

```ts
injectionTarget.__context__[context.type] = context;
```

对标发现：这是 7 个参考项目中**独此一家**的注入方式。所有其他项目均采用非侵入式注入（system prompt 内联 / 状态内置 / 注册表）。

**方案**：

改用 `WeakMap` 实现非侵入式注入：

```ts
const contextRegistry = new WeakMap<object, Map<string, Context>>();

export function inject(target: object, context: Context): void {
  let map = contextRegistry.get(target);
  if (!map) {
    map = new Map();
    contextRegistry.set(target, map);
  }
  map.set(context.type, context);
}

export function extract(target: object, type: string): Context | undefined {
  return contextRegistry.get(target)?.get(type);
}
```

优势：不污染目标对象、自动 GC（目标释放后 WeakMap 自动清空）、类型安全。

**风险评估：WeakMap 生命周期陷阱**：WeakMap 的 key 是对象引用。如果 `ContextInjector.inject()` 的 target 是短生命周期对象（如每次 HTTP 请求重建的上下文），WeakMap 会在 GC 时自动清除注入的 context，导致必现 bug。

**前置审计**：Phase 4 实施前，必须审计所有 `ContextInjector.inject()` 调用方，确认 target 对象生命周期：
- 长生命周期（agent 实例、session 对象）→ WeakMap 安全
- 短生命周期（临时请求对象）→ 改用 Map + 显式 `dispose()` 清理

**长期演进**：参考 codex 的 Context Fragment 注册表模式（20+ 类型安全片段）。

#### 2.23 [新增] Rust FFI 调用方生命周期封装

**问题**：2.2 暴露了 `py_free_string` 但未说明 JS 侧如何安全调用。CString 内存释放依赖调用方显式调用 free，如果遗漏则内存泄漏。

**方案**：

JS 侧使用 **RAII wrapper + 显式 dispose** 模式（`FinalizationRegistry` GC 回调不保证及时执行，不适合管理 Rust 堆内存）：

```ts
class RustString implements Disposable {
  private ptr: number;
  private freed = false;

  constructor(ptr: number) { this.ptr = ptr; }

  toString(): string { return native.readCString(this.ptr); }

  free(): void {
    if (!this.freed) { native.py_free_string(this.ptr); this.freed = true; }
  }

  [Symbol.dispose](): void { this.free(); }  // TS 5.2+ `using` 语法
}

// 使用 `using` 关键字确保确定性释放
function processNativeResult(ptr: number): string {
  using rustStr = new RustString(ptr);
  return rustStr.toString();  // 离开作用域自动调用 free()
}
```

#### 2.24 [新增] Rust FFI 降级与熔断

**问题**：Rust FFI panic（如 `compress_messages_impl` 处理异常输入）会导致整个 Node.js 进程 crash（FFI panic → abort）。当前无任何保护机制。

**方案**：

1. Rust 侧：所有 FFI 导出函数用 `catch_unwind` 包装，panic 转 ErrorCode 返回
2. JS 侧：调用检查返回码，native 不可用时自动降级到 TypeScript fallback
3. 降级行为需在日志中记录（避免静默降级）

```rust
// native/src/context.rs
#[no_mangle]
pub extern "C" fn compress_messages_safe(
    messages_json: *const c_char,
    strategy: *const c_char,
) -> *mut c_char {
    let result = std::panic::catch_unwind(|| {
        compress_messages_impl(messages_json, strategy)
    });
    match result {
        Ok(json) => CString::new(json).unwrap_or_default().into_raw(),
        Err(_) => CString::new(r#"{"error":"native_panic"}"#).unwrap_or_default().into_raw(),
    }
}
```

```ts
// JS 侧降级
async function compressMessages(messages: Message[], strategy: string): Promise<Message[]> {
  try {
    const result = native.compress_messages_safe(JSON.stringify(messages), strategy);
    const parsed = JSON.parse(result);
    if (parsed.error) {
      logger.warn('FFI compress failed, falling back to TypeScript', { error: parsed.error });
      return typescriptCompress(messages, strategy);
    }
    return parsed;
  } catch {
    logger.error('FFI call crashed, falling back to TypeScript');
    return typescriptCompress(messages, strategy);
  }
}
```

#### 2.28 [对标新增] 定价管理增强（对标 cc-switch + hermes-agent）

**问题**：

1. **无 cost_multiplier 倍率系统**：cc-switch 的每个 Provider 可设置自定义成本倍率（基础成本 × 倍率 = 最终成本）
2. **定价更新不自动回填历史**：cc-switch 更新价格后自动重新计算所有关联请求的成本
3. **定价无法 UI 编辑**：当前只能修改代码或 YAML

**方案**：

```ts
// 倍率系统
interface ProviderPricingOverride {
  providerId: string;
  costMultiplier: number;  // 默认 1.0
  pricingSource: 'model_table' | 'provider_response';
}

// 定价更新时自动回填历史
async function updateModelPricing(modelId: string, newPricing: ModelPricing): Promise<void> {
  await db.update('model_pricing', { modelId }, newPricing);
  await db.execute(`
    UPDATE proxy_request_logs 
    SET cost = recalc_cost(usage, newPricing) 
    WHERE model = ?
  `, [modelId]);
}
```
