# 项目管理的自然化设计方案

> 核心命题：怎么管项目，更像人类用计算机，而不是像项目经理用 Jira？

---
## 〇、概念澄清：现有代码中的命名混乱

> 在开始方案之前，必须先理清当前代码中已有的几个易混淆概念。

### 当前存在的 "XXXspace" 和 "XXXtree"

| 名称 | 所在位置 | 实际含义 | 备注 |
|------|---------|---------|------|
| **Worktree** | `client/src/stores/root-store/types.ts` | 前端逻辑 UI 模型：环境 + 任务 + 会话 + 布局 | 历史名称 |
| **Workspace** | 同上，第 103 行 `type Workspace = Worktree` | **与 Worktree 完全相同的类型**，只是别名 | 新规范推荐名称 |
| **物理工作空间** | `app/src/workspaces/` | `~/workspace/` 下的文件系统目录，附带 `.workspace.json` | 与前端 Worktree **不同** |
| **AgentWorkspace** | `app/src/agent/sandbox/index.ts` | 代理执行的沙盒目录 | 第三个叫 "workspace" 的东西 |
| **git worktree** | `app/src/workspaces/WorkspaceGit.ts` | 真正的 `git worktree add/remove` 命令，用于会话隔离 | 是具体功能，不是抽象概念 |
| **cwd** | 各处均有 | 传统的"当前工作目录"，所有文件操作的起点 | 相对清晰，不混淆 |
| **Project** | `client/src/types/work.ts` / `app/src/workspace/types.ts` | 项目实体（name、status、phase、workItemIds...） | 已有数据模型 |

### 同一个 ID 的两种写法

```
Session.workspaceId  ←──同一個值──→  SessionRecord.worktreeId
                     (映射来源: sessionSlice.ts:265)
```

二者指向的是前端的 `Worktree` / `Workspace`（那个"环境+任务+会话+布局"的 UI 模型），**不是**物理目录、不是 Agent 沙盒、不是 git worktree。

### 本方案中的 "projectId" 是什么？

本方案在 `session.metadata` 中新增 `projectId` 字段，**不等于**现有的 `workspaceId`：

| 字段 | 指向 | 语义 |
|------|------|------|
| `session.metadata.workspaceId`（现有） | 前端 Worktree / Workspace | "这个会话属于哪个工作空间"（UI 环境） |
| `session.metadata.projectId`（新增） | Project 实体 | "这个会话关联了哪个项目"（项目上下文） |

**关系**：一个 Project 通过 `project.workspaceId` 关联到一个 Worktree，一个 Worktree 可以有多个 Project。Session 可以同时有 `workspaceId`（UI 环境）和 `projectId`（项目上下文），二者不互斥。

### 命名规范（本方案及后续开发遵守）

| 概念 | 统一用名 | 禁止别名 |
|------|---------|---------|
| 前端 UI 环境模型 | **Workspace** | 不再新增 Worktree 引用 |
| Session 外键 | `workspaceId` | 不用 `worktreeId` |
| Git 隔离功能 | **git worktree** | 全小写，指具体 git 命令 |
| 当前工作目录 | **cwd** | 不变 |
| 项目实体 | **Project** / `projectId` | 不与 workspace 混用 |

**红线自查**：凡出现 `ProjectStore.get(...)` 的地方，入参必须是 `projectId`；出现 `workspaceId` 即视为错误。

### 统一行动计划（P3：命名收敛）

当前 `Worktree = Workspace`（别名）和 `worktreeId = workspaceId`（同一外键两个名字）是历史遗留，必须在本方案实施期间完成收敛：

```
前端（client/src/）：
  1. types.ts: 删除 `type Workspace = Worktree` 别名
  2. types.ts: 将 `Worktree` 接口重命名为 `Workspace`
  3. types.ts: `SessionRecord.worktreeId` → `workspaceId`
  4. types.ts: `WorkItem.worktreeId` → `workspaceId`
  5. 全局替换：所有 `.worktreeId` 引用 → `.workspaceId`
  6. 文件名: workspaceSlice.ts → 不变（已用 workspace）

后端（app/src/）：
  7. SessionMetadata.workspaceId → 不变（已用 workspace）
  8. WorkspaceGit.ts / WorktreeInfo → 保留（指 git worktree 功能，语义正确）

命名规范落地后：
  - "Worktree" 只出现在 git worktree 上下文中
  - 其他所有地方统一用 "Workspace" / "workspaceId"
```

| 改动 | 涉及文件 | 工作量 |
|------|---------|:--:|
| P3 命名收敛 | `client/src/stores/root-store/types.ts`, `client/src/types/`, 全局 `.worktreeId` 替换 | ~2h |

## 一、问题诊断

现代项目管理工具（Jira、Notion、Linear）的共同问题是**发明了一种人类本来不需要的交互模式**：

| 人类自然行为 | 软件强加的模式 |
|------------|-------------|
| 桌面上放文件夹 | 新建项目 → 填表单 → 选模板 |
| 跟人聊天说事 | 创建 Issue → 选类型 → 填字段 |
| 记个便签 | 状态机：待办 → 进行中 → 已完成 |
| 翻聊天记录找上次说的 | 学会用看板/甘特图/筛选器 |

**根因**：这些工具把人当成了"项目经理"，但实际上绝大多数人是"做事的人"。做事的人只需要三样东西：**说话、记住、找到**。

---

## 二、核心设计哲学

### 一句话模型

```
项目 = 文件夹（存东西）+ 聊天记录（过程）
```

用户不需要"管理"项目，只需要：
- **说话** → 事就办了
- **记住** → AI 自动记录
- **找到** → 搜索/最近

### 三条铁律

1. **项目是长出来的，不是建出来的**
   - 用户不需要主动"新建项目"，AI 在对话中发现复杂话题时自动创建
   - 创建过程零交互：用户可能都没注意到项目已经存在了

2. **项目不需要管理，只需要找到**
   - 人类不管理文件夹结构，人类搜索
   - 最近用的自然在上面，不用的自然沉底
   - 没有"归档"按钮——不活跃 = 自动休眠

3. **项目是会话的标签，不是会话的牢笼**
   - 一个会话可以关联到项目，但不是必须
   - 资料/成果可以跨项目引用
   - 切换项目不需要"离开"任何东西

## 三、用户体感对比

### 现在（软件味）

```
用户：打开侧栏 → 找到项目 → 点击 → 看到项目列表
  → 点"新建项目" → 起名字 → 确认
  → 在空白的项目页里开始聊天
  → 聊完了，项目留在列表里，永远不删
  → 一个月后有 20 个项目，分不清哪个是哪个
```

### 方案（自然感）

```
用户：打开应用 → 开始聊天
  → 聊着聊着，AI 说"这个话题我帮你整理了一下"
  → 侧栏多了一个项目（用户没主动创建）
  → 右侧面板自动出现：资料 / 成果 / 讨论记录
  → 以后再聊这个话题，AI 自动关联到这个项目
  → 一个月没碰的项目自动沉到底部
  → 想找就说一句话："上次聊那个记账的怎么样了？"
```

## 四、三个核心改动（按优先级）

### 改动 1：AI 自动建项目（P0）

**现状**：AI 在 system prompt 中被引导"建议建项目"，用户需要手动操作。

**改为**：AI 直接创建项目，不需要用户确认。

**触发条件**（满足任一）：
- 一轮对话中产生了 3 个以上不同的产出物（计划、代码、文档等）
- 用户表达了明确的长期目标（"我要做一个..."、"帮我规划..."）
- 同一话题连续聊了 5 轮以上（每轮重算 goal 指纹，变化超过阈值则重新计轮，避免话题滑移误触发）
- ImplicitEngineHook 检测到 goal + 至少 2 个 deliverables

**实现**：
```
ChatManager._finalizeStreamMessage()
  → ImplicitEngineHook.persist() 返回 { hasGoal, deliverables, goalSummary }
  → if hasGoal && deliverables.length >= 2 && !已有项目关联:
      → 跨会话去重检查：
          goalFingerprint = hash(normalizeKeywords(goalSummary))
          查询 ProjectStore 中相似度 > 0.8 的已有项目
          → 命中已有项目：关联当前 session 到已有项目，不新建
          → 未命中：继续新建流程
      → 自动调用 ProjectStore.create({ name: 从 goal 提取, ... })
      → 将当前 session.metadata.projectId 设为新项目 ID
      → 迁移已有的 context/artifacts 到新项目（移动引用，非复制）
      → 非模态 toast："已为你整理了「家庭记账」相关资料"
```

**跨会话去重机制**：
- 基于 goal 摘要生成话题指纹（关键词归一化 + hash）
- **MVP 阶段**：关键词归一化 + 精确/近义匹配（不依赖 embedding 服务）
- **增强阶段**（embedding 服务就绪后）：语义相似度 > 0.8 视为同一话题
- 命中时：只关联 session、不新建项目
- 未命中时：正常建项目
- 用户手动 `create_project` 工具调用**不受去重约束**（用户显式说"新建"就是真的要新建）

**迁移语义**：
- 自动建项目后"迁移已有的 context/artifacts 到新项目"
- **S2 上线前**：物理复制 context/artifacts 文件到新项目目录，源会话保留原文件
- **S2 上线后**：改为移动引用（在 items.db 中写入新记录，`refIds` 指向源数据）
- 效果：项目页面可追溯来源，原聊天页不受影响（两种模式均保证）

**用户体验**：聊着聊着，右侧面板突然有内容了——项目已经存在了。不需要"创建"这个动作。

### 改动 2：搜索 + 活跃度排序（P1）

**现状**：项目列表按创建顺序排列，无搜索。

**改为**：

**2a. 搜索框**
- 列表顶部增加搜索输入框
- **两级搜索**：
  - 第一级（即时）：匹配项目名称 + 项目内会话标题（前端本地过滤）
  - 第二级（按需）：点击"全文搜索"后，搜索项目内内容全文
    - S2 上线前：history.jsonl 正则匹配 + rules.md/artifacts.json 文本搜索（兜底方案）
    - S2 上线后：items.db FTS 索引 + history.jsonl 消息文本（正式方案）
- 搜索结果高亮匹配文字
- 支持拼音模糊匹配（如输入"jizhang"匹配"记账"）
- **会话标题缺失时**：用 S6 生成的会话摘要或首条消息内容参与匹配

**2b. 活跃度排序**
- 默认按"最近一次会话时间"排序
- 今天聊过的置顶
- 标记活跃度：🟢 今天 | 🟡 本周 | ⚪ 更早

**2c. 智能建议**
- 无搜索结果时，提示："没有找到「XXX」，要不要用 AI 搜索所有聊天记录？"

### 改动 3：项目休眠机制（P2）

**现状**：所有项目平铺在列表中，永不消失。

**改为**：

```
列表分区：
  ┌─ 活跃（最近 7 天有会话）── 全部展开
  ├─ 休眠（7-30 天无会话）  ── 默认折叠，显示 "(3 个项目)"
  └─ 归档（30 天以上）       ── 默认隐藏，底部"查看归档"入口
```

- 休眠和归档只是**视觉隐藏**，不删除数据
- 重新在这个项目里聊天 → 自动回到活跃区
- 归档区的项目在搜索结果中仍然可见

**可配置阈值**（默认值，用户可在设置中调整）：
| 参数 | 默认值 | 说明 |
|------|:--:|------|
| 休眠阈值 | 7 天 | 超过后从活跃区折叠到休眠区 |
| 归档阈值 | 30 天 | 超过后从休眠区隐藏到归档区 |

**置顶（固定）**：
- 项目右键菜单 → "置顶" / "取消置顶"
- 置顶项目固定在活跃区顶部，不参与活跃度排序和休眠
- 一个 📌 图标标记置顶状态

## 五、与现有系统的衔接

### 和 PDCA 隐性引擎的关系

```
自然化项目管理 = 外层体验
PDCA 隐性引擎 = 内层驱动力

体验层：用户只管聊天，项目自己长出来
驱动层：AI 在每次对话中隐性执行 Plan→Do→Check→Act
```

自动化建项目后，升级通道变为：
```
聊天 → 检测到复杂目标 → 自动建项目（不自动启动 PDCA）
（PDCA 由用户后续表达"帮我规划/推进"时启动，或通过 create_project 工具显式启动）
```
> **为什么不自动启动 PDCA？** 自动建项目是轻量级的"顺手帮你整理"，默默加一个 PDCA 循环属于隐性流程过重。用户显式说"建项目"（S1 路径）时启动 PDCA 才是合理的——用户有明确预期。

### 数据模型

- Project 类型已有 `pdcaIds`、`phase`、`workItemIds`
- 引擎钩子已有 `hasGoal` 返回值
- **仅新增 `sandboxPath` 一个字段**（S4 专属文件夹），其余改动在交互层

### 改动范围

| 优先级 | 改动 | 涉及文件 | 工作量 |
|:--:|------|---------|:--:|
| P0 | AI 自动建项目 | `ChatManager.ts`、`ImplicitEngineHook.ts`、`systemPromptSections.ts` | ~2h |
| P1 | 搜索 + 排序 | `ProjectsPage.tsx`（左栏） | ~1h |
| P2 | 休眠分区 | `ProjectsPage.tsx`（左栏） | ~1h |

## 七、补充方案一：AI 工具化 — `create_project` 工具

> 回应：用户明确说"创建项目"，Liri 怎么处理？

### 现状问题

system prompt 引导 AI 建议用户手动建项目（"在左侧点'+'就行"），但 AI **不能帮你建**。当用户说"帮我建一个家庭记账项目"时，AI 只能回复操作指南，不能执行。

### 方案

给 AI 注册一个 `create_project` 工具，让它可以真正创建项目：

```
工具定义：
  name: "create_project"
  description: "创建一个新项目，用于跟踪复杂任务"
  parameters:
    name: string          # 项目名称（必填）
    description?: string   # 项目描述（可选，AI 自动从对话摘要）
    goal?: string          # 项目目标（可选，从对话提取）
  returns:
    projectId: string      # 新项目的 ID

工具实现（复用已有的项目创建逻辑）：
  1. ProjectStore.create({ name, description, ... })
  2. 将当前 session 关联到新项目（session.metadata.projectId = projectId）
  3. 如果 AI 已经提取了 goal，自动启动 PDCA（handlePdcaStart）
  4. 静默完成，AI 在回复中确认
```

### 用户体感

```
用户："帮我建一个家庭记账项目"
AI：[调用 create_project 工具]
    → 项目创建成功
    → session 自动关联
    → 如果有明确目标，后台启动 PDCA
    "好了，「家庭记账」项目已创建，我们继续聊。右侧面板会自动跟踪进度。"
```

### 与隐性引擎的关系

```
两个建项目路径，互补不冲突：

路径 A（隐性）：聊天 → 引擎检测到复杂目标 → 自动建项目
  → 适用：用户没说要建项目，但聊着聊着自然产生了

路径 B（工具）：用户明确说"建项目" → AI 调用 create_project 工具
  → 适用：用户有清晰意图，期望立刻看到反馈

两路径最终走同一底层：ProjectStore.create() + session 关联
```

#### 路径冲突仲裁规则

两条路径可能同时触发（用户在聊天中说"帮我规划一下"，引擎已自动建项目，同一句话又命中了"用户表达明确意图"）。仲裁规则：

```
优先级：路径 B（工具显式创建）> 路径 A（引擎隐性创建）

引擎检测到当前 session 已经有 projectId 关联时：
  → create_project 工具：返回已有项目 ID，不新建
  → 引擎自动建项目：跳过，不重复建

时序冲突保护（同一轮对话中两路径同时触发）：
  → create_project 先执行 → projectId 已写入 session.metadata
  → 引擎检测到 projectId 已存在 → 跳过自动建
  → 结果：只有一个项目被创建

去重依据：session.metadata.projectId（而非 projectId 全局查重）
```

**设计理由**：工具路径优先级更高，因为用户明确说"建项目"是显式意图，应得到即时反馈；隐性路径是"顺手帮你整理"，可被覆盖。

### 配套：system prompt 更新

当前 prompt 中"绝对不要提及 Plan/Do/Check/Act"的限制保持不变，但新增：

```
当用户表达明确的"创建项目/管理任务/追踪进度"意图时：
- 有 create_project 工具可用时：直接调用工具创建项目
- 没有工具可用时：引导用户在左侧点击"+"创建（最多建议一次）
```

## 八、补充方案二：数据模型统一 — ProjectItem

> 回应：现有的"模型"模块进一步提升——数据模型层面

### 现状问题

项目相关的数据分散在两个存储系统、两种文件格式：

| 存储 | 路径 | 格式 | 面板 |
|------|------|------|------|
| ProjectContext | `<id>/rules.md` | Markdown `### [type]` | 项目资料 |
| ProjectArtifact | `<id>/artifacts.json` | JSON 数组 | 成果 |

问题：
- 资料和成果**不能互相引用**（"这个成果来源于哪个资料？"→跨文件查）
- 搜索时要分别搜两个文件
- 讨论记录是第三种格式（`.jsonl`），又是独立系统
- 新增一种内容类型就要新增一个文件→**文件膨胀**

### 方案：ProjectItem 统一模型

```typescript
// 项目中的所有内容 — 一个模型，一种存储，按 kind 区分
interface ProjectItem {
  id: string;
  projectId: string;
  
  // 来源
  kind: 'context' | 'artifact';
  // 注意：history（聊天记录）不纳入 ProjectItem，由 history.jsonl 独立存储
  // 讨论记录面板从 history.jsonl 读取，通过 sessionId 关联
  
  // 内容
  title: string;          // 列表显示用
  content: string;        // 完整内容
  summary?: string;       // AI 生成的摘要
  
  // 关联
  sessionId?: string;     // 来源会话
  messageId?: string;     // 来源消息
  refIds?: string[];      // 引用其他 ProjectItem（解答"成果来源于哪个资料"）
  
  // 元数据
  phase?: 'plan' | 'do' | 'check' | 'act';  // PDCA 阶段标注
  tags?: string[];        // 自由标签
  createdAt: string;
  updatedAt: string;
}
```

**统一存储**：`<id>/items.db`（SQLite 单文件，替换 rules.md + artifacts.json）

> **为什么不继续用 JSONL？** rules.md 和 artifacts.json 是随机读写场景（引用追溯、重命名、搜索），JSONL 的 append-only 模式不适合。但 history.jsonl（聊天记录流式追加）保持 JSONL 不变：聊天记录是 append-only 的，JSONL 正是最优解。详见下方"存储分层设计"。

### 存储分层设计

```
项目数据三层存储，各司其职：

第一层：project.json     — 项目元数据（name, phase, sandboxPath, status...）
        格式: JSON       — 随机读写，文件小（<10KB）

第二层：items.db         — 项目内容（context + artifact）
        格式: SQLite     — 随机读写 + 全文搜索 + 引用追溯
        表: items (id, projectId, kind, type, title, content, summary, 
             sessionId, messageId, refIds, phase, tags, created_at, updated_at)
        索引: projectId, kind, type, phase
        FTS: items_fts 虚拟表（title + content + summary）

第三层：history.jsonl    — 聊天记录（流式追加）+ 会话级 meta 行（如摘要）
        格式: JSONL      — append-only，O(1) 追加不变
        职责: 存储消息流 + 会话元数据，不参与项目内容检索
```

**选型理由**：
| 方案 | 追加性能 | 随机读写 | 全文搜索 | 引用追溯 | 复杂度 |
|------|:--:|:--:|:--:|:--:|:--:|
| 全部 JSONL（现状） | ✅ | ❌ | ❌ | ❌ | 低 |
| 全部 items.json（原方案） | ❌ | ✅ | ❌ | ✅ | 低 |
| **SQLite + JSONL（新方案）** | ✅ | ✅ | ✅ | ✅ | 中 |

### 迁移策略

```
惰性迁移，不强制全量：
1. 读时检测：打开项目时检查旧格式（rules.md / artifacts.json）是否存在
2. 存在 → 解析后写入 items.db，保留旧文件为 .bak 备份
3. 确认写入成功 → 延迟删除旧文件（下次启动时清理 .bak）
4. 不存在 → items.db 已是唯一数据源
5. history.jsonl 不变，不参与迁移
```

> **原子性保证**：先写 items.db 成功后保留 .bak，再异步清理。写失败时回退读旧文件。

> **S2 上线后的下游切换**：S5b 的 projectContext 注入数据源由 `rules.md` 切换为 items.db 的 context 行。S6 的 summary/decision 由 `summaries.json` 迁移到 items.db，迁移完成后删除 summaries.json。

### refIds 引用维护

- 引用在创建时建立，基于当前内容快照
- 被引用内容更新后，引用不自动同步（避免级联更新复杂性）
- 引用关系在 items.db 中通过 `refIds` 字段存储，可随时查询
- 删除被引用条目时，`refIds` 中保留悬空引用（标记为 `[已删除]`）

### 收益

| 改善 | 之前 | 之后 |
|------|------|------|
| 引用追溯 | 跨文件查找 | `items.filter(i => item.refIds.includes(i.id))` |
| 搜索 | 分别搜 rules.md + artifacts.json + history.jsonl | 一次 grep |
| 扩展 | 新类型→新文件 | 新 type → 加枚举值 |
| PDCA 关联 | 无 | `phase` 字段直接标注 |

## 九、补充方案三：模型-阶段路由 — ModelPhaseRouter

> 回应：现有的"模型"模块进一步提升——AI 模型选择层面

### 现状问题

`modelRouter` 按任务类型路由（生图→生图模型、翻译→翻译模型），但不考虑**对话状态**。同一个项目里：
- 用户说"帮我规划" → 应该用推理强的模型
- 用户说"帮我写代码" → 应该用性价比高的模型  
- 用户说"帮我审查这段" → 应该用严谨的模型

但目前这三个请求可能用同一个模型，因为路由只看"是什么任务"，不看"在什么阶段"。

### 方案：阶段感知路由

```
modelRouter 扩展：

现有：modelRouter.route(taskType) → modelId
新增：modelRouter.route(taskType, phaseContext) → modelId

phaseContext 来源（按优先级降级）：
  1. **最近一条 ImplicitEngineHook 返回的 intent**（置信度 ≥ 0.7）——优先使用，因为意图是即时的、精准的
  2. 项目上下文：project.phase → 'plan' | 'do' | 'check' | 'act'
  3. null（无阶段上下文）
  
  > **多 PDCA 说明**：`project.phase` 是项目级单值，当项目有多个 PDCA 循环（`pdcaIds` 数组）时，phase 取最近活跃的 PDCA 阶段。但实际路由优先使用最新 intent（第 1 级），project.phase 仅作兜底。
```

**默认映射**（用户可在"任务分工"页面自定义）：

| 阶段上下文 | 模型偏好 | 理由 |
|-----------|---------|------|
| Plan（规划、分析） | 推理能力强（如 DeepSeek-R1） | 需要深度思考 |
| Do（执行、生成） | 性价比高（如 DeepSeek-V3） | 量大，成本敏感 |
| Check（审查、验证） | 严谨保守（如 DeepSeek-V3，temperature=0.1） | 稳定 > 创意 |
| Act（总结、反馈） | 默认模型（用户设置） | 通用任务 |
| 无上下文（普通聊天） | 默认模型（用户设置） | 不变 |

### 实现管线

```
用户发消息
  → ChatManager.processMessage()
    → 查找阶段上下文（优先级降级）：
      1. 最近一条引擎钩子分析的 intent（置信度 ≥ 0.7）→ intent
      2. session.metadata.projectId → ProjectStore.get(pid).phase
      3. null（无阶段上下文）
    → modelRouter.route(taskType, { phase, projectId })
      → 查 CustomPhaseMapping（用户自定义） 
        → 有 → 用自定义映射
        → 无 → 用默认映射（上表）
      → 返回 modelId
    → 用选中的模型继续
```

### 配套改动

1. **modelRouter 接口扩展**：`route()` 增加可选的 `phaseContext` 参数
2. **"任务分工"页面**：新增"阶段偏好"Tab，允许用户配置 Plan/Do/Check/Act 各用哪个模型
3. **ChatManager**：在调用 modelRouter 前注入阶段上下文

### 意图置信度与降级

引擎返回的 intent 分析不是 100% 准确。用户随口说"帮我看看"可能被误判为 Check 阶段：

```
降级策略：
  ImplicitEngineHook 返回 intent 时附加 confidence（0~1）
  → confidence >= 0.7：使用阶段路由
  → confidence < 0.7：回退到用户默认模型（等价于"无上下文"）
  → 引擎未返回 intent：使用默认模型
```

**路由可观测性**（验收标准补充）：
- 前端在消息旁显示当前使用的模型名称（如状态栏小标签）
- 用户可一键"切回默认模型"，无需进入设置页
- 路由决策日志（debug 级别）：记录 `{ intent, confidence, selectedModel, fallbackReason }`

## 十、补充方案四：项目专属文件夹 — ProjectSandbox

> 回应：每个项目应有指定的文件夹来管理相关资料

### 设计理念

"项目 = 文件夹 + 聊天记录"模型中，文件夹是真实存在的东西。用户应该能用文件管理器打开它、往里拖文件、从里面复制东西——就像桌面上的一个普通文件夹。

### 方案

创建项目时，自动在用户文档目录下创建专属文件夹：

```
~/Documents/LiriProjects/
├── proj-abc123/                  ← 文件夹名 = projectId（稳定唯一）
│   ├── 银行账单.pdf              ← 用户拖进来的
│   ├── 预算表.xlsx                ← 用户放进来的
│   ├── 分析报告.md                ← AI 生成的
│   └── images/
│       └── 截图.png
├── proj-def456/
│   ├── 需求文档.md
│   └── design/
│       └── 首页草图.png
└── proj-ghi789/
    └── 课程大纲.md
```

> **为什么文件夹名用 projectId 而非项目名？** 项目名是 AI 提取的、用户可随时改的，可能含非法字符、可能与其他项目重名。projectId 是唯一且稳定的标识符，解耦显示名与目录名。显示名单独存在 `project.name` 字段中。

### 三条原则

**1. 文件夹是双向的**

| 方向 | 操作 | 示例 |
|------|------|------|
| 用户 → AI | 拖文件进文件夹 → AI 能读 | 拖入 PDF → AI 说"我看到你的账单了，帮你分析" |
| AI → 用户 | AI 写文件到文件夹 → 用户能用 | AI 生成报告 → 用户双击打开 |

**2. 文件夹内容自动出现在右侧面板**

```
~/Documents/LiriProjects/<projectId>/
  → 右侧面板「项目资料」自动索引
  → 按文件类型分组：文档 / 表格 / 图片 / 其他
  → 文件变更自动检测（chokidar 监听）
```

**3. 文件夹路径可自定义**

- 默认：`~/Documents/LiriProjects/<projectId>/`
- 创建项目时可选自定义路径
- ProjectStore 记录 `sandboxPath` 字段

### 实现

```typescript
// workspace/types.ts — Project 接口扩展
interface Project {
  // ...existing fields...
  /** 项目专属文件夹路径（用户可访问的真实目录） */
  sandboxPath: string;  // e.g. "C:\Users\xxx\Documents\LiriProjects\proj-abc123"
}
```

**创建项目时**：
```
ProjectStore.create({ name, sandboxPath? })
  → sandboxPath = sandboxPath ?? join(DOCUMENTS_DIR, 'LiriProjects', projectId)
  → mkdirSync(sandboxPath, { recursive: true })
```
> 文件夹名用 `projectId`（唯一稳定），而非 `sanitize(name)`（用户可改、可能冲突）。显示名与目录名解耦。

**右侧面板集成**：
- `ProjectMaterialsPanel` 新增"文件"分组
- 读取 `project.sandboxPath` 目录，按类型展示
- 使用 `chokidar` 库监听文件变更（`fs.watch` 跨平台行为差异大）
- debounce 500ms 合并连续事件（编辑器保存常触发多次）
- **初始扫描**：创建项目时立即全量索引目录（覆盖用户直接拷贝文件不经过拖拽的场景）

**聊天集成**：
- 给 AI 注册一个 `read_project_file` 工具：读取 sandbox 中的文件内容
- 给 AI 注册一个 `write_project_file` 工具：向 sandbox 写入文件
- @引用扩展自动包含 sandbox 中的文件
- **写入安全**：`write_project_file` 写入前检测目标文件是否被其他进程占用（独占打开探测或时间戳对比），被占用时改为新文件名（如 `原文件名-ai修订.ext`）避免覆盖用户正在编辑的内容

### 与现有存储的关系

```
~/.pyapp/projects/<id>/       ← Liri 内部数据（project.json, items.db, history.jsonl）
  ├── project.json
  ├── items.db                ← S2 迁移后
  └── history.jsonl

~/Documents/LiriProjects/<id>/  ← 用户可见的项目文件夹
  ├── *.pdf, *.xlsx, *.md       ← 真实文件
  └── images/                    ← 子文件夹

两套存储互补，不是替代：
  内部存储 = AI 的工作笔记（自动维护，用户不需要碰）
  项目文件夹 = 用户的工作空间（用户管理，AI 辅助读写）
```

### 三层目录职责对照表

当前应用存在三个"目录"概念，明确各自的职责边界：

| 属性 | 物理工作空间 | AgentWorkspace | 项目文件夹 |
|------|------------|---------------|-----------|
| 路径 | `~/workspace/` | 临时目录 | `~/Documents/LiriProjects/<id>/` |
| 谁拥有 | 用户 | Liri 运行时 | 用户 |
| 谁可读写 | 用户 + AI（有约束） | 仅 AI（沙盒隔离） | 用户自由读写、AI 通过专用工具受限读写 |
| 用户可见 | 是 | 否 | 是 |
| 安全边界 | `.workspace.json` 元数据 | `maxSize`/`allowSymlinks`/`ignorePatterns` | `realpath` 校验 + 路径穿越防护 |
| AI 访问方式 | cwd 设置 + 沙盒约束 | 自动（代理执行环境） | `read_project_file`/`write_project_file` 工具 |
| 文件生命周期 | 长期 | 会话期间 | 长期（与项目同生命周期） |

**关键规则**：项目文件夹 ≠ AgentWorkspace。AI 不会自动以项目文件夹为 cwd，必须通过工具调用才能读写项目文件夹中的文件。这样用户放进项目文件夹的文件不会被 AI 无意中读取发送给 LLM。

### 安全边界

- AI 只能读写 `sandboxPath` 内的文件，不能越界
- 写文件操作用 `path.resolve(sandboxPath, relativePath)` 校验，防止路径穿越
- **符号链接防护**：读写前用 `fs.realpath()` 校验实际路径仍在 `sandboxPath` 内（Windows 上 junction 同理）
- 文件大小限制（默认 50MB），超大文件只索引不读取内容
- **云同步检测**：创建项目时检测 `Documents` 是否被 OneDrive/iCloud 接管（注册表/环境变量），如被接管则提示用户或建议改用非同步目录（如 `~/LiriProjects/`），避免文件锁冲突
- **隐私提示**：AI 通过 `read_project_file` 读取用户私人文件（PDF/图片等）时，文件内容会发送给 LLM 服务商。首次读取时前端提示一次"该文件内容将外发给 AI 服务商用于分析"

## 十一、补充方案五：聊天与项目的无缝切换

> 回应：AI 创建项目后前端自动跳转；项目页面自动加载文件夹资源到聊天上下文

### 现状问题

目前聊天和项目是**两个独立页面**：

1. 在普通聊天中说"帮我建个项目"，AI 即使能建项目（S1），用户也看不到——因为还在聊天页
2. 进入项目页面后，聊天上下文是**空的**——AI 不知道项目文件夹里有什么文件、不知道项目目标和约束
3. 项目页面中生成的成果，用户不知道它存在了哪里

### 方案

#### 5a. AI 创建项目后前端自动跳转

```
用户（在聊天页面）："帮我建一个家庭记账项目"
  → AI 调用 create_project 工具 → 项目创建成功
  → HTTP 响应返回 { projectId: "xxx", _meta: { action: "suggest_navigate" } }
  → 前端在聊天区顶部显示非模态提示条："已创建「家庭记账」项目 — [查看项目] [忽略]"
  → 用户点击"查看项目" → 跳转到项目页面，自动打开新项目
  → 用户点击"忽略" → 留在聊天页，什么都不发生
```

**实现**：
- HTTP 流式响应结束时，在最终 chunk 附加 `_meta: { action: "suggest_navigate", target: "/projects?open=<projectId>", label: "查看项目" }` 字段
- 前端 `chatService` 拦截流结束事件中的 `_meta` 字段，在聊天区顶部显示非模态提示条："已创建「家庭记账」项目 — [查看项目] [忽略]"
- 用户点击"查看项目"才跳转，不强制跳转（避免打断聊天心流）
- 项目管理页面支持 `?open=<projectId>` query 参数，自动选中

#### 5b. 项目页面聊天上下文自动注入

进入项目页面并选中项目后，聊天 context 自动包含三样东西：

```
ChatManager 构建 system prompt 时注入 projectContext：

1. 项目目标与约束（来自 rules.md 的 goal/constraint）
   示例：## 项目目标
         实现一个家庭记账系统，支持收入支出记录和月度报表
         ## 约束
         必须使用 SQLite、不需要用户登录

2. 项目文件夹文件列表（来自 sandboxPath 的目录扫描）
   示例：## 项目文件
         - 银行账单.pdf (234KB)
         - 预算表.xlsx (56KB)
         - images/截图.png

3. 项目阶段与进度（来自 project.phase + pdcaIds）
   示例：## 项目状态
         阶段: plan（规划中）
         PDCA 任务: 1 个进行中
```

**实现管线**：
```
ChatManager.buildSystemPrompt(session, messages)
  → if session.metadata.projectId:
      → ProjectStore.get(projectId) → project
      → ProjectContextService.parseRulesFile(rulesPath) → contexts
      → 扫描 sandboxPath 文件列表（缓存 30 秒）
      → 组装为 projectContext 段落
      → 注入 system prompt

  → 无 projectId: 跳过（普通聊天走 pdcaThinking 段落）
```

**注入上限策略**（防止撑爆 token）：
| 内容 | 上限 | 策略 |
|------|:--:|------|
| 文件列表 | 前 20 个 | 超出时标注 "(+N 个文件未列出)" |
| 单个文件内容 | 自动读取时不给内容 | 仅列路径+大小，AI 需用工具读取 |
| rules.md | 截断到 2000 字符 | 超出部分折叠为 "(完整内容见项目资料面板)" |

#### 5c. 输出自动落地到项目文件夹

AI 在项目上下文中产出的文件，自动写入 `sandboxPath`：

```
AI 生成："我帮你写了分析报告"
  → write_project_file 工具自动调用
  → 文件写入 ~/Documents/LiriProjects/<projectId>/分析报告.md
  → 用户：打开文件夹就能看到，双击编辑
  → 右侧面板「项目资料」→「文件」分组自动刷新
```

### 完整切换流程

```
普通聊天                    项目页面
─────────                  ─────────
"帮我建项目"
  │                           │
  ├─ AI 调 create_project ──→ 自动跳转 ──→ 三栏布局
  │   ├─ 创建 sandbox 文件夹              ├─ 左栏：新项目高亮
  │   ├─ 写入初始 rules.md               ├─ 中栏：ChatArea 上下文已注入
  │   └─ 返回 navigate _meta             └─ 右栏：资料区已显示初始资料
  │
  │  用户继续聊天
  ├─ AI 读项目文件夹 ──→ 分析文件
  ├─ AI 写分析报告 ──→ sandboxPath/分析报告.md
  └─ 成果自动刷新 ──→ 右侧面板更新
```

### 改动范围

| 子项 | 涉及文件 | 工作量 |
|------|---------|:--:|
| 5a 导航跳转 | `chatService.ts`（_meta 拦截）、`ProjectsPage.tsx`（?open= 参数） | ~1h |
| 5b 上下文注入 | `ChatManager.ts`（buildSystemPrompt 扩展） | ~1.5h |
| 5c 输出落盘 | 已有（`write_project_file` 工具，见 S4） | ~0h |

## 十二、补充方案六：AI 主动沉淀 — 让"记住"不只是"数据不丢"

> 回应：核心哲学是"记住"，但方案只停留在存储层。真正的"记住"是 AI 替用户记。

### 设计理念

"记住"有三个层次：

| 层次 | 当前方案 | 能力 |
|------|:--:|------|
| 数据不丢 | ✅ items.db + history.jsonl | 持久化存储 |
| 结构不乱 | ✅ ProjectItem 统一模型 | 引用追溯 |
| **用户不记** | ❌ 缺失 | AI 自动总结、提炼、提醒 |

这个方案补上第三层：AI 在每轮会话结束时**主动沉淀**关键信息。

### 三种沉淀产物

```
会话结束后自动生成（后台异步，不阻塞用户）：

1. 会话摘要（条件触发）
   → 仅对有关联项目（projectId 非空）且消息数 ≥ 3 的会话生成
   → 3~5 句话概括本轮聊了什么
   → 写入 history.jsonl 作为该 session 的元数据行
   → 在项目讨论记录面板顶部显示
   → 连续短间隔会话（5 分钟内）合并生成一次摘要，避免重复调用

2. 阶段性小结（累计触发）
   → 同一项目连续 3 次会话后自动生成
   → 汇总：目标进展、关键决策、待办事项
   → **S2 上线前**：写入 `<id>/summaries.json`（独立 JSON 文件）；**S2 上线后**：写入 items.db，kind='context', type='summary'
   → 在项目资料面板「摘要」区显示

3. 关键决策记录（条件触发）
   → AI 通过意图分析检测到用户做了选择/决定时自动提取
   → 检测方式：意图分析 + 关键词置信度双条件（避免"我决定不了"误触发）
   → 格式："用户决定：XXX，原因：YYY"
   → **S2 上线前**：写入 `<id>/summaries.json`；**S2 上线后**：写入 items.db，kind='context', type='decision'
   → 在项目资料面板「决策」区显示
```

### 成本控制

| 约束 | 值 | 原因 |
|------|:--:|------|
| 仅对有关联项目的会话生成 | `projectId != null` | 普通闲聊不需要摘要 |
| 短会话跳过 | < 3 条消息 | 无足够内容 |
| 连续短间隔合并 | 5 分钟内 | 避免重复 LLM 调用 |
| 使用低成本模型 | DeepSeek-V3 | 摘要任务不需要推理能力 |

### 实现管线

```
ChatManager._finalizeStreamMessage()
  → 消息流结束后：
    1. 异步调用 LLM（低成本模型，如 DeepSeek-V3）生成会话摘要
    2. 写入 history.jsonl（meta 行，type='summary'）
    3. if 同一 projectId 下有 ≥3 个 session：
       → 触发阶段性小结生成
       → 读取最近 3 个 session 的摘要
       → LLM 汇总为阶段性小结
       → 写入 `<id>/summaries.json`（S2 上线后改为 items.db）
    4. if 消息中检测到决策关键词（"决定"、"就选"、"定下来"）：
       → 触发决策记录提取
       → LLM 提取决策内容
       → 写入 `<id>/summaries.json`（S2 上线后改为 items.db）
```

### 用户体感

- 用户什么都不用做，下次打开项目页面时"摘要"和"决策"区已经有内容
- 翻聊天记录找上次的决定 → 变成直接看"决策"面板
- 多轮对话后忘记进展 → 看"阶段性小结"一目了然

## 十三、补充方案七：项目生命周期（删除/完结/撤销）

> 回应：项目怎么长出来设计好了，但怎么凋零/删除/完结？

### 设计原则

"项目是长出来的"意味着项目也有自然终结。提供三种终结方式，对应三种用户心理：

| 操作 | 用户心理 | 行为 | 可逆？ |
|------|---------|------|:--:|
| **删除** | "这个项目我不要了" | 彻底删除项目数据 + sandbox 文件夹（移到回收站） | 回收站可恢复 |
| **完结** | "这个项目做完了" | 项目标记为 `completed`，保留在活跃区（带 ✅ 标记），保留全部数据 | 可重新激活 |
| **撤销创建** | "AI 搞错了，我没想要这个" | 30 分钟内可一键撤销（项目数据 + session 关联回滚） | 限时 |

### 入口设计

```
删除：项目列表右键菜单 → "删除项目" → 二次确认对话框
      → 显示文件夹大小（如 "123 MB"）
      → 选项 1："删除全部"（项目数据 + sandbox 文件夹 → 回收站）
      → 选项 2："仅删项目数据，保留文件夹"（sandbox 文件夹不删除）
      → 回收站保留 30 天，之后物理删除

完结：项目页面顶部状态栏 → 点击"标记完成"
      → project.status = 'completed'
      → 保留在活跃区（带 ✅ 标记），不进入隐藏的归档区
      → 用户刚完结就能看到结果，避免"做完就消失"的困惑

撤销：自动建项目后 30 分钟内，右侧面板出现"撤销"按钮
      → 点击后删除项目 + 回滚 session.metadata.projectId
      → toast："已撤销项目「XXX」"
```

### 编辑项目信息

- 项目列表右键菜单 → "重命名" → 修改 `project.name`（不影响 sandboxPath）
- 项目页面顶部 → 点击项目名 → 内联编辑名称和描述
- 与 P0 中"AI 自动提取项目名"形成闭环：用户可随时修正 AI 起的名字

### 完结后行为

- PDCA 走到 Act 结束**不自动完结**——只有用户能判定"做完了"
- 完结后仍可聊天，聊天操作自动重新激活项目（`status → 'active'`）
- 完结项目在搜索中正常可见，标签标注"已完成"
- **完结项目豁免休眠**：不参与 P2 活跃度沉底，类似置顶但带 ✅ 标记
- 用户手动取消完结 → 项目恢复正常活跃状态（恢复参与休眠排序）

### 数据保留策略

```
活跃项目：全部数据保留
完结项目：全部数据保留（显示在活跃区，带 ✅ 标记）
已删除项目：回收站保留 30 天，之后物理删除
撤销项目：立即删除，不进回收站
```

## 十五、验收标准（完整）

### 自然化交互

1. **零操作建项目**：一次对话聊到复杂话题后，项目已存在
2. **AI 能建项目**：说"帮我建一个XX项目"，AI 直接执行
3. **找到比管理重要**：10 个项目时，搜索 3 秒内找到目标
4. **列表永远清爽**：活跃在上，休眠在下，归档隐藏
5. **聊天可跳转**：AI 建项目后提示用户可跳转，用户点击后进入项目页面

### 上下文智能

6. **项目上下文注入**：进入项目页面后，AI 自动知道项目目标、约束、文件列表
7. **输入输出互联**：用户放进文件夹的文件 AI 能读，AI 产出的文件自动进文件夹

### 文件管理

8. **真实文件夹**：每个项目在 `~/Documents/LiriProjects/` 下有真实目录
9. **双向互通**：拖入文件 AI 能读，AI 写入的文件用户能打开
10. **安全隔离**：AI 不能读写项目文件夹以外的路径

### 数据一致性

11. **资料/成果统一存储**：`items.db` (SQLite) 替换 rules.md + artifacts.json，history.jsonl 保持独立
12. **引用可追溯**：成果可以追溯到来源资料
13. **惰性迁移**：旧数据自动迁移，不丢数据

### 智能路由

14. **阶段感知**：Plan 阶段用推理模型，Do 阶段用廉价模型
15. **用户可定制**：在任务分工页面自定义阶段-模型映射
16. **降级保底**：无阶段上下文或置信度不足时回退到用户默认模型
17. **路由可观测**：用户能看到当前使用的模型名称，可一键切回默认

### 项目生命周期

18. **删除**：右键删除 → 回收站保留 30 天
19. **完结**：用户标记完成 → 保留在活跃区（带 ✅ 标记，豁免休眠）
20. **撤销**：自动创建后 30 分钟内可一键撤销

## 十六、风险与回滚

### 可预见风险及应对

| 风险 | 概率 | 影响 | 回滚手段 |
|------|:--:|:--:|------|
| 自动建项目误判（AI 不该建却建了） | 中 | 低 | 30 分钟内一键撤销；30 分钟后可手动删除（回收站保留 30 天） |
| 跨会话重复建项目 | 中 | 中 | 话题指纹去重 + 手动合并项目（未来功能） |
| 存储迁移失败（rules.md → items.db） | 低 | 高 | 迁移前保留旧文件备份（`.bak`），迁移失败时回退读旧文件 |
| ModelPhaseRouter 路由错误 | 中 | 低 | 置信度 < 0.7 降级默认模型；用户可一键切回默认 |
| Sandbox symlink 逃逸 | 低 | 高 | `realpath` 校验 + 沙箱外访问被拒绝并记录告警日志 |
| chokidar 监听失败 | 低 | 低 | 降级为轮询（30 秒间隔），右侧面板显示"手动刷新"按钮 |

### 回滚原则

- 自动建项目：可撤销、可删除，不留不可逆痕迹
- 数据迁移：保留备份快照（`.bak`），手动或自动恢复
- 存储格式：惰性迁移意味着旧格式长期共存，非破坏性切换
- 模型路由：降级路径始终指向用户默认模型

## 十七、MVP 分期路线

按"独立上线、彼此不阻塞"原则拆分：

### 第一阶段（MVP，约 1 周）

```
P3 + P0 + P1 + S1 + S4 + S5
```

交付物：命名收敛（消除 worktree/workspace 混用）+ AI 能自动建项目 + 用户能搜索找项目 + AI 能通过工具显式建项目 + 项目有专属文件夹 + 聊天项目可切换。

### 第二阶段（约 1 周）

```
P2 + S6 + S7 + S3
```

交付物：项目休眠分区 + AI 主动沉淀（摘要/小结/决策） + 删除/完结/撤销生命周期 + 模型按阶段智能路由。

### 第三阶段（约 1 周）

```
S2（SQLite 存储迁移）
```

交付物：items.db 替换 rules.md/artifacts.json，全文搜索 FTS。此阶段独立上线，不影响前两阶段功能。

> **依赖声明**：前两阶段的 S6（summary/decision）和 P0（refIds）在 S2 上线前均使用独立 JSON 文件 / 物理复制作为过渡方案，S2 上线时统一迁移至 items.db。S2 上线后 S5b 的数据源由 rules.md 切换为 items.db。详见各方案中的"S2 上线前/后"标注。

> **原则**：每个阶段独立上线，不阻塞后续。S2 放在最后是因为它涉及数据迁移，需要前两阶段的功能稳定后再做。

## 十九、多设备边界声明

**本方案暂不支持多设备同步。**

以下能力在单机单用户前提下设计，多设备场景存在已知限制：

| 能力 | 单机 | 多设备 |
|------|:--:|:--:|
| items.db (SQLite) | ✅ | ❌ 文件锁冲突 |
| chokidar 文件监听 | ✅ | ❌ 跨设备同步不触发事件 |
| sandboxPath 绝对路径 | ✅ | ❌ 不同设备路径不同 |
| 项目数据一致性 | ✅ | ❌ 需引入同步协议 |

**未来多设备支持方向**（不在本方案范围内）：
- items.db 换为服务端 SQLite 或 PostgreSQL
- sandbox 目录使用云同步目录（OneDrive/iCloud），但需处理文件锁和冲突
- 引入 CRDT 或操作日志同步项目元数据
