## 一、现象（用户可见）

在长程代码分析任务中，Agent 执行到一半**直接结束本轮**，界面**没有给出任何结论文字**，用户只能看到"任务完成"的观感，不知道发生了什么、也不知道结论是什么；用户连续两次追问后才拿到阶段性结论。

### 3.5 根因精化（审核复核后的三处校正，均已核实）

**精化 1：真病根是「phase 被提前写死」，不是「事后拼装」。**
`ReActLoop.ts:628` 在 `shouldContinue === false` 时**先**置 `phase = 'completed'`；而 `getTerminationReason()`（`:398-416`）**每一路分支都读 `phase`**（`:399/402/406/408`），末尾以 `return 'completed'` 兜底。
⇒ 只要走了这条路（**含超时**），**判别器无论怎么改都会返回 `'completed'`**。
⇒ **修复优先级：先修"谁写 phase"，再谈"怎么读 phase"**。D5 描述的"事后拼装"是现象。

**精化 2：超时不是"忘了处理"，是两处判据互相打架。**

| 行 | 代码 | 语义 |
|---|---|---|
| `ReActToolLoop.ts:1919` | `if (this.loopState.loopDetected) return false;` | 循环检测出口 |
| `ReActToolLoop.ts:1922-1929` | 超时 ⇒ `logger.warn` + `return false`，**不置 phase** | **短路**了 `:1930` 的判据 |
| `ReActToolLoop.ts:1930` | `return result.toolCalls.length > 0;` | 正常判据（超时**根本走不到**） |
| `ReActToolLoop.ts:2010` | `if (result.toolCalls.length > 0) return false;` | 救援入口**又一次**用"有工具调用"拒绝救援 |
| `ReActLoop.ts:628` | `phase = 'completed'` | 落终态 |

⇒ **`shouldContinue` 说"停"，`onIncompleteTurn` 说"这不是我的锅"**。已产出的 tool_calls 从此无人认领，**静默消失（必然，非"可能"）**。
⇒ 修法应是统一的：**先定"这批调用怎么处置"，再决定停不停**（即 F2-0）。

**精化 3：主聊天路径「从未接入」既有 A2 判别器 —— 不是没有机制，是没通电。**

| 既有机制（已核实存在） | 位置 |
|---|---|
| `export type TerminationReason` | `app/src/query/ReActLoop.ts:78` |
| `getTerminationReason(): TerminationReason` 统一判别器（aborted / error / budget_exhausted / max_turns / loop_detected / completed） | `app/src/query/ReActLoop.ts:398-416` |
| 子类钩子 `isLoopDetectedReason()` / `isBudgetExhaustedReason()` | `app/src/query/ReActLoop.ts:387-395` |
| 已消费方 | `TAORLoop.ts:1930/1936`（含 `override`）、`SubAgentEngine.ts:1040` |

而在 `ReActToolLoop.ts` 中检索 `TerminationReason` ⇒ **No matches found（零引用）**。
⇒ **F2-1 从"新建枚举"改为"接线"**：给 `ReActToolLoop` 补两个钩子 + 让出口调用判别器。

**B1「TAORLoop 有轮级重置」不精确 —— 实为 run 级归零，且键集只有 2 个。**
- 审核称 `TAORLoop.ts:2184-2185` 是"**轮级**重置"。
- 实读：该处位于 `reset()` 内，其上方注释原文为「**回合质量重试计数随 run 归零（不跨 run 累积）**」⇒ 是 **run 级**，非轮级。
- 且 `TAORLoop._incompleteRetries` 的键集**只有 `{ empty, planning }`**（`TAORLoop.ts:630-633`），而 `ReActToolLoop` 有 **4 键**（`empty / reasoning / planning / truncated`）⇒ "对齐"意味着 **4 键都要 run 级归零**。
- **影响**：若真按"轮级"实现，`empty` 类**每轮**都能再救一次，与"每类 1 次防死循环"的初衷冲突。**F2-4 定为：run 级归零 + 保留每类 1 次上限。**

**B2「编译器强制」的边界需精确化。**
- 审核称"未读 `ReActState` 定义，无法断言 `phase` 是否字面量联合" ⇒ **现已核实：是字面量联合**（`ReActLoop.ts:93-105`，8 个取值：`reasoning / acting / completed / aborted / error / truncated / budget_exhausted / yielded`，**无 `'timeout'`**）。
- **但结论要收紧**：`getTerminationReason()` 是 **if 链 + 末尾 `return 'completed'` 兜底**，**新增 `TerminationReason` 成员不会触发任何编译错误**。
- ⇒ "编译器强制"目前只在 **`phase` 赋值侧**成立（写非法 phase 会报错）；**判别链消费侧仍是软约束**。要达到 v0.1 所期望的"新增终止原因必被强制补全"，**必须给判别链加穷尽断言**（`switch` + `never` 兜底），否则仅接线不够。此为本计划对审核的进一步精确化，已落入 F2-1。

**B3「N2 副作用不对称」成立，但落点表述需校正。**
- `settleGoalForTurnDetached` 实读为 **2 处**：`:2053`（`compaction_stalled`，位于 `onIncompleteTurn` 内、**不在 `finalize`**）与 `:2151`（`turn_error`，在 `finalize` 的 loopDetected 分支）。
- 审核"maxIterations / budget_exhausted / error / 空消息兜底**四处**均不落 Goal"**成立**，但更准确的表述是：**`finalize` 内 4 个分支仅 1 处落 Goal**。已按此写入 R14。

### C. 未证实（1 条）

**C1「55–60s 共享 deadline」假设 —— 全仓未找到对应常量。**
- 审核据"grep 56.3s 与 file_read 56.0s 几乎相同"推断存在约 55–60s 的共享 deadline。
- 实测检索 `60000 / 60_000 / 55_000 / 55000 / 58_000`：**命中无一在 `grep` / `file_read` 路径**（均为 cron / agent / analytics / cache 的间隔常量）。
- 工具超时实际为：`TOOL_EXEC_TIMEOUT_MS` 默认 **300_000（5 分钟）**（`chat/services/ToolTimeoutWrapper.ts:42-47`）、`DEFAULT_TOOL_TIMEOUT = 30_000`（`constants/toolLimits.ts:53`）、`StreamingToolExecutor.toolTimeoutMs = 120_000`（`:98`）；`60_000` 常量只出现在 **代码执行类**工具（`CodeRunnerTool.ts:38`、`CrossPlatformRunner.ts:31`、`REPLToolImpl.ts:204`）。
- 且两个相关 env（`TOOL_EXEC_TIMEOUT_MS` / `REACT_LOOP_MAX_DURATION_MS`）在配置中**均未覆写**。
- ⇒ **记为待查（§八 #9），不写成结论**。另注：`withToolTimeout` 是 `Promise.race([executor(), timer])`，其注释自述"**底层工具无法强制取消**"（幽灵执行），故 56s 更可能是工具内部遍历/文件系统阻塞，需实测。

- **CS01（新增前先查已有）**：F2-1 由"新建枚举"改为"接线既有判别器"，即本条规则的直接产物（`ReActLoop.ts:78/387-395/398-416` 已存在）。

- **不新增 Mock/不估算**：兜底文案是**系统生成的事实性提示**（"已达 X 上限，以下是已得结论"），不可伪装成模型产出。

## 十二、一句话结论

**这不是"某处忘了写提示"，而是「用户看到什么」由三套不同源的判据各自拼凑、且多数终止路径**架构上**没有第二次开口的机会**；而其**真病根**是 `ReActLoop.ts:628` 在出口**提前写死 `phase='completed'`** —— 它污染了既有判别器的输入，使"事后拼装"成为必然（§三.5）。一期止血可立即消除静默空白；二期（**接线**既有 `TerminationReason` 判别器 + 统一两处对立判据 + 副作用归口）才是根因修复 —— 不做它，下次新增终止原因仍会重现同样的静默空白。
