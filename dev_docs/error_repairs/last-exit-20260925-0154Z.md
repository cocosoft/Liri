## 4. 结论（是什么 / 不是什么）

**【实证】① 不是崩溃、进程未退出**：全局 `unhandledRejection` 处理器记录后 `return`/不退出
（[main.ts:1474-1508](file:///e:/PY/Documents/CODES/PY_APP/app/src/main.ts#L1474-L1508)，注释原文「不退出进程，unhandledRejection 可能是非致命的」）；同一秒删除流程继续执行（52719）。

**【实证】② 触发者是"删除正在运行的会话"**：`deleteSession` 会对该会话的 abort controller 调 `abort(SYSTEM_ABORT_REASON)`
（[SessionLifecycleManager.ts:549-556](file:///e:/PY/Documents/CODES/PY_APP/app/src/chat/services/SessionLifecycleManager.ts#L549-L556)；HTTP 断开路径同源见 [ChatManager.ts:407-419](file:///e:/PY/Documents/CODES/PY_APP/app/src/chat/ChatManager.ts#L407-L419)），
而 `SYSTEM_ABORT_REASON = 'liri:system-abort'` 是**裸字符串**常量（[ReActLoop.ts:120](file:///e:/PY/Documents/CODES/PY_APP/app/src/query/ReActLoop.ts#L120)）。**系统侧中止是设计内的预期行为**（用于把 Goal 落成 `system_aborted` 而非 `user_aborted`）。

**【实证】③ 判据缺口 ⇒ 预期中断被误记为错误**：全局处理器的 `isAbort` 只认 `DOMException/Error` 形态
（[main.ts:1479-1483](file:///e:/PY/Documents/CODES/PY_APP/app/src/main.ts#L1479-L1483)：`reason instanceof DOMException && name==='AbortError'` 或 `reason instanceof Error && (name==='AbortError' || message.includes('aborted'))`）。
裸字符串 `'liri:system-abort'` **两条都不满足**（既非 Error，也不含 `aborted`）⇒ 落入"非预期"分支：`writeCrashDump` + `logger.error` + `handleError`（`UNHANDLED_ERROR / severity: medium`）。
这与该分支 2026-08-30 的既定意图（「避免"正常取消操作"被误报为错误污染告警」）**相悖**——即**漏判**，不是过判。

**【未定位】④ 外泄的具体 promise 链**：reason 非 Error ⇒ 无抛出点栈；当前只能确定"发生在被中止的那次 LLM 请求链上"（同秒 provider/FetchInterceptor 均报同一 reason）。

**【跨系统观察】**：同类 `main`/`error` 级 `unhandledRejection` 在留存日志中累计 **36 次 / 7 个轮转文件**（2026-09-12 ~ 09-25，其中 09-21 一轮 17 次）；**未逐条判定是否同因**（复核命令见 §9）。

## 11. 顺带发现（新，**未修**）：`deleteSession` 在流式进行中于 Windows 命中 `EPERM`

**现象（实测，2026-09-25T11:44:56.624Z）**：

```json
{"level":"error","module":"session:storage","message":"[deleteSession] EPERM: operation not permitted, rename '…\\sessions\\57971aa3\\session_mugw8pvni78yr7r0nqo' -> '…\\sessions\\57971aa3\\.trash\\session_mugw8pvni78yr7r0nqo_1790336696594'","meta":{"category":"unknown","severity":"medium","code":"UNHANDLED_ERROR","context":{"originalType":"object"}}}
```

**触发条件**：删除一个**仍有在飞流式请求**（约 2s 前发起）的会话。该次删除**仍返回 200**、会话**已从列表移除**（`chat:manager deleteSession:会话删除完成 {elapsedMs:38}`）。

**磁盘实际状态（已核对）**：会话目录**未被移入 `.trash`**、**仍留在原地**（含 `events.jsonl` 75,845 B / `messages.jsonl` / `session.json` / `memory.md`）⇒ **列表已删、磁盘残留的"孤儿目录"**。

**成因（推断）**：在飞流仍持有会话目录内文件的句柄 ⇒ Windows 不允许 `rename`（POSIX 下可删除"已打开"文件，Windows 不行）。

**与本说明主线索的关系**：**同源场景**（删除正在运行的会话）但**不同缺陷** —— 本条是文件占用（I/O 层），主线索是 abort reason 的**判据漏判**（分类层）。

**建议**：与 §7-③ 一并处理 —— 即"删除会话时应先 abort 并等待流收敛，再执行目录操作"；是否需要在 `deleteSession` 中串行化（abort → 等待 → rename）需评估其与现有软删/`.trash` 语义的兼容性。**本轮未改**（超出建议①范围）。
