# 提示词中文化分析报告

**版本**: 1.0  
**日期**: 2026-05-22  
**范围**: `backend/src/` 下所有系统提示词、工具提示词、模板提示词  
**目标**: 统一全中文提示词（必要英文除外），消除语言混杂导致的 AI 行为不一致，为后续国际化（i18n）做准备  

---

## 背景与原则

### 为什么需要中文化

1. **身份一致性**：AI 应使用用户母语（中文）思考和工作，语言即身份
2. **消除混淆**：中英混杂的提示词可能导致 AI 在回复语言上摇摆不定
3. **统一体验**：工具提示词已全部为中文，但系统级提示词仍为英文，形成分裂

### 中文化原则

- **正文全中文**：所有提示词指令、描述、说明使用中文
- **保留英文**：以下内容保持英文不变：
  - 代码中保留的英文标识符（如 `<analysis>`、`<summary>` 标签、JSON 字段名）
  - 技术术语（如 `stdout`、`stderr`、`exitCode`、`API`）
  - 特殊标记（`[Previous conversation summarized]` 等）
- **注释保持中文**：代码中的注释使用中文（已有中文的保留，英文的翻译）
- **常量/变量名保持英文**：提示词字符串的变量名（如 `BASH_TOOL_PROMPT`）保持英文不变

### i18n 规划

1. **当前阶段**：全中文提示词（不引入 i18n 框架）
2. **第二阶段**：用简单 i18n 机制（如 key-value JSON 文件）统一管理提示词
3. **第三阶段**：多语言支持（中/英/日等），通过用户配置选择语言

> 当前仅执行第一阶段，直接替换提示词正文为中文字符串。后续阶段时机成熟时另行规划。

### B 类 — 对话压缩提示词（定位：系统级，直接影响对话摘要质量）

#### B1. `services/compact/prompt.ts`（~280 行，提示词正文）

**当前状态**：全部英文，包含：
- `NO_TOOLS_PREAMBLE` — 禁止调用工具的提示前导
- `DETAILED_ANALYSIS_INSTRUCTION_BASE` — 完整对话分析指令
- `DETAILED_ANALYSIS_INSTRUCTION_PARTIAL` — 部分对话分析指令
- `BASE_COMPACT_PROMPT` — 完整压缩提示词模板
- `PARTIAL_COMPACT_PROMPT` — 部分压缩提示词模板
- `PARTIAL_COMPACT_UP_TO_PROMPT` — 前置压缩提示词模板
- `NO_TOOLS_TRAILER` — 禁止调用工具的尾注

**变更复杂度**：**高**。因为：
1. 提示词正文很长（~200 行有效指令文本）
2. 定义了结构化的输出格式（section 标题、示例结构）
3. 需保留 `<analysis>`、`<summary>` XML 标签为英文（输出格式约定）
4. 示例中的英文占位符文本需中文化
5. `NO_TOOLS_PREAMBLE` 和 `NO_TOOLS_TRAILER` 中的关键指令（如 "Do NOT call unknown tools"）需保留英文关键短语但补充中文说明

**示例中文化映射**：

| 当前英文 Section 标题 | 建议中文 |
|----------------------|---------|
| `Primary Request and Intent` | `主要请求与意图` |
| `Key Technical Concepts` | `关键技术概念` |
| `Files and Code Sections` | `文件与代码段落` |
| `Errors and fixes` | `错误与修复` |
| `Problem Solving` | `问题解决` |
| `All user messages` | `所有用户消息` |
| `Pending Tasks` | `待处理任务` |
| `Current Work` | `当前工作` |
| `Optional Next Step` | `可选下一步` |

**特殊保留内容**：
- `<analysis>` 和 `<summary>` XML 标签 — 输出格式协议，必须保留英文
- `\`\`\`` 代码块标记 — 格式标记，保留
- 示例 JSON — 内容可中文化，但字段名（如 `file_name`）保持英文

## 中文化实施计划

### 总体方案

```
1. 先做 D 类（杂项，风险最低）→ 熟悉流程
2. 再做 A 类（身份与行为提示词，影响面广但量少）
3. 再做 C 类（记忆提取，中等复杂度）
4. 最后做 B 类（对话压缩，最复杂）
```

### 执行顺序

| 优先级 | 文件 | 预估工作量 | 说明 |
|-------|------|----------|------|
| 🥇 1 | `buddy/prompt.ts` | 1 处，~10 行 | 低风险，可快速完成 |
| 🥇 2 | `constants/prompts.ts` | ~18 处语句 | 低风险，纯字符串替换 |
| 🥇 3 | `context/PromptTemplates.ts` | ~8 条语句 | 影响系统身份，但修改简单 |
| 🥇 4 | `constants/systemPromptSections.ts` | ~1 段落 | 同上 |
| 🥇 5 | `services/SessionMemory/prompts.ts` | ~1 模板 | 简单模板翻译 |
| 🥈 6 | `services/extractMemories/prompts.ts` | ~50 行 | 中等复杂度，需保留输出协议 |
| 🥉 7 | `services/compact/prompt.ts` | ~280 行 | 最复杂，需仔细处理输出格式协议 |

### 注意事项

1. **保留协议标记**：`TYPE:` / `TITLE:` / `CONTENT:` / `CONFIDENCE:`、`<analysis>` / `<summary>`、`\`\`\`` 等格式标记保持英文
2. **保留技术术语**：`stdout`、`stderr`、`exitCode`、`API`、`JSON`、`Git`、`PID` 等保持英文
3. **保留代码标识符**：`task_id`、`file_path`、`operation` 等 JSON 字段名保持英文
4. **不修改变量名**：提示词字符串的导出变量名（如 `BASH_TOOL_PROMPT`）保持英文不变
5. **保持换行和缩进**：中文化后保持原有换行和缩进格式
6. **注释使用中文**：已有注释（如 `基于CC源码`）保持中文
